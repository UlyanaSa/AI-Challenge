### task-3

День 3. Разные способы рассуждения

Возьмите одну задачу
(логическую, алгоритмическую или аналитическую)

Решите её через API четырьмя способами:

- получите прямой ответ без дополнительных инструкций
- добавьте в промпт инструкцию: «решай пошагово»
- попросите модель сначала составить промпт для решения задачи,
  а затем используйте его
- создайте в промпте группу экспертов
  (например: аналитик, инженер, критик)
  и получите решение от каждого

Сравните:

- отличаются ли ответы
- какой способ дал наиболее точный результат

**Результат:** несколько решений одной задачи и их сравнение.

**Заключение (проверено на загадке «С какой скоростью должна двигаться собака, чтобы не слышать звона сковородки, привязанной к её хвосту?»):**

Все четыре способа решают задачу, но по-разному раскрывают её. Ключевой момент — в условии спрятана ловушка: сковородка привязана к самой собаке, поэтому звук распространяется к её ушам и по воздуху, и через кости черепа (костная проводимость), и убежать от собственного звона невозможно — задача шуточная. Лучше всех это вскрыл вариант с составленным промптом.

| Вариант | Суть ответа | Токены (вх/вых/всего) | Время, с | Скорость, ток/с | Длина, симв | Стоимость | Точность | Глубина |
|---|---|---|---|---|---|---|---|---|
| Прямой ответ | Физически невыполнимый ответ «быстрее звука», краткий разбор парадокса | 45/587/632 | 6,7 | 88 | 1803 | $0,000658 | 8/10 | 9/10 |
| «Решай пошагово» | Те же выводы по шагам: звон идёт по воздуху и костям, в пределах возможного собаки — невыполнимо | 74/627/701 | 6,4 | 98 | 2009 | $0,000710 | 9/10 | 9/10 |
| Составленный промпт | Самый полный разбор: ошибка условия, костная проводимость, все трактовки и итог | 962/2430/3392 | 23,2 | 105 | 7653 | $0,002933 | 8/10 | 9/10 |
| Группа экспертов | Аналитик (физика волн), инженер (пути передачи звука), критик (ошибка постановки) | 237/2051/2288 | 22,5 | 91 | 6496 | $0,002320 | 7/10 | 6/10 |

Ответы отличаются по полноте и глубине. Вердикт модели-судьи (параметры: правильность, полнота, обоснованность, ясность): наиболее точное — решение «составленный промпт»: оно единственное полностью вскрывает скрытую ошибку условия (костная проводимость) и систематизирует все трактовки; решение группы экспертов сильно, но менее структурировано и содержит избыточные рассуждения.

Вывод по способам: дорогие многошаговые способы (составленный промпт, эксперты) дают заметно более полные ответы ценой ~4–5× больше токенов и времени, чем прямой ответ или пошаговое решение.

### task-4

День 4: Температура

Выполните один и тот же запрос с параметрами:

- temperature = 0
- temperature = 0.7
- temperature = 1.2

Сравните ответы по:

- точности
- креативности
- разнообразию

Сформулируйте:

- для каких задач лучше подходит каждая настройка

**Результат:** примеры ответов с разной температурой и выводы по их использованию.

**Заключение (проверено на задаче «Предложи 5 разных идей необычного музея, каждая идея — одним предложением и обязательно про звук; музей тишины подходит, а музей картин — нет»):**

Один и тот же запрос прогнан при temperature 0 / 0.7 / 1.2 (по два прогона на каждое значение) через собственный сервер. Задача-зонд покрывает все три критерия сразу: условие «5 идей, все про звук» измеримо (точность), выбор тем свободен (креативность), пересечение прогонов считается (разнообразие). Закрытая задача-ловушка («17 овец», правильный ответ 9) для этой проверки не годится: у неё нет простора для креативности — все температуры дали верный ответ 7/7, и ответы неразличимы по структуре.

| temperature | Идей из 5 (2 прогона) | Про звук | Пересечение прогонов | Примеры идей |
|---|---|---|---|---|
| 0 | 5/5 и 5/5 | 10/10 | 2 из 5 (Jaccard 0,25): «Эхо исчезнувших профессий», «Тишина в движении» | «Эхо исчезнувших профессий», «Голоса вещей», «Шум времени» |
| 0.7 | 5/5 и 5/5 | 10/10 | 0 (Jaccard 0) — темы переформулированы | «Симфония вещей», «Слушая землю», «Шёпот стен» |
| 1.2 | 5/5 и 5/5 | 9/10 | 0 (Jaccard 0) | «Предсмертный треск пластинок», «Шёпоты птичьих перелётов», «Слуховая амнезия» |

- **Точность** (следование условию) стабильна: 5/5 идей и 10/10 «про звук» при 0 и 0.7. При 1.2 — 9/10: единственное во всём эксперименте отклонение («Музей дыхания архитектуры» — звук через старинные органы) случилось именно на максимальной температуре.
- **Креативность** растёт с температурой: 0 даёт «надёжное» ядро идей, 1.2 — смелые и образные («предсмертный треск пластинок», «слуховая амнезия»).
- **Разнообразие** между прогонами растёт с температурой: при 0 два прогона делят 2 идеи из 5, при 0.7 и 1.2 пересечение нулевое — каждый прогон даёт полностью новый набор.

Вывод по настройкам: temperature 0 — когда нужен один воспроизводимый результат (шаблоны, A/B-варианты); 0.7 — «похожее, но свежее» для регулярной генерации: идеи не выпадают из ожидаемого пула, а формулировки новые; 1.2 — мозговой штурм: прогнать 3–5 раз и объединить списки, приняв риск выхода за рамки условия. На задачах с единственно верным ответом температура до 1.2 точность не роняет — её влияние проявляется на открытых задачах.

**Результат:** сравнение одного запроса на моделях разного уровня: время, токены, стоимость, качество.

**Заключение (проверено на вопросе «Почему ночью небо тёмное, если Вселенная бесконечна и заполнена звёздами? Объясни парадокс Ольберса и как он разрешается»):**

В приложение добавлен выбор модели из живого списка DeepSeek `/v1/models` (начало/середина/конец списка): `deepseek-v4-flash` (быстрая и дешёвая), `deepseek-v4-pro` (сильная, тяжёлая), `deepseek-v4-flash-vision-exp` (экспериментальная, Flash со зрением). Сервер замеряет каждый прогон: время, токены (вход → выход), скорость и стоимость по тарифам DeepSeek V4 на 07.09.2026 (Flash $0.22/$0.66, Pro $0.66/$1.98 за 1 млн токенов; у vision-модели опубликованного тарифа нет).

| Модель | Время | Токены вх→вых | Скорость | Стоимость | Длина ответа |
|---|---|---|---|---|---|
| V4 Flash | 29,8 с | 129→1461 | 48 ток/с | ≈$0,00099 | 3501 симв |
| V4 Pro | 55,4 с | 129→1401 | 25 ток/с | ≈$0,00286 | 2902 симв |
| V4 Flash Vision (exp) | 14,1 с | 129→1465 | 103 ток/с | тариф не опубликован | 3769 симв |

- **Качество:** все три модели корректно разрешают парадокс Ольберса (конечный возраст Вселенной, конечная скорость света, расширение и красное смещение). Vision-модель дала самый полный ответ (5 из 7 ключевых пунктов разрешения против 4 у Flash и Pro), хотя по архитектуре это Flash со зрением.
- **Скорость:** Pro самая медленная (25 ток/с — тяжёлая модель, ~1,6T параметров), Flash быстрее (48 ток/с), Vision — самая быстрая (103 ток/с). Первый прогон Flash (38 ток/с, 126 с) — выброс из-за пиковой нагрузки API: серия обрывов по лимиту с автоувеличением бюджета; на повторе Flash отработала за 29,8 с.
- **Ресурсоёмкость:** Pro дороже Flash примерно в 3 раза по тарифу и в ~2,9 раза по факту на этом вопросе ($0,00286 против $0,00099) при сопоставимой длине ответа. Стоимость растёт вместе с «силой» модели.
- **Практический вывод:** на этом вопросе сильная модель не дала заметного выигрыша в качестве — Flash справилась с тем же результатом в ~3 раза дешевле. Pro оправдана там, где Flash реально ошибается (сложная логика, код); vision-модель в текстовых задачах ведёт себя как быстрый Flash, её преимущество — только в работе с изображениями.

Стоимость считается по финальному запросу прогона; при обрыве по лимиту сервер повторяет запрос с увеличенным бюджетом (пометка «лимит увеличен до N» в отчёте), и промежуточные запросы в сумму не входят. Также в этот день поднят таймаут HTTP-клиента сервера с дефолтных ~15 с до 300 с: сильные модели на длинных ответах не укладывались в дефолт.

### task-6

День 6. Свой агент

Реализуйте простого агента, который:

- принимает запрос пользователя
- отправляет его в LLM через API
- получает ответ
- выводит результат в вашем интерфейсе (простой чат, CLI или web, запросы через HTTP-клиент)

Важно: агент должен быть отдельной сущностью, а не просто один вызов API; логика запроса и ответа должна быть инкапсулирована в агенте.

**Результат:** агент принимает запрос и корректно вызывает LLM через API.

**Заключение.** Вся работа с моделью вынесена из HTTP-маршрута в отдельную сущность — агент `LlmAgent`, размещённый в отдельном Gradle-модуле `:agent` (`agent/src/main/kotlin/com/osvin/aichallenge/agent/LlmAgent.kt`). Сервер зависит от модуля (`implementation(project(":agent"))`), но не содержит логики обращения к модели:

- **`LlmAgent`** — сам агент: принимает набор параметров `AgentOptions` (модель, лимит токенов, температура, стоп-слова, свой system prompt и история диалога), нормализует их к допустимым границам, собирает сообщения (system prompt → история → текущий запрос), делает один вызов LLM через `LlmClient` и возвращает `AgentResult` — ответ модели и расход токенов.
- **`LlmClient`** — контракт транспорта к LLM API. Агент не знает про HTTP: транспорт передаётся снаружи, поэтому логика агента тестируется без сети.
- **`DeepSeekClient`** — HTTP-реализация контракта через Ktor: авторизация, отправка `DeepSeekRequest`, разбор ответа и ошибок API.
- **DTO `DeepSeekRequest`/`DeepSeekResponse`/`ChatMessage` и `AppConfig`** — модели LLM API и конфигурация агента; лежат в том же модуле `:agent`.
- Маршрут `POST /v1/chat/completions` в `:server` стал тонким адаптером: принять `ChatRequest` (включая `systemPrompt` и `history`), создать агента через `DeepSeekClient`, вызвать `agent.run(...)`, вернуть `ChatResponse`. Логики обращения к модели в маршруте больше нет.

Многократные прогоны одного вопроса, сверка и настройка формата ответа убраны: агент просто ходит в API с заданными параметрами.

Интерфейс — Compose Multiplatform (Android / iOS / Web). При запуске открывается экран создания чата «Новый чат»: агент настраивается до первого сообщения (модель, температура, лимит токенов, стоп-слова, system prompt), после кнопки «Начать чат» открывается диалог. Кнопка «＋» в шапке создаёт новый чат с настройкой агента заново; параметры уже запущенного чата не меняются. Чат отправляет запрос на тот же endpoint по HTTP и показывает ответ агента сообщением ассистента, передавая агенту свой system prompt и предыдущие сообщения диалога — модель отвечает с учётом контекста. Контракт HTTP не изменился.

**Проверка.** Юнит-тесты агента (`agent/src/test/kotlin/com/osvin/aichallenge/agent/LlmAgentTest.kt`) на подменном `LlmClient` проверяют без сети: сборку одного запроса (модель / температура / лимит / стоп-слова), порядок сообщений (system prompt → история → текущий запрос) и возврат ответа модели с расходом токенов.

Запрос через API с system prompt и историей (сервер поднят, запрос отправлен HTTP-клиентом; имя есть только в истории):

```
curl -X POST http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"message":"Как меня зовут? Ответь одним словом.","model":"deepseek-v4-flash","maxTokens":128,"temperature":0,
       "systemPrompt":"Отвечай предельно кратко, одним словом.",
       "history":[{"role":"user","content":"Меня зовут Улан"},{"role":"assistant","content":"Приятно познакомиться, Улан"}]}'
```

```
HTTP 200
{"success":true,"reply":"Улан","usage":{"prompt_tokens":75,"completion_tokens":50,"total_tokens":125}}
```

Агент собрал сообщения из system prompt, истории и текущего запроса, вызвал LLM через API и вернул ответ модели как есть (`Улан`).


### task-7

День 7. Сохранение контекста

Добавьте агенту сохранение контекста:

- храните историю диалога (messages) в JSON или SQLite
- при перезапуске агента загружайте историю обратно
- продолжайте диалог так, как будто агент не выключался

**Результат:** агент, который сохраняет и восстанавливает контекст между запусками.

**Заключение.** История диалога лежит в SQLite через Room и поднимается обратно при старте приложения:

- **`ChatHistoryStore`** (`app/shared/src/commonMain/kotlin/com/osvin/aichallenge/data/ChatHistoryStore.kt`) — контракт хранилища: `load()`, `append(message)`, `clear()`. Он в общем коде, поэтому репозиторий и UI не знают, куда именно пишутся сообщения.
- **`RoomChatHistoryStore`** (`app/androidApp/src/main/kotlin/com/osvin/aichallenge/data/RoomChatHistoryStore.kt`) — реализация на Room: таблица `chat_messages` (`ChatMessageEntity` — id, role, content, timestamp), DAO с suspend-запросами (`all()` / `insert()` / `deleteAll()`), база `ChatHistoryDatabase` (версия 1, файл `chat-history.db`). Room подключён к Android-модулю (KSP + `androidx.room`), так как для iOS/Web его артефактов нет; на этих таргетах работает `InMemoryChatHistoryStore` — там история живёт в памяти процесса и перезапуск не переживает.
- **`ChatRepository`** получает хранилище в конструкторе, грузит историю (`loadHistory()`) и дописывает оба сообщения — и пользователя, и ассистента; `clearHistory()` чистит и память, и базу.
- **`ChatViewModel`** загружает сохранённый диалог в `init` и отдаёт UI признак `historyLoaded`.
- **`App`** по этому признаку выбирает первый экран: есть сохранённые сообщения — сразу открывается чат с прежней перепиской, нет — экран «Новый чат».

**Позже (день 9)** хранилище выросло до чатов: вместо `ChatHistoryStore` — `ChatStore` (`data/ChatStore.kt`, модель `data/Chat.kt`), вместо `RoomChatHistoryStore` — `RoomChatStore` (`data/RoomChatStore.kt`, база `ChatDatabase` версии 2), сохранённая история при обновлении переезжает в отдельный чат; подробности — в разделе `task-9`.

**Проверка на устройстве** (эмулятор Android, `./gradlew :app:androidApp:assembleDebug` → `adb install -r`):

1. «My name is Ulan» → ассистент: «Nice to meet you, Ulan! How can I help you today?». В `chat-history.db` появились две строки: `role=user` и `role=assistant`.
2. `adb shell am force-stop com.osvin.aichallenge` — приложение и его процесс убиты.
3. Запуск заново: открылся не экран настройки, а чат с теми же двумя сообщениями — история восстановлена из Room.
4. «What name do I have answer with one word» → ассистент: «Ulan». Контекст прежнего диалога сохранён, агент отвечает так, как будто не выключался.
5. Кнопка «＋» → «Начать чат»: экран пустой, таблица `chat_messages` пуста — новый диалог стирает историю и в памяти, и в базе.

Добавьте в код агента подсчёт токенов:

- для всей истории диалога
- для ответа модели

Сравните:

- короткий диалог
- длинный диалог
- диалог, который превышает лимит модели

Покажите:

- как растёт стоимость/токены по мере диалога
- что ломается при переполнении

**Результат:** код, который считает токены и показывает, как они влияют на поведение агента.

**Заключение.** Агент считает токены по частям и следит за границами модели:

- **`TokenCounter`** (`agent/src/main/kotlin/com/osvin/aichallenge/agent/TokenCounter.kt`) — счётчик: `count(text)` для текста и `countPrompt(messages)` для всего запроса (обвязка чата + обвязка каждого сообщения + текст). ### task-9

День 9. Управление контекстом: сжатие истории

Научите агента управлять контекстом:

- последние N сообщений отправляйте в модель как есть
- более старые сообщения сворачивайте в summary (например, каждые 10 сообщений)
- summary храните отдельно и подставляйте в запрос вместо полной истории

Сравните качество ответов и расход токенов без сжатия и со сжатием истории.

**Результат:** агент, который сжимает историю и экономит токены.

**Заключение.** Политика сжатия живёт в агенте, состояние — по сессии:

- **`HistoryCompressor`** (`agent/src/main/kotlin/com/osvin/aichallenge/agent/HistoryCompressor.kt`): последние `keepLastMessages = 10` сообщений уходят в модель как есть, старшие сворачиваются в сводку, как только их накопится `compressStep = 10`. `plan(history, stored)` возвращает `HistoryPlan` — что оставить (`recent`), что свернуть (`toFold`) и какая сводка уже есть; `summaryRequest(...)` собирает служебный запрос «сверни эти сообщения в факты»; `summaryMessage(...)` подставляет готовую сводку в основной запрос служебным сообщением с ролью `system`.
- **`SummaryStore`** (`.../SummaryStore.kt`): `get(sessionId)` / `put(sessionId, summary)` / `clear(sessionId)`, реализация `InMemorySummaryStore` держит `StoredSummary(text, foldedMessages, tokens)` в `ConcurrentHashMap` — сводка хранится отдельно от сообщений. Вместе с текстом хранится число свёрнутых сообщений: если диалог начали заново (`stored.foldedMessages > history.size`), сводка отбрасывается, иначе бюджет из прошлого диалога попал бы в новый.
- В агенте сжатие выключено по умолчанию (`AgentOptions.strategy = ContextStrategy.FULL`), сервер включает его для запросов приложения (стратегия `summary` — см. день 10): поведение без сессии и прежние сценарии агента не изменились. Позже, в день 10, стратегия стала явным переключателем (`AgentOptions.strategy`), а сжатие — одной из четырёх стратегий рядом с окном, памятью фактов и ветками.
- Сжатие **серверное**: клиент, как и раньше, присылает всю историю, а `sessionId` (32 hex-символа, генерируется один раз на жизнь `ChatRepository`) говорит серверу, к какому диалогу относится сводка. Так сводка не требует ни миграций Room, ни хранения её на клиенте.
- **Сбой сводки не теряет диалог**: если служебный вызов упал (сеть, 4xx, отмена) или вернул пустой текст, сводка не обновляется и в модель уходит полная история; в отчёте при этом `foldedMessages = 0`, а `history == historyRawTokens`.

**Правило system prompt.** Свой system prompt из настроек важнее: если он задан, в модель уходит он. Если нет — его роль играет **первое сообщение диалога**:

- на первом ходу диалога истории ещё нет, поэтому system prompt — это текущее сообщение: инструкция из него действует сразу, а не со следующего хода;
- первое сообщение остаётся и в истории обычным сообщением пользователя: диалог не теряет начало (небольшое дублирование текста в ролях `system` и `user`);
- это же первое сообщение **не сворачивается вместе со старшими** — сводка уезжает в модель вместо свёрнутых сообщений, а исходная инструкция остаётся в силе, потому что её несёт system prompt. Так инструкция из первого сообщения переживает сжатие.

Правило живёт в агенте (`LlmAgent`, строки с `val systemPrompt`), а не в клиенте: агент видит всю историю, а клиент по-прежнему присылает пустой `systemPrompt`, если поле в настройках не заполнено. В настройках клиента у поля есть подсказка: «Пусто — их задаёт первое сообщение чата». В разбивке токенов такой system prompt виден в поле `system_prompt_tokens`, как и свой.

**Что видно в отчёте.** `TokenReport` (`agent/.../TokenReport.kt` и `app/shared/.../data/TokenReport.kt`) получил поля `historyRawTokens`, `summaryTokens`, `foldedMessages`, `compressionTokens`, `compressionCostUsd`: `history` — сколько истории реально ушло, `historyRawTokens` — сколько ушло бы без сжатия. ### task-10

День 10. Управление контекстом: три стратегии без сжатия в сводку

Тот же агент должен уметь вести диалог по-разному и переключаться между стратегиями:

- **скользящее окно**: в модель уходят только последние сообщения диалога;
- **память фактов**: важное из диалога копится списком «ключ — значение» и переживает отброшенные сообщения;
- **ветки диалога**: от любой точки диалога можно продолжить его в сторону, и в модель уходит только путь активной ветки.

Стратегию выбирает пользователь. Один и тот же сценарий (сбор ТЗ, 14 сообщений) прогоняется на каждой стратегии, результаты сравниваются по качеству ответа, стабильности (не теряются ли важные детали), расходу токенов и удобству.

**Результат:** агент с тремя стратегиями управления контекстом плюс сравнение результатов.

**Где что лежит.**

- **`ContextStrategy`** (`agent/src/main/kotlin/com/osvin/aichallenge/agent/ContextStrategy.kt`): `FULL`, `SLIDING_WINDOW`, `FACTS`, `BRANCHES` и `SUMMARY` — сжатие из дня 9 стало одной из стратегий того же переключателя, а не отдельным флагом (`AgentOptions.compressHistory` больше нет). Значение уезжает по проводу (`wire`) и попадает в лог и отчёт; неизвестное значение сервер считает сжатием, поэтому старое приложение продолжает работать как в дне 9. Свойства `usesWindow` и `keepsState` говорят, нужен ли стратегии размер окна и состояние сессии.
- **`Facts`** (`.../Facts.kt`): список `ключ → значение` с обрезкой (до 20 фактов по 200 символов) и дедупликацией по ключу; хранилище `FactsStore` держит память по сессии отдельно от сообщений.
- **`FactsExtractor`** (`.../FactsExtractor.kt`): служебный вызов «обнови память» — прежние факты, последние два сообщения и новый вопрос; ответ строгим JSON. Разбор терпит ```-обёртку и мусор: если JSON не разобрался, остаются прежние факты, и в логе появляется строка об этом.
- **`DialogBranches`** (`.../DialogBranches.kt`): путь активной ветки — общая часть до точки ветвления плюс сообщения своей ветки; вложенные ветки и защита от петли. Метки `branchId` расставляет клиент, а в API сообщения уходят без них.
- **`LlmAgent.planContext`** — одна точка, где решается, что из присланной истории уйдёт в модель; служебные вызовы стратегий (сводка, память фактов) живут там же, и их сбой диалог не ломает.
- **Отчёт** (`TokenReport`) получил `strategy`, `windowMessages`, `droppedMessages`, `excludedMessages`, `branchId`, `facts`, `factsTokens`, `factsUpdateTokens`, `factsUpdateCostUsd`: в логе агента видны блоки «Скользящее окно истории», «Память фактов», «Ветки диалога» и «Сжатие истории», а клиент печатает те же строки в logcat.
- **Переключатель** — в шторке настроек чата: селектор стратегии и поле размера окна (`GenerationSettingsForm`), настройка живёт в `GenerationSettings` и уезжает полями `strategy` и `windowMessages` запроса, а с дня 11 стратегия хранится у самого чата (`Chat.strategy`, миграция 3→4) и переключается ещё и из шторки памяти — от неё зависит, читает ли чат свою память (см. день 11); сервер отображает запрос в настройки агента в одном месте (`ChatRequestOptions.kt`). Варианты продолжения живут на самих сообщениях: у сообщения, от которого диалог разошёлся, видно «‹ 2/3 ›» (`DialogBranches.choiceAfter`), стрелка переключает активную ветку, а «Ветка от этого сообщения» заводит новое продолжение. Отдельного меню веток и шага «перейти в ветку» нет, а блок «Память фактов» показывает, чем агент помнит диалог.

**Сцена сравнения** (`ContextStrategiesDemoTest`): пользователь собирает ТЗ на приложение учёта расходов — 14 сообщений, важные детали названы в начале (цель, бюджет 300 000 ₽, срок 6 недель, платформа Android, без регистрации, данные на устройстве, графики на Compose, сводка по пятницам, экспорт CSV, без синхронизации). Затем один и тот же вопрос: «Собери короткое ТЗ: перечисли цель, бюджет, срок, платформу, ограничения, принятые решения и договорённости». У стратегий окна и фактов окно выбрано маленьким (6 сообщений), чтобы сцена действительно упиралась в предел контекста. Каждый ответ модели оценивается по числу важных деталей, которые в нём уцелели, — это и есть мера стабильности.

| память фактов | 9 | 7 176 | 4 255 | 52 656 | 8 из 10 |
| ветки диалога | 20 | 18 625 | 2 979 | 0 | 9 из 10 |

Деньги того же прогона: окно — $0.046 за 15 вызовов, память фактов — $0.079 за 30 вызовов (обновление памяти идёт на каждое сообщение), ветки — $0.015 за продолжение ветки и вопрос: общая часть диалога из 16 сообщений одна на обе ветки, поэтому в модель она уходит один раз, а не два.

**Ветки диалога.** Точка ветвления — после восьмого сообщения пользователя (16 сообщений). Обе ветки растут из неё в одной истории: в запрос каждой уходит 20 сообщений — 16 общих, 2 своих и вопрос, — а 2 сообщения соседнего продолжения остаются вне пути (это видно и в логе, и в `excludedMessages`). Ответы разошлись: «подписка» и «разовый платёж» дали разные ТЗ, при этом общий контекст не продублирован — вторая альтернатива не стоила повторной отправки всего диалога.

**Что показало сравнение.**

- **Качество и стабильность.** Скользящее окно потеряло детали из отброшенных сообщений: в ответе нет ни бюджета (300 000 ₽), ни срока (6 недель), ни Compose, ни CSV — осталось только то, что попало в последние шесть сообщений: 5 важных деталей из 10. Память фактов сохранила больше (8 из 10), но память же и исказила деталь: «бюджет проекта — 300 000 ₽» превратился в «в MVP нет бюджетов», и в ответе появилось «денежный бюджет не фиксировался» — неверный факт закрепился и пережил все следующие сообщения. Память при этом ограничена сверху (20 фактов): у длинного диалога самые старые факты вытесняются. Ветки не потеряли ничего (9 из 10): бюджет, срок и решения на месте, потому что в запрос уходит весь путь активной ветки.
- **Расход токенов.** Самый дешёвый вход — у окна (5 057 токенов против 7 176 у памяти фактов и 18 625 у веток). Память фактов платит за сохранность деталей отдельным вызовом на каждое сообщение: 52 656 служебных токенов за сцену — в семь с лишним раз больше, чем весь вход, и почти вдвое дороже окна. Ветки дороже по входу (в модель идёт весь путь диалога), но служебных вызовов не требуют.
- **Удобство.** Окно «просто работает» и ничего не требует от пользователя, но о потерянном контексте он узнаёт только из ответа. Память фактов показывает, чем агент помнит диалог: блок «Память фактов» на экране чата сразу выдаёт и то, что сохранилось, и то, что исказилось. Ветки дают лучший результат: вариант создаётся одним действием на сообщении, а переключаться между вариантами можно стрелкой там же, где диалог разошёлся, — переписывать или терять прежнюю линию не нужно; платой идёт растущий контекст (в модель уходит весь путь активной ветки).
- **Итог.** Для длинного сбора требований окно — самый рискованный вариант: оно теряет ровно те сообщения, где названы цель, бюджет и ограничения. Память фактов — компромисс: детали переживают окно, но каждое сообщение тянет служебный вызов, и память может закрепить неверный факт. Ветки — самый надёжный: ничего не теряется и альтернативы не смешиваются, если вести диалог деревом. Сжатие в сводку (день 9) остаётся четвёртой стратегией того же переключателя: оно дешевле памяти фактов и короче веток, но пересказывает историю свободным текстом, а не списком фактов.

**Проверка.** Стратегии проверяются отдельно от демонстрации: `./gradlew :agent:test --tests '*ContextStrategiesTest*'` — 15 тестов на сборку запроса (окно и его границы 2..100, короткий диалог, накопление памяти фактов и откат при негодном ответе, путь ветки и вложенная ветка, неизвестная ветка, метки веток не уходят в API, разбор ответа извлечения фактов). Клиентскую сторону проверяет `ContextStrategiesClientTest` (`app/shared/src/androidHostTest/...`, пять тестов на `MockEngine`): что уезжает в тело запроса, какой путь видит чат после переключения ветки, как ответ агента попадает в состояние и в лог. Отображение запроса в настройки агента закреплено в `ApplicationTest` (`:server:test`).

Схему БД сверяли отдельно, без устройства: SQL миграции 2→3 прогнали через `sqlite3` на базе версии 2 и сравнили результат с той схемой, которую ожидает Room (колонки, типы, `NOT NULL`, первичный ключ, индекс совпадают), — данные при этом остались на месте. Сам экран на устройстве не проверялся: приложение и эмулятор в этой задаче не запускались, проверка ограничена сборкой APK, host-тестами и сверкой схемы БД.


### task-11

День 11. Модель памяти агента: краткосрочная, рабочая и долговременная

Память агента делится на три типа, и это не три списка одного и того же, а три разных ответа на вопрос «сколько это живёт»: что сказано в диалоге, над чем работаем сейчас и что останется после задачи. Требование дня: типы хранятся отдельно, выбор «что куда» явный, и видно, какие данные попадают в каждый тип и как это меняет ответы агента.

**Результат:** три типа памяти с разными владельцами и временем жизни, названные словами задания — «краткосрочная (текущий диалог)», «рабочая (данные текущей задачи)», «долговременная (профиль, решения, знания)»; тип записи называет тот, кто её пишет: модель — в служебном ответе, человек — в шторке чата; управление памятью переехало из ленты сообщений в шторку, которую открывает кнопка «Память» в верхней панели; запись — это тип и одна фраза, без ключа и значения; отчёт ответа и лог агента показывают, что ушло в модель и чего это стоило; демонстрация сравнивает ответы с памятью и без неё.

**Три типа памяти — три владельца данных.**

| Тип (в коде — `MemoryLayer`) | Что хранит | Область | Где физически лежит | Время жизни |
| --- | --- | --- | --- | --- |
| краткосрочная (`SHORT_TERM`) | сообщения диалога: активный путь, а из него — то, что пустила стратегия | чат (сессия) | устройство: `chat_messages` (Room) / `InMemoryChatStore` | до удаления чата |
| рабочая (`WORKING`) | данные текущей задачи: цель, ограничения, числа, сроки, договорённости | профиль (все чаты) | сервер: `InMemoryMemoryStore` по `DEFAULT_PROFILE` | переживает чаты и отброшенные сообщения; обнуляется перезапуском сервера, вытеснением (20 записей) и забыванием в шторке |
| долговременная (`LONG_TERM`) | профиль пользователя, принятые решения, знания о проекте | профиль | сервер: `JsonFileMemoryStore`, файл `server/data/memory.json` | переживает чаты, их удаление и перезапуск сервера |

Отдельного хранилища для краткосрочной памяти не заводили: она уже отделена — сообщения живут с чатом на устройстве, сервер их не хранит, а стратегия лишь выбирает, что из них увидит модель. Следствие для удаления: `DELETE /v1/chats/{id}` чистит только сводку истории своей сессии — память агента от сессии не зависит, оба её слоя живут по профилю и удаления чата не замечают. Различаются слои не областью, а сроком жизни: рабочую обнуляет перезапуск сервера (она в памяти процесса), долговременная перезапуск переживает (она в файле). Долговременная память разделена по профилям, но профиль пока один: приложение отправляет `DEFAULT_PROFILE = "local"` не по проводу, а как ключ хранилища на сервере (`AgentOptions.profileId` не вводили — провод не менялся).

Подписи и пояснения типов живут в одном месте — в перечислении `MemoryLayer` (`title` и `hint`), а клиент получает их каталогом вместе со снимком памяти. Своей таблицы типов у клиента нет, поэтому подпись «рабочая (данные текущей задачи — общие для всех чатов)» в шторке не может разойтись с тем, что знает сервер.

**Что куда: тип называет тот, кто пишет.** Тип записи — и есть явный выбор «что куда», и он один и тот же для модели и для человека: в служебном ответе тип называет модель, в шторке — пользователь. Что при этом делает код:

| Правило | Что происходит |
| --- | --- |
| тип из трёх, названных в задании | запись сохраняется |
| тип неизвестен (`настроение`) | запись **отклоняется**, счётчик `memory.rejected` |
| тип `short_term` | запись **отклоняется**: это сообщения диалога, а не хранилище |
| тип, которого стратегия не ведёт | запись **отклоняется**: спрашиваем про свои типы, лишнее не храним |
| предел типа | рабочая — 20 записей, долговременная — 30, фраза до 200 символов; вытесняются самые старые (`memory.evicted`) |
| повтор фразы | заменяет прежнюю запись и становится самой свежей; пересказанная фраза становится второй |

Здесь же — цена решения, о которой стоит сказать прямо. В прежнем варианте этого дня слой решала таблица видов, и «данные задачи» не могли уехать в долговременную память по воле модели; теперь тип называет тот, кто пишет, и такой защиты нет. Второе: без ключа повтор узнаётся только по точному тексту, поэтому пересказанная своими словами фраза становится второй записью, а предел типа вытесняет не дубли, а осмысленные записи. Взамен ушло второе поле, которое пользователю пришлось бы придумывать и помнить, чтобы правка не превращалась в дубль; увидеть и удалить лишнюю запись можно в шторке.

**Где что лежит.**

- **`Memory`** (`agent/src/main/kotlin/com/osvin/aichallenge/agent/Memory.kt`): `MemoryLayer` (три типа памяти: названия, пояснения, `writable` и значение на проводе), `MemoryRecord` (тип и текст), `MemoryReport` (что ушло в запрос по типам и чего это стоило), `MemoryRules` (пределы, слияние по тексту, `normalize`, `forget`).
- **`MemoryStore`** (`.../MemoryStore.kt`): `get`/`put`/`clear` по области хранения (`DEFAULT_PROFILE = "local"`) и `InMemoryMemoryStore`. Область у обоих слоёв теперь одна — профиль: различаются хранилища и срок жизни, а не адрес. Рабочая и долговременная память — два независимых хранилища, они не смешиваются даже в коде слияния.
- **`MemoryExtractor`** (`.../MemoryExtractor.kt`): служебный вызов «обнови память» — прежние записи **только тех типов, которые ведёт стратегия**, последние два сообщения и новый вопрос; ответ строгим JSON `{"memory":[{"layer":"long_term","value":"хранилище — Room"}]}`. В инструкции типы описаны словами задания, про краткосрочную сказано «не трогай — это сообщения диалога». Блоки в запросе собираются отдельно на каждый тип: «Рабочая память задачи (данные текущей задачи)» и «Долговременная память (профиль, решения, знания)». Негодный ответ — память остаётся прежней, диалог продолжается.
- **`LlmAgent`**: порядок сообщений — system prompt, сводка (если стратегия суммаризующая), долговременный блок, рабочий блок, история по стратегии, текущий вопрос. Пустой блок в запрос не добавляется. Обновление памяти живёт в `planContext` и вызывается, только если стратегия ведёт типы памяти; сессия ему не нужна — оба слоя читаются и пишутся по профилю; ответ раскладывается по типам `partition`-ом: тип не из задания или тип, которого стратегия не ведёт, — в `rejected`.
- **`ContextStrategy`**: `FULL` (∅), `SLIDING_WINDOW` (рабочая), `MEMORY` (рабочая + долговременная), `BRANCHES` (∅), `SUMMARY` (∅). Набор типов — свойство стратегии (`strategy.memory`), поэтому сравнение стратегий дня 10 остаётся в силе: память — это то, что даёт конкретная стратегия, а не фон для всех. `FACTS` дня 10 переименована в `MEMORY` (wire `"memory"`), старое значение `facts` читается как `MEMORY` — приложение дня 10 не переключается молча на сводку.
- **Отчёт** (`TokenReport`): вместо `facts*` — один блок `memory`: записи по типам, токены по типам, `short_term_messages`, `short_term_dropped`, `rejected`, `evicted`, `update_tokens`, `update_cost_usd`. В логе агента появился блок «Память агента» (для окна — строки о памяти внутри блока «Скользящее окно истории»).
- **Сервер**: `memory/JsonFileMemoryStore.kt` — долговременная память в файле с атомарной записью (временный файл + переименование), переживает перезапуск; испорченный файл означает пустую память, а не отказ сервера; путь переопределяется `-Dmemory.file` / `MEMORY_FILE`, по умолчанию `data/memory.json` от рабочего каталога процесса (то есть `server/data/memory.json`). `Application.kt` заводит оба хранилища и передаёт их агенту.
- **Явная запись** (`.../MemoryWriter.kt`): `layers()` — снимок обоих хранимых типов и каталог типов, `remember(layer, value)` — запись пользователя, `forget(layer, value)` — забывание по тексту. Явная запись проходит то же слияние и те же пределы, что и запись модели; в краткосрочную память писать нельзя (`writable = false`), а оба писаемых типа живут по профилю и видны из любого чата.

**Явное сохранение: шторка памяти и три маршрута.** Управление памятью вынесено из ленты сообщений в шторку (`ui/components/MemorySheet.kt`), которую открывает кнопка «Память» в верхней панели чата:

| Маршрут | Что делает | Ответ |
| --- | --- | --- |
| `GET /v1/memory` | снимок: оба хранимых типа целиком и каталог типов | `working`, `long_term`, `types` |
| `POST /v1/memory` `{layer, value}` | записать фразу в названный тип | тот же снимок |
| `DELETE /v1/memory?layer=…&value=…` | забыть запись с таким текстом | тот же снимок |

Шторка показывает три раздела в порядке каталога, подписанные его же словами: у каждой записи рабочей и долговременной памяти — «✕», в краткосрочном разделе записей нет, там строка отчёта последнего ответа («N сообщ. в запросе, не ушло M»), потому что краткосрочная память — это сообщения диалога. Форма записи — выбор типа чипами (краткосрочный чип недоступен с пояснением почему) и одно поле «Запись»: одна фраза, которую надо запомнить. Снимок полный, а не только то, что ушло в последний запрос, поэтому шторка работает при любой стратегии: править память можно и в чате, который её сейчас не читает.

Отказы приходят причиной в теле (400): тип не из задания, тип `short_term`, пустой текст. Удаление идемпотентно: забыть то, чего нет, — не ошибка, а вот неизвестный тип — ошибка, потому что шторка рисует выбор по каталогу. Ошибка записи не ломает диалог: текст отказа виден строкой в шторке, снимок остаётся на месте.

**Чтение памяти включает стратегия чата, и это её свойство.** Записи в шторке и то, что агент реально видит, — разные вещи: в запрос память отдаёт только стратегия (`ContextStrategy.memory`), а сама стратегия теперь хранится у чата (`Chat.strategy`, миграция БД 3→4). До этой правки стратегия жила в настройках генерации в памяти приложения, и там её ждали две ловушки: значение по умолчанию было «сжатие в сводку» (набор типов памяти у него пуст), а `openChat` выбранную при создании чата стратегию не восстанавливал. Значит, после перезапуска приложения или открытия соседнего чата любой чат читал как «сжатие»: записи лежали на сервере, шторка их показывала, но в модель они не уходили — ни в своём чате, ни в другом. Теперь чат хранит свою стратегию, у нового чата по умолчанию «память агента», стратегия переключается в самой шторке памяти (там же, где записи), а шторка предупреждает, когда записи есть, а текущая стратегия их не читает. Оба слоя общие по профилю, поэтому запись, сделанная в одном чате, видна и в другом — если тот чат читает память; различаются слои сроком жизни (рабочую обнуляет перезапуск сервера, долговременную нет), а не областью.

**Демонстрация** — `MemoryLayersDemoTest` (`./gradlew :agent:demoLogs`), четыре этапа на одной сцене сбора ТЗ (8 сообщений, окно 4, важные детали названы в начале: имя и роль пользователя, цель, бюджет 300 000 ₽, срок 6 недель, без регистрации, данные на устройстве, хранилище Room, графики на Compose):

1. **раскладка по типам** — что попало в рабочую и долговременную память, сколько это токенов, сколько сообщений не ушло в запрос и сколько стоил служебный вызов;
2. **влияние на ответ** — один вопрос «что ты обо мне знаешь и что мы решили по прошлому проекту?» в трёх конфигурациях: окно без долговременной памяти (новый чат), память агента в новом чате с наполненной долговременной памятью, память агента в том же чате (история + оба типа);
3. **какая запись в какой тип попала** — на подставленном ответе модели: две записи, названные её типами, и одна с типом, которого в задании нет;
4. **явная запись** — каталог типов, две записи пользователя (долговременная и рабочая), запись в краткосрочную память и запись с типом не из задания: печатается, куда что попало, отказ и результат забывания.

**Прогон без сети** (подставленные ответы, числа повторяемы): рабочая память — 5 записей / 76 токенов, долговременная — 5 / 60, блоки памяти в запросе — 136 токенов, служебные вызовы — 5 959 токенов за 9 ходов; окно пустило в запрос 4 сообщения (138 токенов), отброшено 12 (436 токенов), история без памяти — 574 токена. Сравнение конфигураций:

| Конфигурация | Сообщений в запросе | Вход, ток. | Рабочая | Долговрем. | Важных деталей в запросе |
| --- | --- | --- | --- | --- | --- |
| окно, пустые слои | 2 | 77 | 0 | 0 | 0 из 8 |
| память, новый чат | 4 | 219 | 5 | 5 | 8 из 8 |
| память, тот же чат | 8 | 372 | 5 | 5 | 8 из 8 |

На третьем этапе модель вернула четыре записи, у одной тип `настроение` — такого типа в задании нет, запись в память не попала, в отчёте `rejected = 1`.

**Живой прогон после перехода на типы памяти не повторялся.** Инструкция служебного вызова и форма записи изменились (виды записей и ключ → типы и одна фраза), поэтому числа прежнего живого прогона к текущему коду не относятся и здесь не приводятся. Непроверенным остаётся поведение настоящей модели на новой инструкции: как она делит фразы между рабочей и долговременной памятью и не дописывает ли лишнее. Наблюдение прежнего прогона, которое стоит перепроверить: модель добавляла в долговременную память решения, которых в диалоге не было, — от такой записи код не защищает, но её видно в шторке и можно удалить там же («✕»).

**Что показало сравнение** (подставленный прогон, числа повторяемы).

- **Рабочая память переезжает в новый чат, краткосрочная — нет.** Оба хранимых слоя живут по профилю, поэтому чат с пустой историей видит и данные задачи (5 записей), и профиль с решениями (5): в его запросе оказываются все 8 важных сведений сцены против нуля у окна. Не переезжает только то, что и есть краткосрочная память, — сообщения прошлого диалога (0 сообщений в запросе). Это и есть ответ на «какие данные попадают в каждый тип»: данные задачи и знания о пользователе доступны в любом чате, сама история — нет.
- **Слоям памяти история не нужна.** Второй строке таблицы хватает четырёх сообщений в запросе, чтобы до модели дошли все 8 важных деталей сцены: то же окно без слоёв памяти не доносит ни одной из них, потому что важное названо в начале диалога, а окно видит только его конец.
- **Рабочая память окупается на длинном диалоге.** При окне в 4 сообщения из 8 в модель уходит меньше половины сцены, а все 8 важных деталей остаются в запросе: 136 токенов блоков памяти вместо 574 токенов истории целиком.
- **Служебный вызов стоит отдельных денег.** 5 959 токенов за 9 ходов в подставленном прогоне — это по вызову на каждое сообщение пользователя, дороже самого входа в модель. Поэтому типы памяти включает стратегия: у `FULL`, `BRANCHES` и `SUMMARY` служебных вызовов нет вовсе. Для нового чата приложение выбирает «память агента» — иначе записанное в шторке не уходило бы в модель, — но стратегию можно сменить прямо в шторке памяти.

### task-12

День 12. Персонализация: профиль пользователя в каждом запросе

Профиль — это то, что пользователь **заявил** о себе, а не то, что модель вывела из переписки. Поэтому он не память: у него нет извлечения, слияния, пределов и отклонения типов, он не зависит от диалога и не меняется от чата к чату, а доходит до модели в **каждом** запросе — независимо от стратегии контекста. Требование дня: профиль пользователя (KMP-разработчик, стандартный стек), предпочтения по стилю и формату ответа и видимая проверка, что ассистент это учитывает сам, без напоминаний в вопросе.

**Результат:** профиль из шести полей (`role`, `stack`, `style`, `format`, `constraints`, `sign_off`) уходит в модель отдельным системным сообщением сразу после system prompt; он хранится на сервере и правится из приложения кнопкой «Профиль» в верхней панели; приложение персонализировано с первого запуска, потому что пустой стор отдаёт профиль KMP-разработчика; стоимость профиля видна в отчёте (`profile_tokens`) и в логе агента («профиль: 343 ток.»). Персональная настройка одна и она проверяемая: владелец просил заканчивать каждый ответ строкой «Ты молодец» — по ней видно, что профиль действительно дошёл до модели, а не остался настройкой интерфейса.

**Профиль владельца** (`UserProfile.DEFAULT`, он же профиль по умолчанию для того, кто своего ещё не задал):

| Поле | Текст |
| --- | --- |
| кто (`role`) | Kotlin Multiplatform разработчик: общий код на Android, iOS, desktop и wasm, сервер на JVM |
| стек (`stack`) | Kotlin, kotlinx.coroutines и Flow; Compose Multiplatform и Material 3; Ktor (клиент и сервер); kotlinx.serialization; Room и SQLDelight; Koin; Gradle Kotlin DSL с version catalog; kotlin.test и Turbine; Detekt и Ktlint |
| стиль (`style`) | сначала вывод, потом причина; без вступлений, без пересказа вопроса, без извинений; риск и сомнение называть прямо; если данных не хватает — сказать, каких именно |
| формат (`format`) | код на Kotlin полным куском: путь файла, сигнатуры, без пропусков «…»; шаги — нумерованным списком; сравнения — таблицей; по-русски, идентификаторы как в проекте |
| ограничения (`constraints`) | только Kotlin, без Java и RxJava; общий код в commonMain, платформенное — expect/actual; версии — из version catalog; новых зависимостей не добавлять без явной просьбы; не выдумывать незнакомые API — сказать «не проверял» |
| в конце ответа (`sign_off`) | подпись, если она нужна: в профиле по умолчанию поле пустое — концовку «Ты молодец» убрали в день 18 по просьбе владельца приложения, потому что она попадала в каждый ответ |

**Почему профиль не стал частью памяти.** Соблазн был: память дня 11 уже умеет хранить «профиль, решения, знания» в долговременном слое. Но слой наполняет модель и он живёт по правилам стратегии — в запрос его отдаёт только стратегия, ведущая этот тип. Предпочтения же задаёт человек, и они обязаны доходить до модели всегда.

| Свойство | Память (`MemoryLayer`) | Профиль (`UserProfile`) |
| --- | --- | --- |
| Кто наполняет | модель (служебный вызов) или человек в шторке | только человек, целиком |
| Правила | слияние по тексту, пределы 20/30 записей, отклонение чужих типов | никаких: что прислали, то и лежит |
| В запросе | если стратегия ведёт этот тип | всегда, при любой стратегии |
| Хранение | рабочая — в памяти процесса сервера, долговременная — в файле | файл `server/data/profile.json` |
| Изменчивость | записи приходят и уходят по ходу диалога | меняется только правкой человеком |

Область хранения у профиля та же, что у обоих слоёв памяти (`DEFAULT_PROFILE = "local"`), потому что пользователь в приложении один; сущность при этом другая — у профиля своё хранилище (`ProfileStore`), и `MemoryStore` о нём ничего не знает.

**Как профиль попадает в запрос.** Порядок сообщений в `LlmAgent`:

| Позиция | Сообщение | Условие |
| --- | --- | --- |
| 1 | system prompt | всегда |
| 2 | профиль пользователя | профиль не пуст — при любой стратегии |
| 3 | сводка предыдущего диалога | стратегия суммаризующая |
| 4–5 | долговременная и рабочая память | стратегия ведёт тип, слой не пуст |
| 6 | история по стратегии | сколько — решает стратегия |
| 7 | текущий вопрос | всегда |

Пустые поля в блок не печатаются, и пустой профиль сообщения не добавляет: строка «стиль: » без значения читается моделью как забытое требование, а не как отсутствие требования.

**Где что лежит.**

- **`UserProfile`** (`agent/src/main/kotlin/com/osvin/aichallenge/agent/UserProfile.kt`): модель профиля, `isEmpty`, `render()` (блок для промпта), `DEFAULT` — профиль KMP-разработчика. KDoc объясняет, почему профиль объявленный, а не извлечённый, и почему он не становится памятью.
- **`ProfileStore`** (`.../ProfileStore.kt`): `get`/`put` по идентификатору области и `InMemoryProfileStore`. Правка профиля — та же операция, что его создание, поэтому отдельного `clear` нет: профиль заменяют целиком.
- **`LlmAgent`**: `AgentOptions.profile`, системное сообщение профиля в сборке запроса и `profileTokens` в отчёте; **`TokenReport`**: `profile_tokens`.
- **Сервер**: `profile/JsonFileProfileStore.kt` — файл с атомарной записью (временный файл + переименование), переживает перезапуск; испорченный файл означает профиль по умолчанию, а не отказ сервера; путь переопределяется `-Dprofile.file` / `PROFILE_FILE`, по умолчанию `data/profile.json` от рабочего каталога процесса (то есть `server/data/profile.json`). `Application.kt` читает профиль **на каждый** `/v1/chat/completions` и кладёт его в `AgentOptions` — подставить профиль может только сервер, клиент его в запрос не добавляет, а `ChatRequest` не менялся.
- **Клиент**: `data/UserProfile.kt` (своя копия модели), `ChatRepository.profile`/`profileError`/`loadProfile()`/`saveProfile()`, `ChatViewModel` — обёртки в `viewModelScope`, `ui/components/ProfileSheet.kt` — форма из шести полей, `ChatTopBar` — кнопка «Профиль», `ChatScreen` — черновик одним объектом `UserProfile` в `rememberSaveable`. Своей копии текста профиля у клиента нет: умолчание приходит от сервера.

**Что показало сравнение.**

- **Профиль не зависит от стратегии.** Тот же блок профиля уходит в модель и при «всей истории», и при «ветках диалога»: 5 запросов из 5 по 343 токена. Стратегия решает, что уйдёт из истории и какая память, — профиль она не трогает, потому что он объявлен в настройках, а не выведен из диалога.
- **Память так не умеет.** Рабочую память берут только «скользящее окно» и «память агента», долговременную — только «память агента»; чтобы предпочтения работали, пользователю пришлось бы выбирать стратегию под них. Профиль снимает этот выбор: персонализация — не режим, а фон ответа.
- **Профиль — это отдельное сообщение, и он стоит отдельных токенов.** 343 токена из 9 сообщений запроса. Полный профиль владельца дороже короткого профиля второго пользователя в пять раз (343 против 70) — за подробность описания платят в каждом запросе, и это видно в отчёте, а не выясняется по счёту.
- **Разные профили — разные ответы на один вопрос.** На подставленном транспорте этого не видно (ответ один и тот же — он не зависит от профиля), поэтому различие формулировок доказывает только живой прогон: тот же вопрос дал план под KMP-стек и список без кода для продуктового менеджера.

### task-13

День 13. Состояние задачи как конечный автомат: этап → текущий шаг → ожидаемое действие

Задача ведётся не «в голове» модели, а в явном состоянии из трёх полей: **этап** (`planning` → `execution` → `validation` → `done`), **текущий шаг** и **ожидаемое действие**. Состояние живёт на сервере по сессии диалога, уходит в каждый запрос системным сообщением и виден в интерфейсе. Переход предлагает модель, а принимает код по таблице: без таблицы модель закрывает задачу, не проверив результат, — в следующем запросе она видит только переписку и решает, что работа сделана.

**Результат:** конечный автомат задачи с четырьмя этапами и таблицей переходов; задача заводится явным действием человека (как явная запись в память в дне 11) — до этого её не ведёт никто и служебных вызовов нет вовсе; пауза на любом этапе замораживает состояние (служебного вызова на паузе нет), продолжение идёт с того же шага; состояние видно в полосе над полем ввода вместе с кнопками «Взять в работу», «Пауза»/«Продолжить» и «✕».

| Этап (`TaskStage`) | Что на нём происходит | Куда можно дальше |
| --- | --- | --- |
| `planning` — планирование | что нужно сделать и в каком порядке | планирование, выполнение, готово |
| `execution` — выполнение | делаем шаг за шагом по плану | выполнение, проверка, планирование |
| `validation` — проверка | сверяем результат с задачей | проверка, выполнение, готово, планирование |
| `done` — готово | задача закрыта, следующая начинается заново | готово, планирование |

Запрещённый переход отклоняется с причиной, и работа продолжается с того же шага:

| Предложено моделью | Причина отказа | Этап остался |
| --- | --- | --- |
| планирование → проверка | из планирования нельзя в проверку: проверять пока нечего — сначала выполните план | планирование |
| выполнение → готово | из выполнения нельзя в готово: результат не проверен — перейдите в проверку | выполнение |
| готово → выполнение | из готово нельзя назад в выполнение: задача закрыта — начните новую с планирования | готово |

**Где состояние в запросе.** Порядок сообщений: system prompt → профиль → **состояние задачи** → сводка → слои памяти → история → текущий вопрос. Блок зависит от стратегии контекста так же мало, как профиль: он собирается до выбора того, что делать с историей. Печатается он так (пустые поля пропускаются):

```
Задача в работе (веди её по шагам, не начинай заново):
- этап: выполнение
- текущий шаг: шаг 2: итог
- ожидаемое действие: посчитать итог
- на паузе: задача остановлена — продолжай с этого же шага, выполненное не пересказывай
```

**Пауза — флаг, а не этап.** На паузе задача не движется, но остаётся ровно там, где её оставили: служебный вызов не делается вовсе (нечего обновлять — состояние заморожено), поэтому переход на паузе невозможен не «по договорённости с моделью», а по устройству. Ставит и снимает паузу человек: это решение о работе, а не шаг работы.

**Состояние живёт по сессии.** В отличие от памяти и профиля (они по профилю, все чаты видят одно), задача принадлежит диалогу: у каждого чата она своя, а `DELETE /v1/chats/{id}` её стирает вместе со сводкой. Хранится в памяти процесса — перезапуск сервера состояние теряет; клиент присылает всю историю диалога, поэтому после перезапуска работа продолжается с той же переписки, но этап и шаг начнутся заново. Это осознанный выбор: файл хранил бы курсор к истории, которой сервер не хранит.

| Маршрут | Что делает |
| --- | --- |
| `GET /v1/task?sessionId=…` | снимок: состояние диалога и каталог этапов (подписи и пояснения — только с сервера) |
| `POST /v1/task` `{sessionId}` | взять задачу в работу: этап «планирование», шаг и ожидаемое действие назовёт модель первым же сообщением; повторный вызов ничего не сбрасывает |
| `PUT /v1/task` `{sessionId, paused}` | пауза и продолжение; задачи нет — 400 с причиной |
| `DELETE /v1/task?sessionId=…` | забыть задачу (идемпотентно) |

### task-14

День 14. Инварианты и ограничения состояния: правила, которые ассистент нарушать не имеет права

Инварианты — то, что в проекте уже решено и не обсуждается заново: выбранная архитектура, принятые технические решения, ограничения стека, бизнес-правила. Хранятся они **отдельно от диалога** — своим хранилищем на сервере, как профиль и память, — потому что правило это не реплика в переписке, а условие над ней: блок правил уходит в каждый запрос системным сообщением при любой стратегии контекста, поэтому действует и в новом чате, где о нём никто не говорил, и его нельзя вытеснить сжатием истории.

**Результат:** правила проекта действуют с первого запуска; ассистент учитывает их в каждом ответе, а на конфликт отвечает **отказом с объяснением**, называя нарушенный инвариант и предлагая решение в его рамках.

| Вид (`InvariantKind`) | Что в него пишут | Правило проекта по умолчанию (`Invariant.DEFAULT`) |
| --- | --- | --- |
| `architecture` — архитектура | выбранная архитектура | один общий код на Kotlin Multiplatform в `commonMain` и тонкие платформенные адаптеры; сервер на Ktor, агент — отдельный модуль, сервер к нему только адаптер HTTP |
| `decision` — решение | принятые технические решения | состояние и правила (память, профиль, задача, сами инварианты) живут на сервере и уходят в модель системными сообщениями; клиент их не подставляет и в теле запроса не передаёт |
| `stack` — стек | ограничения по стеку | только Kotlin: без Java и RxJava; версии — из version catalog; новых зависимостей не добавлять без явной просьбы |
| `business` — бизнес-правило | правила предметной области | данные пользователя не уходят третьим лицам: наружу уходит только запрос к модели, долговременное состояние хранится на своём сервере |

**Как правило проверяется.** Два места, и оба видны в отчёте. Первое — блок правил в запросе (`InvariantRules.render`): `Инварианты проекта (нарушать нельзя, решение обязано им соответствовать):` и по строке на вид. Второе — служебный вызов `InvariantGuard` на каждый ход, пока правила объявлены: он получает правила, последние сообщения и вопрос и отвечает строгим JSON `{"verdict":"allowed"|"violated","violations":[{"kind":"stack","reason":"…"}]}`. По вердикту в запрос уходит ещё одно системное сообщение:

```
Проверка инвариантов: запрос нарушает — стек: только Kotlin: без Java и RxJava; версии — из version catalog;
новых зависимостей не добавлять без явной просьбы (просят код на Java, а проект только на Kotlin).
Не выполняй его: откажись, назови нарушенный инвариант и предложи решение, которое его не нарушает.
```

Отказ формулирует модель, но по причине, которую назвал код: вид нарушения и причина — от проверки, формулировка правила — из хранилища. На запрос в рамках правил приходит `Проверка инвариантов: запрос им не противоречит — предлагай решение в их рамках.` — то самое явное «учитываю в рассуждениях».

| Маршрут | Что делает |
| --- | --- |
| `GET /v1/invariants` | снимок: правила и каталог видов (подписи и пояснения — только с сервера) |
| `POST /v1/invariants` `{kind, value}` | объявить правило; отказ (вид, пустая или длинная формулировка, предел 20) — 400 с причиной |
| `DELETE /v1/invariants?kind=&value=` | убрать правило; убрали все — правил нет, и проверки в запросах тоже нет |

Набор проекта кладёт в хранилище **сервер при первом запуске** (`seedProjectInvariants`), а не агент: правило — условие, наложенное на работу, и назначать его себе агент не может. Поэтому агент с пустым хранилищем работает ровно так, как работал до дня 14 (ни блока, ни вызова), а прежние дни ничего не потеряли и не подорожали; «правил нет» при этом переживает перезапуск — подстановка бывает только однажды.

**Демонстрация** — `InvariantDemoTest` (`./gradlew :agent:demoLogs`), четыре этапа: правила вне диалога и в каждом запросе (блок 255 ток., с сообщением проверки 285 ток. на ход; в истории диалога правил нет — только реплики), три нарушающих запроса (Java и RxJava → стек, данные во внешний сервис → бизнес-правило, нативные модули → архитектура) с вердиктом, видом, причиной и правилом отказа, два запроса в рамках правил, живой прогон. Живьём на «перепиши агент на Java и RxJava» ассистент ответил: «Не сделаю этого — запрос прямо противоречит инварианту стека. **Нарушенный инвариант:** «стек: только Kotlin: без Java и RxJava…»» — и предложил `kotlinx.coroutines` + `Flow` вместо RxJava.

Сквозная проверка по HTTP: `GET` на первом запуске отдаёт четыре правила проекта; `POST` добавляет пятое; `DELETE` с чужим видом — 400 «вид инварианта неизвестен»; живой ход с нарушающим запросом — `verdict: violated`, `violated: ["stack"]`, блок и проверка 401 ток., служебный вызов 667 ток.; после удаления всех правил тот же запрос идёт без блока и без вызова (отчёт об инвариантах пуст), а перезапуск сервера пустой список сохраняет — набор проекта возвращается только вместе с файлом.

**Проверка.** `:agent:test` — 87 тестов (день 14 добавил демонстрацию, 4 теста), `:server:test` — 9, `:app:shared:testAndroidHostTest` — 19, APK собирается. Новых тестов сверх демонстрации день не писал.

Шторку инвариантов глазами не проверяли: приложение и эмулятор в этой задаче не запускались, проверка ограничена сборкой APK, host-тестами и сквозными `curl`-запросами. Проверка смотрит на **запрос** человека: ответ модели ограничен блоком правил и правилом отказа в промпте, а не отдельной проверкой текста ответа — отдельного «судьи над ответом» день не заводил.

### task-15

День 15. Контролируемые переходы состояний: ассистент не может перепрыгнуть этап

Задача живёт в четырёх состояниях, и переходы между ними разрешает код, а не модель: `TaskRules.allowed` — единственное место, где сказано, куда из какого этапа можно, и она же причина отказов. Из планирования нельзя сразу в проверку (проверять нечего), из выполнения нельзя в готово (результат не проверен), из готово нельзя назад в работу (задача закрыта). Тем самым «нельзя делать реализацию до утверждённого плана» и «нельзя финал без валидации» — не пожелание в промпте, а отказ с причиной.

**Результат:** ассистент с контролируемым жизненным циклом задачи — прыжок через этап отклоняется, состояние остаётся на месте, а ассистент объясняет отказ и продолжает работу с текущего шага.

| Из этапа | Можно | Почему так |
| --- | --- | --- |
| планирование | планирование, выполнение, готово | план уточняется; реализацию начинают после плана; задачу можно закрыть, не начиная |
| выполнение | выполнение, проверка, планирование | следующий шаг внутри этапа; результат сверяют до «готово»; неверный план пересобирают целиком |
| проверка | проверка, выполнение, готово, планирование | проверка идёт по частям; не прошла — назад в работу; сошлась — задачу закрывают |
| готово | готово, планирование | закрытая задача не продолжается: следующая начинается с плана |

**Переходы видны и человеку.** Таблица уезжает клиенту вместе со снимком задачи (`TaskSnapshot.transitions` — из этапа, куда и почему), и полоса задачи печатает по ней строку «дальше можно: проверка, планирование». Своей копии таблицы у клиента нет — как и у каталога этапов: список переходов и таблица, которой ограничен агент, не могут разойтись.

**Реакция ассистента.** Отказ мало зафиксировать — о нём надо сказать модели, иначе она видит только неизменившийся блок состояния и пробует перепрыгнуть снова. Поэтому причина отказа уходит в тот же запрос отдельным системным сообщением сразу после состояния задачи (`TaskState.renderRejection`):

```
Переход отклонён (этап остался прежним): из выполнения нельзя в готово: результат не проверен — перейдите в проверку.
Продолжай работу на этапе «выполнение», текущий шаг: шаг 1: разметка, ожидаемое действие: свёрстать список.
Этапы не перескакивают: переход станет возможен, когда работа дойдёт до него.
```

Причина берётся из таблицы, а не сочиняется в сообщении: отказ в логе, отказ в отчёте (`rejected`, `reject_reason`) и отказ в промпте говорят одно и то же.

**Демонстрация** — пятый этап `TaskStateDemoTest` (`./gradlew :agent:demoLogs`): таблица из 12 разрешённых переходов из снимка (и она же сверяется с `TaskRules.allowed` — таблица в демонстрации не переписана), задача стоит в выполнении, сцена просит «объявляй готово» → переход отклонён с причиной, состояние не сдвинулось, ассистенту ушло сообщение об отказе. Живьём на ту же просьбу ассистент ответил: «Готово объявить не могу: переход в „готово“ из „выполнения“ не пройдёт, пока результат не проверен. Этапы не перескакивают — сначала проверка.» — и продолжил текущий шаг. Этапы 2 и 3 той же демонстрации показывают три запрещённых перехода с причинами и паузу на каждом из четырёх этапов: на паузе вызовов нет, состояние заморожено, после снятия работа идёт с того же шага — то есть продолжение после паузы не сбивает ни этап, ни шаг.

**Проверка.** `:agent:test` — 87 тестов, `:server:test` — 9, `:app:shared:testAndroidHostTest` — 19, APK собирается: 115 проверок, падений нет. Новых тестов день не писал: проверки дня — пятый этап демонстрации и живой прогон.

Что осталось непроверенным: полоса задачи с строкой «дальше можно» на устройстве (эмулятор не запускался — проверка ограничена сборкой APK и host-тестами), а живьём проверен один прыжок — выполнение → готово; остальные отказы идут на подставленном предложении, потому что живая модель может и не предложить запрещённый переход.

### task-16

День 16. Подключение MCP: агент спрашивает у сервера, какие инструменты у него есть

До этого дня агент собирал данные проекта своим кодом и вкладывал их в запрос. MCP меняет способ: данные объявляются **инструментами**, и клиент спрашивает у сервера, что у него есть. День 16 — подключение: клиент запускает MCP-сервер процессом (транспорт stdio — так подключают большинство серверов в мире: у сервера не адрес, а команда запуска), проходит рукопожатие и получает список инструментов с описаниями и схемами аргументов.

**Результат:** код, который подключается к MCP и выводит список доступных инструментов — `./gradlew :mcp:mcpDemo`. Плюс та же информация от самого сервера, без подключения: `./gradlew :mcp:mcpTools` (процесс сервера с флагом `--list-tools` печатает свои инструменты и выходит).

Оба конца протокола (`kotlin-sdk-client` 0.15.0 и `kotlin-sdk-server` 0.15.0) ставятся в **отдельный модуль `:mcp`**: версия одна на оба конца, иначе в одном проекте оказались бы две реализации разбора кадров. SDK требует более новых общих библиотек, чем было в каталоге, поэтому `kotlinx-serialization-json` поднят 1.6.0 → 1.11.0, `kotlinx-coroutines-core` 1.7.3 → 1.11.0, добавлен `kotlinx-io-core` 0.9.1 (кадры stdio — потоки байтов); версии подняты в каталоге явно, а не «как разрешит Gradle», и проверены всеми четырьмя наборами тестов и сборкой APK.

**MCP — не часть агента и не часть серверного приложения.** Сначала клиент стоял в `:agent`, а сервер — в `:server`; и то и другое неверно. Агент — логика работы с моделью: он не должен меняться, когда меняется транспорт или версия MCP-клиента, поэтому про MCP он не знает вовсе, а зависимость направлена в обратную сторону (`:mcp` → `:agent`) — инструменты отдают данные проекта, типы которых описывает агент. Серверное приложение — HTTP-маршруты для приложения и человека; локальный MCP-сервер — отдельная точка входа со своим жизненным циклом (процесс, stdio, выход по концу входного потока), и в модуле приложения он значил бы, что модуль приложения отвечает за два разных сервера. Заодно файловые хранилища переехали из `:server` в `:agent`: это реализации контрактов, объявленных агентом (`InvariantStore`, `ProfileStore`, `MemoryStore`), и потребителей у них теперь двое — приложение и MCP-сервер; пакеты не изменились, поэтому приложение собирает их по-прежнему, а MCP-сервер читает те же файлы, что и приложение, и ответ инструмента не расходится с ответом маршрута.

**MCP не заменяет сервер приложения, и замены не было.** `:server` остался Ktor-приложением (`:server:run`, `Main-Class` `com.osvin.aichallenge.ApplicationKt`), MCP-сервер — вторая точка входа рядом, а `:mcp` от `:server` не зависит вовсе. Причина в потребителях: HTTP-маршруты нужны приложению и человеку — Compose-клиент читает и правит состояние, шторка профиля пишет предпочтения, и всё это с кодами ответа и контрактом, который держит код, а не языковая модель; MCP нужен агенту — это способ отдать модели список инструментов и вызвать их (процесс на stdio против слушающего порта, у каждого своя роль). Права тоже разные: MCP-сервер проекта только читает правила и профиль, а запись осталась маршрутам `POST`/`PUT`, потому что менять состояние — решение человека. Подключиться к MCP-серверу можно и сторонним клиентом: `./gradlew :mcp:jar && java -cp mcp/build/libs/mcp-1.0.0.jar com.osvin.aichallenge.mcp.ProjectMcpServerKt` (запускать из каталога, рядом с которым лежит `data/`, либо указать путь переменной `INVARIANT_FILE`).

Подключаться есть к кому: сервер проекта сам стал MCP-сервером (`mcp/.../ProjectMcpServer.kt`) и отдаёт по протоколу свои же данные — только на чтение, из тех же хранилищ, что сервер приложения.

**Сервер можно запустить службой и остановить** — `mcp/mcp-server.sh` (`start`, `stop`, `restart`, `status`, `tools`, `logs`, `frames`). Это нужно потому, что stdio-сервер живёт ровно столько, сколько живёт клиент, и посмотреть на работающий сервер иначе нельзя: скрипт поднимает его фоном, держит открытым канал ввода (именованный канал, FIFO), пишет кадры протокола и логи в файлы, а `status` проверяет не процесс, а ответ на `tools/list` по протоколу. Сторонний клиент к такому процессу не подключается — клиенты MCP поднимают сервер сами; служба нужна человеку: увидеть сервер, проверить его и положить кадр в протокол руками.

```
$ ./mcp/mcp-server.sh start

  данные:      …/server/data
  логи:        mcp/build/mcp-server/server.log
  кадры:       mcp/build/mcp-server/frames.log
$ ./mcp/mcp-server.sh status

сервер отвечает: кадров получено на 1077 байт
$ ./mcp/mcp-server.sh stop
сервер остановлен: pid 54723
```

**«Что у тебя есть» — это команда, а не печать во время работы.** В рабочем режиме стандартный вывод сервера занят протоколом, и список инструментов, напечатанный туда, ушёл бы клиенту мусором вместо кадра. Поэтому список печатает отдельный режим — флаг `--list-tools`: сервер поднимается, отвечает на вопрос о своих инструментах и выходит, не открывая ни транспорта, ни хранилищ (печатать список можно и без данных):

```
$ ./gradlew :mcp:mcpTools

инструментов: 2; список объявлен кодом, поэтому изменения не рассылаются (listChanged = false)

1. list_invariants
   Правила проекта (инварианты), которые ассистент не имеет права нарушать: вид правила и его формулировка.
   аргументы:
     profile_id: string, необязательный — чей набор читать; без него — данные профиля по умолчанию

2. user_profile
   Профиль пользователя: объявленные им предпочтения — кто он, на чём пишет и каким хочет видеть ответ.
   аргументы:
     profile_id: string, необязательный — чей набор читать; без него — данные профиля по умолчанию
```

То же самое без Gradle — из fat JAR (так эту команду и вызывает сторонний клиент, которому нужен запуск сервера): `./gradlew :mcp:fatJar && java -cp mcp/build/libs/mcp-1.0.0-all.jar com.osvin.aichallenge.mcp.ProjectMcpServerKt --list-tools`. Без аргументов тот же jar работает сервером на stdio; неизвестный аргумент — отказ с кодом 2, чтобы опечатка не превратилась в молча поднятый сервер. Список берётся из той же спецификации (`ProjectMcpServer.tools`), по которой сервер регистрирует инструменты, поэтому показать одно, а объявить другое он не может. Fat JAR собирается отдельной задачей, а обычный jar модуля остаётся тонким: тонкий jar — это артефакт, который получают зависящие от `:mcp` модули, и вложенные в fat JAR классы ломали бы их сборку (подробнее — `### task-17`).

| Инструмент | Что отдаёт | Аргумент |
| --- | --- | --- |
| `list_invariants` | правила проекта (инварианты): вид правила и формулировка | `profile_id` — чей набор; необязательный |
| `user_profile` | профиль пользователя: объявленные предпочтения | `profile_id`; необязательный |

**Соединение — это рукопожатие, а не «процесс запустился».** Клиент ждёт `initialize` → `initialized` с ограничением по времени (молчащий сервер не должен вешать вызывающего), и только потом спрашивает инструменты. Процессом владеет тот, кто его поднял: закрытие сессии закрывает транспорт, потом процесс, а если сервер не вышел сам — силой; неудачное рукопожатие гасит процесс там же, чтобы не осталось сироты. Поток ошибок сервера идёт вызывающему построчно, потому что его поток вывода занят протоколом. Список инструментов спрашивается каждый раз и не кэшируется: живой сервер может его менять. Конец входного потока — конец работы сервера: транспорт при естественной остановке закрывает вход и выход сам, поэтому `main` только ждёт её и `Server.close()` после неё не зовёт — служба уведомлений SDK в этом состоянии завершается через раз (уведомление о конце уходит в поток без буфера и висит, если подписчик занят отправкой в уже остановленный транспорт), и с закрытием процесс висел в трёх прогонах из пяти, а без него выходит каждый раз. Схему разбирает клиент — имена, типы и обязательность аргументов объявляет сервер, своих мы не придумываем.

**Стандартный вывод — это протокол, и он отдан протоколу целиком.** Первый прогон упал именно на этом: `kotlin-logging` печатает приветствие в stdout, клиент разобрал его как сообщение протокола (`Failed to deserialize message from line: kotlin-logging: initializing…`) и потерял бы ответ. Поэтому сервер не «старается не печатать» в stdout, а забирает его: прежний `System.out` уходит транспорту, а `System.out` процесса перенаправляется в поток ошибок — печатать в канал протокола больше не может никто, а логи сервера идут в stderr (`warn` для чужого, `info` для своего).

**Демонстрация** — `McpDemoTest` (`./gradlew :mcp:mcpDemo`): клиент поднимает сервер проекта процессом, проходит рукопожатие, печатает список инструментов, вызывает один из них и закрывает сессию.

Ожидаемый список демонстрация берёт из `ProjectMcpServer.tools` — той же спецификации, по которой сервер регистрирует инструменты: копии «как должно быть у клиента» рядом с настоящей спецификацией нет. Вызов инструмента добавлен, чтобы список не остался декларацией, и сервер при этом запускается с `INVARIANT_FILE` на временный файл с двумя правилами, которых в умолчаниях проекта нет: ответ разбирается в правила проекта теми же типами, что и у сервера, и сверяется с этим файлом целиком. Пришли `echo` и `sum`, обязательные аргументы прочитались как `text: string (required)`, `a: number (required)`, `b: number (required)` — клиент говорит по протоколу, а не только со своим SDK. ### task-17

День 17. MCP-сервер для GitHub и вызов инструмента самим агентом

День 16 подключил агента к MCP и показал список инструментов — но вызывал их код демонстрации, а не модель. День 17 доводит это до работы: появляется второй MCP-сервер, который ходит в GitHub REST API, и **агент сам** выбирает инструмент по обычной просьбе («покажи мои приватные репозитории»), получает данные и отвечает по ним.

**Результат:** живой прогон `./gradlew :server:githubDemo -Pdemo.live=1` — три просьбы (все репозитории, публичные, приватные) и одна проверка отказа. Модель живая, сервер инструментов — настоящий отдельный процесс по протоколу MCP, GitHub подставной: токена в окружении нет, адрес API подставляется переменной `GITHUB_API_BASE`, а код-путь тот же, что с настоящим GitHub.

**Вторая часть дня доводит это до интерфейса:** соединение ставит человек кнопкой «GitHub» в шапке чата, шторка показывает подключённый сервер, его инструменты и их аргументы, а команда вызова печатается в ленте карточкой — и когда инструмент вызвал человек, и когда его выбрала модель. Экран проверен живьём на эмуляторе (подключение, вызов, отключение, перезапуск), маршруты — на поднятом `:server:run` с подставным GitHub.

**Третья часть дня убирает из этого интерфейса поле токена:** доступ ищется готовым на машине (переменная окружения, файл, связка ключей, `gh`, учётные данные git), авторизация целиком живёт внутри MCP-сервера, а шторка показывает состояние доступа — кто вошёл, с какими правами и откуда взят токен — и кнопку «Проверить снова». Токен не проходит ни через клиент, ни через тело запроса, ни через состояние экрана: наружу отдаётся только логин, права и источник.

**Сервер GitHub — отдельный модуль `:mcp-github`**, но не копия сервера проекта. У сервера проекта данные — правила и профиль, у GitHub — сеть и доступ к аккаунту, которого у первого нет вовсе; в одном модуле они получили бы один fat JAR и одну точку входа с чужими настройками. Общая часть при этом вынесена в `:mcp` (`DeclaredTool.kt`, `StdioServer.kt`): объявление инструмента, его схема, регистрация и режимы запуска stdio — одни на оба сервера. Объявление одно и на регистрацию, и на консольный список, и на схему для клиента, поэтому «показал одно, объявил другое» невозможно по построению.

Решения вокруг сервера:

- **Доступ ищется в момент вызова, а не при старте.** Сервер поднимают и для `--list-tools`, где GitHub не нужен; падать из-за отсутствия доступа на старте значило бы запрещать знакомство с инструментом до настройки. Нет доступа — инструмент отвечает отказом с причиной, и модель говорит об этом человеку.
- **Доступ берётся готовым с машины, цепочкой источников.** Порядок: `GITHUB_TOKEN` → файл из `GITHUB_TOKEN_FILE` → связка ключей macOS → `~/.config/ai-challenge/github.token` → `gh auth token` → `git credential fill`; побеждает первый найденный. Человек не набирает секрет руками, а тот, у кого доступ уже есть (`gh`, связка ключей), не заводит второй токен. Учётные данные git читаются последними: они принадлежат другому инструменту, и брать их без нужды невежливо.
- **Кэшируется только успех.** Найденный токен запоминается вместе с источником, а «доступа нет» — нет: иначе положенный после подключения токен не подхватился бы без перезапуска сервера. Отсюда кнопка «Проверить снова» в шторке.
- **Файл с правами 644 отвергается** с подсказкой `chmod 600`: запись, читаемая любым пользователем машины, — это не доступ, а утечка. Внешние команды запускаются с таймаутом и с запретом диалогов: `git credential fill` без учётных данных иначе ждал бы ввода в терминале, а связка ключей — открыла бы окно.
- **Инструмент `github_access` не отказывает никогда.** Отсутствие доступа — состояние, о котором и спрашивали, а не ошибка инструмента: причина уходит в подсказку, и модель тоже видит, чего не хватает. Логин и права берутся из `GET /user` (`X-OAuth-Scopes`); `scopesReported=false` честно говорит, что токен прав не сообщает — так ведут себя fine-grained-токены. Токена нет ни в одном поле отчёта: только источник.
- **Адрес API — параметр** (`GITHUB_API_BASE`, по умолчанию `https://api.github.com`). Это не «гибкость на будущее»: токена GitHub в окружении этого проекта нет, и проверка идёт на подставном API на localhost; без параметра её негде было бы провести.
- **Модель отделена от ответа GitHub.** Публичный `GitHubRepository` — с именами полей из задания (`fullName`, `url`), внутренний `GitHubRepositoryResponse` разбирает ответ GitHub (`full_name`, `html_url`). Аннотации `@SerialName` на самой модели заставили бы её собственный JSON-вывод уехать с именами GitHub — одна аннотация обслуживала бы два разных формата.
- **Видимость берётся из `visibility`, а если поля нет — из `private`** (так GitHub отвечает не всегда). Фильтровать по флагу `private` в обход видимости не стали: тогда третья видимость GitHub (`internal`) попала бы в «приватные», хотя инструмент обещает только публичные и приватные.
- **Пагинация по `Link: rel="next"` с пределом в 10 страниц.** Предел защищает от замкнутой ссылки: без него сервер ходил бы в GitHub вечно, а пользователь не дождался бы ответа.
- **Ошибка GitHub — результат вызова, а не исключение.** 401, 403, прочие не-2xx, сеть, отсутствие токена и неизвестное значение `visibility` (проверяется **до** обращения к API) — всё это `isError` с причиной словами. Исключение ушло бы клиенту отказом инструмента, которого он не вызывал, и до модели не дошло бы вовсе.

**Вызовы инструментов делает агент, а не код вокруг него.** Контракт в `:agent` нейтрален: имя, описание, схема аргументов и функция вызова (`AgentTool`). Ни MCP, ни процессов, ни сессий агент не знает — адаптер `McpSession.agentTools()` живёт в `:mcp`, где видны обе стороны. Цикл в `LlmAgent.run` прост по форме и строг по завершению: объявления уходят в запрос только когда инструменты есть; модель просит вызовы → агент выполняет их и добавляет в переписку сообщение ассистента с вызовами и **ответ на каждый вызов** (`role = "tool"`, `tool_call_id`) → повторяет запрос; когда вызовов нет, приходит текст.

Почему именно так:

- **Раундов конечное число** (`MAX_TOOL_ROUNDS = 3`), после них инструменты не предлагаются. Модель может просить инструмент бесконечно («позови ещё раз, вдруг получится»), и без предела запрос кончился бы не ответом, а расходом. Три, а не один: цель раунда может зависеть от результата предыдущего. Если вызов приходит уже без объявлений, он не выполняется, а работа кончается ответом модели — цикл не зависит от чужого поведения.
- **Неизвестный и упавший инструмент — ответ модели, а не отказ запроса.** Причина уходит в переписку, и модель отвечает без данных. Так падение внешнего сервиса не отменяет ответ на вопрос, который от него не зависел.
- **Аргументы разбираются мягко:** пустая строка — «аргументов нет» (у инструмента есть умолчания), а неразобранная — отказ с причиной. Молча звать инструмент с пустыми аргументами значило бы отдать модели выдумку вместо данных.
- **Переполнение окна проверяется перед каждым раундом**, а расход суммируется по раундам: каждый вызов — это ещё один полный запрос со всей перепиской, и без суммы отчёт показывал бы расход меньше настоящего.

Два нюанса формата пришлось предусмотреть отдельно. У ответа с вызовами `content` приходит `null` — разбор падал бы ровно там, где начинается вызов: поле получило умолчание, а клиентский разбор `coerceInputValues = true`. Поле `type` в объявлении и в вызове помечено `EncodeDefault`: оно совпадает с умолчанием, но провайдер ждёт его всегда, и пропуск — отказ, а не экономия байтов.

**Сервер приложения держит одну долгую сессию инструментов** (`server/.../GitHubTools.kt`): MCP-сервер — отдельный процесс на JVM, и поднимать его на каждый вопрос значило бы платить за запуск и рукопожатие в каждом ответе. Под замком — потому что запросы идут параллельно: без него два одновременных вопроса подняли бы два процесса, и один остался бы сиротой. Недоступный сервер инструментов **не отменяет ответ**: причина уходит в лог, вопрос идёт модели без инструментов, попытка повторяется на следующем запросе. Обратное решение превращало бы недоступность GitHub в недоступность ассистента. Сессия закрывается на `ApplicationStopped`: процесс подняли мы, иначе он пережил бы остановку приложения. Доступ сервер приложения не читает вовсе — он спрашивает состояние у MCP-сервера тем же вызовом инструмента (`github_access`) и потому не может вынести секрет ни в лог, ни в ответ. Отчёт об инструментах возвращается в ответе маршрута (`tokens.tools`) и печатается в клиентском логе рядом со строками про память, задачу и инварианты.

**Fat JAR — не артефакт модуля.** Первая сборка `:mcp-github` упала: `:mcp` собирал fat JAR задачей `jar`, а она и есть основной артефакт модуля, поэтому зависимые модули компилировались против него. Внутри fat JAR лежат классы зависимостей, и компилятор Kotlin, определяя версию `kotlinx-serialization` по классу `Serializable` из первой записи classpath, читал её из манифеста этого jar (1.0.0 — версия проекта) и отказывался собирать: «текущая версия ядра 1.0.0, а плагину нужно не меньше 1.3.0». Классификатор на основном `jar` не помог бы: `jar` остаётся артефактом модуля даже с классификатором. Поэтому в обоих модулях обычный `jar` остался тонким, а выполнимый fat JAR собирает отдельная задача `fatJar` (`:mcp:fatJar`, `:mcp-github:fatJar`).

**Стандартный вывод — это протокол, и забирать его надо раньше, чем что-либо напечатает.** Второй живой прогон показал это ещё раз: сервер печатал в stdout «kotlin-logging: initializing…» и «Adding Tool: …» до того, как вывод был отдан транспорту, — сборка сервера (регистрация инструментов, первые обращения к логгерам SDK) шла раньше захвата вывода. Клиент разбирал эти строки как кадры («Failed to deserialize message from line: … Adding Tool …») и мог потерять ответ. Теперь вывод забирается под протокол **до** сборки сервера, а не после: печатать в канал протокола не может никто, логи сервера идут в поток ошибок.

**Демонстрация** — `GitHubToolsDemoTest` (`./gradlew :server:githubDemo -Pdemo.live=1`). Инструмент на каждом этапе обёрнут записью ответа, поэтому проверяется не красноречие модели, а то, какие данные она получила: вызван ровно тот инструмент и хотя бы один раз, расход инструментов не нулевой, в публичные не попал приватный репозиторий и наоборот, все обращения к GitHub ушли с `Bearer`-токеном, а отсутствие доступа доходит до модели словами и не пустой строкой. Тем же прогоном видно и то, что сервер печатает свои логи в поток ошибок: строка `[agent] github: kotlin-logging: …` — это его stderr, подхваченный клиентом, а не мусор в канале протокола (иначе он приехал бы испорченным кадром).

Демонстрация не смотрит на это глазами: она утверждает, что вызван ровно тот инструмент и хотя бы один раз, что расход инструментов не нулевой, что в публичные не попал приватный репозиторий и наоборот, что все обращения к GitHub ушли с `Bearer`-токеном, а отказ без токена имеет `isError` и не пустой ответ модели.

**Служба теперь обслуживает оба сервера:** `mcp/mcp-server.sh start --server github` — тот же запуск, `status` (проверка по протоколу), `tools`, `logs`, `frames`, `stop`. Механика у серверов одна, поэтому второй сервер не отдельный скрипт, а выбор модуля, точки входа и каталога состояния; `--data-dir` у GitHub-сервера отклоняется: своих файлов данных у него нет, и делать вид, что опция что-то меняет, было бы хуже отказа.

**Соединение с GitHub ставит человек кнопкой, а не первый запрос к модели.** Кнопка «GitHub» в шапке чата (рядом с «Память», «Инварианты», «Профиль») открывает шторку: состояние доступа и соединения, список инструментов с их аргументами (значения выбираются из объявленных) и кнопку вызова. Поля токена в шторке нет: доступ ищет сам MCP-сервер, а шторка показывает, кто вошёл, с какими правами и откуда взят токен. Ленивое подключение убрано нарочно: при нём «GitHub подключён» — скрытое следствие того, что кто-то однажды спросил модель, и человек не отличает «инструментов нет» от «ещё не подключались»; заодно чужой процесс больше не поднимается за спиной у человека. Плата — подключение перестало быть бесплатным для того, кто забыл нажать кнопку, поэтому на вызов без соединения приходит 409 с прямым указанием, что делать.

Контракт — четыре маршрута вокруг одного соединения: `GET /v1/github` (снимок), `POST /v1/github/connect` (200 с подключением, 502 — «не удалось подключиться»; тела не читает — доступ ищет MCP-сервер), `POST /v1/github/disconnect` (тела не требует и не читает), `POST /v1/github/call` (200 с ответом инструмента, 404 — нет такого имени, 409 — нет соединения). Коды различают три разных положения дел: отказ инструмента — это 200 с `failed=true`, потому что вызов состоялся и инструмент словами сказал, почему данных нет; один код на все три случая заставил бы интерфейс разбирать текст причины, чтобы понять, показывать ли кнопку «Подключить». Подключение возвращает не исключение, а `GitHubConnect.Connected`/`Rejected`: причину показывает шторка, и падать из-за неё запрос не должен. Тесты маршрутов идут на настоящем MCP-процессе и подставном GitHub (`GitHubRoutesTest`), а `module(githubTools)` — параметр, а не глобальное состояние: маршрут чата и шторка получают одни и те же инструменты.

**Команда инструмента печатается в чате карточкой** — и когда её вызвал человек из шторки, и когда её вызвала модель сама. Карточка одна на оба случая (`ToolCallCard`): моноширинная строка команды (`get_repositories {"visibility": "private"}`), ответ инструмента и пометка отказа. Поэтому отчёт о вызове (`ToolCallRecord`) получил `arguments` и `result` — до этого текст вызова жил только в логе сервера, и лента не смогла бы напечатать команду. `result` обрезается тем же `forLog()` (2 000 символов), что и лог: одна политика на лог и ленту, а модели уходит ответ целиком. Ответ инструмента приходит ролью `TOOL` с пустым текстом, и вместо пузыря на его месте печатается та же карточка; из истории, уезжающей модели, записи `TOOL` отсеиваются — иначе служебная строка читалась бы как реплика, которой не было, и модель отвечала бы на собственный отчёт о вызове. Вызовы хранятся вместе с сообщением (колонка `toolCalls`, миграция Room 4 → 5): вызов относится к конкретному ответу, и после перезапуска приложения видно, откуда взялись данные.

Токен вообще не проходит через интерфейс: доступ ищется готовым на машине, а кнопка «Проверить снова» повторяет поиск — это и есть способ подхватить токен, положенный уже после подключения, без перезапуска сервера и приложения. Положить токен можно в одно из четырёх мест: `export GITHUB_TOKEN=<токен>` (переменная окружения), файл `~/.config/ai-challenge/github.token` с правами `600` (открытые права сервер отвергает), связка ключей macOS (`security add-generic-password -a "$USER" -s ai-challenge-github -w`) или готовый вход через `gh auth login`; путь к файлу можно задать переменной `GITHUB_TOKEN_FILE`. В коде, логах и ответах токена нет ни в одном виде: наружу уходят только логин, права и источник («файл ~/.config/ai-challenge/github.token»).

**Проверка.** `:agent:test` — 102 теста, `:mcp:test` — 7 (+2: описание и допустимые значения аргумента в объявлении), `:mcp-github:test` — 60 (+40: цепочка готовых доступов, инструмент `github_access`, `GET /user` с правами, разбор не-2xx), `:server:test` — 11 (+3: `GitHubRoutesTest` — маршруты на настоящем MCP-процессе и подставном GitHub, `connect` без тела и без токена в ответе), `:app:shared:testAndroidHostTest` — 27 (+8: `GitHubToolsClientTest` — подключение без тела, состояния доступа, ручной вызов, вызов инструмента без аргументов, отсев `TOOL` из истории, вызовы модели у ответа, обновление снимка), APK собирается: 213 проверок по XML (в шести файлах демонстрационных тестов XML дублируется), падений нет. Живые прогоны: демонстрация `:server:githubDemo` (четыре запроса к модели), `:mcp:mcpDemo`, `:mcp:mcpTools`, `:mcp-github:mcpTools`, маршруты поднятого `:server:run`, поиск доступа (нет доступа — подсказка из четырёх способов; файл с правами 600 — доступ, с 644 — отказ; `GITHUB_TOKEN` — доступ; отозванный токен — 401) и экран на эмуляторе.

**Маршруты** проверены на поднятом `:server:run` с подставным GitHub на 8787: подключение без тела отвечает снимком с доступом, вызов инструмента возвращает его результат, незнакомое имя инструмента — 404, вызов без соединения — 409, а отказ инструмента приходит ответом с `failed = true`, а не отказом маршрута. Тесты маршрутов идут на настоящем MCP-процессе и подставном GitHub (`GitHubRoutesTest`), поэтому транскрипт одного запуска здесь ничего не добавил бы: проверяется свойство кода, а не кадр прогона.

**Экран** проверен на запущенном эмуляторе (`emulator-5554`), а не в браузере: `app/shared` под JS и wasm не собирается (`Unresolved reference 'System'` — ограничение, записанное ещё в `docs/task-16-mcp.md`). APK поставлен поверх базы прошлых дней, и это заодно проверка миграции: восемь старых чатов открылись, то есть `MIGRATION_4_5` прошла без потерь. Что подтвердилось по шагам: кнопка «GitHub» открывает шторку; без доступа шторка говорит «Доступ к GitHub не найден», показывает подсказку и кнопку «Проверить снова»; когда доступ появился — «Доступен как ⟨логин⟩ · права: …» и источник; у инструмента с объявленными значениями аргумент выбирается вариантами (`all` / `public` / `private`), а у состояния доступа аргументов нет вовсе и остаётся одна кнопка; вызов кладёт в ленту карточку с командой и результатом; «Отключить» разрывает соединение; после `force-stop` чат, сообщения и карточки вызовов на месте.

Что осталось непроверенным: настоящий `https://api.github.com` не вызывался ни разу (в окружении этого проекта токена нет, `gh` не установлен), поэтому живые лимиты, 403 с `X-RateLimit-*` и пагинация на настоящем `Link` не проверены — проверено тем же кодом на подставном API; из цепочки источников живьём проверены переменная окружения и файл с правами 600/644, а связка ключей macOS, `gh auth token` и `git credential fill` — только подделками в тестах (ни записи в связке, ни `gh`, ни сохранённых учётных данных git на этой машине нет); на физическом устройстве и на iOS приложение не запускалось (экран проверен на эмуляторе); JS- и wasm-таргеты `app/shared` не собираются, поэтому браузер как способ проверки интерфейса недоступен; выбор моделью между несколькими инструментами (сервер проекта и сервер GitHub одновременно) не проверялся: сегодня сервер подключает только инструменты GitHub. Живые демонстрации гейтятся флагами `-Pdemo.live=1`/`-Ddemo.live=1` и `DEEPSEEK_API_KEY`; снимки экрана сняты `adb screencap` и в репозиторий не добавлены.

### task-18

День 18. Сервис мониторинга курсов валют, MCP и ответ агента по накопленной истории

День 17 показал, что агент умеет звать чужие инструменты. День 18 даёт ему то, чего у него
не было, — **свои данные во времени**: сервис раз в минуту забирает EUR/RUB, USD/RUB и GEL/RUB
у внешнего источника, складывает историю в SQLite, отдаёт её тремя MCP-инструментами
(`get_currency_rates`, `get_currency_summary`, `get_currency_change`) и живёт на сервере обычным
`java -jar`. Вторая часть того же задания — **закреплённый чат** в приложении: лента курсов
без ввода и без модели, строка на минуту, а при открытии — изменение за сутки, собранное
из сохранённых часовых сводок.

**Источник — ЦБ РФ** (`https://www.cbr-xml-daily.ru/daily_json.js`, по умолчанию): отдаёт
курсы к рублю файлом, без ключа и без регистрации. Проверено живьём — Frankfurter для рубля
JSON не отдаёт, `open.er-api.com` считает обратные курсы, поэтому выбор один. ЦБ называет курс
за `Nominal` единиц (для евро, доллара и лари — за одну), и номинал учитывается в разборе.

**Модуль `:currency-monitor` — третий сервер MCP**, а не папка внутри `:mcp-github`: у сервиса
курсов своё время жизни (служба на VPS между подключениями клиентов) и своя команда запуска,
тогда как сервер GitHub бесполезен без аккаунта. Общая часть — объявления инструментов
и stdio-цикл — берётся из `:mcp`, как и раньше: объявление одно на регистрацию, консольный
список и схему для клиента, поэтому «показал одно, объявил другое» невозможно по построению.
Пакеты внутри модуля повторяют слои задания: `remote/` (источник), `storage/` (история),
`scheduler/` (расписание), `summary/` (агрегация), `mcp/` (инструменты).

Решения вокруг данных:

- **Курс — только `BigDecimal`, и в SQLite он лежит текстом.** `REAL` вернул бы 95.8709 уже
  другим числом, а курс — деньги; текст хранит ровно то, что пришло. Масштаб — 6 знаков,
  поэтому значения в базе одной длины.
- **Момент получения — ISO-8601 UTC с секундной точностью.** Иначе текстовый порядок строк
  перестал бы совпадать с хронологическим (`…32.9Z` сортировалось бы после `…32.10Z`).
  И это именно момент, когда сервис узнал курс, а не дата публикации ЦБ: история отвечает
  на первый вопрос.
- **Строка на каждое обновление, без дедупликации** — так требует задание. Плата: при дневном
  курсе ЦБ в истории стоят одинаковые значения за соседние часы, и «за сутки данных нет»
  остаётся отличимым от «за сутки курс не менялся».
- **Одно обновление — одна транзакция**: три курса одного обхода попадают в базу вместе или
  не попадают вовсе, иначе половина обновления выглядела бы записью из другой даты.
- **«Предыдущий» курс берётся из истории целиком, а не из окна сводки** — иначе у службы,
  работающей вторые сутки, изменение за сутки всегда было бы неизвестным.
- **Неопределённое — `null`, а не ноль**: нет истории — нет чисел, нет предыдущего курса — нет
  изменения. Ноль на месте неизвестного читался бы как «курс равен нулю». Отказ хранилища
  не глотается: недоступную историю нельзя выдавать за «период без данных».

**Агрегация** (`CurrencySummaryService`) считается по окну `[сейчас − период, сейчас]`, обе
границы входят в него: `DAY` — 24 часа, `WEEK` — 7 суток, `MONTH` — 30 суток; масштаб ответа
4 знака. `get_currency_summary` объявляет `period` **обязательным** и с перечислением значений:
умалчивание читалось бы как «за сутки» там, где человек имел в виду месяц, а свободная строка
дала бы модели возможность выдумать `MONTHLY`. `get_currency_rates` аргументов не имеет
и при пустой истории отвечает не отказом, а подсказкой, что данных ещё нет.

**Планировщик** делает первое обновление сразу, а дальше — пауза после конца предыдущего:
ждать час до первой записи значило бы, что инструмент всё это время отвечает «история пуста».
Цикл переживает сбой хранилища и разбора (иначе молча прекратил бы сбор), но пробрасывает
отмену, а ожидание идёт на `delay` — `Thread.sleep` не заметил бы `cancel()` до конца паузы.
**Сбор не зависит от клиента**: он идёт по расписанию, а не по вызову инструмента. Интервал —
настройка (`CURRENCY_INTERVAL`), по умолчанию минута: её требует лента закреплённого чата,
а дневному курсу ЦБ в unit-файле для VPS оставлена подсказка про `PT1H` — минутный сбор стоит
до 1440 обращений в сутки ради ряда, который у бесплатного источника почти не меняется.
После каждого состоявшегося обновления планировщик **закрывает прошедший час часовой сводкой**
в ту же базу (`currency_hourly_summaries`, ключ «час + валюта», `INSERT OR REPLACE`): суточная
картина должна быть полной независимо от того, было ли приложение открыто, поэтому считает её
служба, а не клиент по своей ленте.

**Один процесс на всё, четыре режима** (`Application.kt`): без аргументов — служба (сбор,
протокол, жизнь после конца ввода: на VPS клиента может не быть вовсе); `--mcp` — процесс
для клиента, который выходит вместе с ним (так его поднимает сервер приложения, локально
и по ssh); `--once` — одно обновление и код возврата для скриптов; `--list-tools` — объявления
и выход, без базы и сети. Настройки приходят только из окружения (`CURRENCY_API_BASE`,
`CURRENCY_DB`, `CURRENCY_INTERVAL`), потому что ребёнку аргументы назначает тот, кто его поднял,
и настройка жила бы в двух местах. **Планировщик стартует внутри лямбды `runStdioServer`**:
до неё стандартный вывод ещё не забран под протокол, и первые строки логов уехали бы клиенту
вместо кадров — тем же уроком, что у сервера GitHub в прошлый день.

**Сервер приложения подключает инструменты курсов** (`CurrencyTools.kt`) так же, как инструменты
GitHub: одна долгая сессия, лениво на первом запросе, закрытие на `ApplicationStopped`.
Кнопки и шторки в интерфейсе у курсов нет — настраиваемого доступа и состояния для показа тоже
нет, поэтому инструменты просто доступны модели. Команду запуска можно задать переменной
`CURRENCY_MCP_COMMAND` (например, `ssh vps sudo -n -u currency env CURRENCY_DB=/var/lib/currency-monitor/currency.db java -jar /opt/currency-monitor/currency-monitor.jar --mcp`);
недоступный процесс инструментов **не отменяет ответ** — вопрос идёт модели без
инструментов, причина в логе, попытка повторяется на следующем запросе.

**Развёртывание на VPS — не только артефакты, но и живой запуск:** `:currency-monitor:fatJar`
даёт `currency-monitor-1.0.0-all.jar` с манифестом (запуск ровно такой, как в задании),
а `currency-monitor/deploy/currency-monitor.service` — unit-файл с `CURRENCY_DB`,
`CURRENCY_INTERVAL=PT1M` и `Restart=on-failure` вместе с инструкцией установки. Сервис развёрнут
на виртуальной машине (Ubuntu 25.10, OpenJDK 21, systemd) и работает службой: `active` и
`enabled`, `User=currency`, без перезапусков; в логе видно, что он ходит к настоящему ЦБ, пишет
историю в `/var/lib/currency-monitor/currency.db` и обновляется по минутному расписанию, а после
`systemctl reboot` поднимается сам и продолжает сбор с той же историей. Проверено и то, чем
служба полезна клиенту: кадры MCP к развёрнутому jar вернули три инструмента и курсы из базы
службы, а локальный `:server:run` с `CURRENCY_MCP_COMMAND`, указывающим на машину, ответил
на `GET /v1/currency` теми же курсами. Попутно выяснилось то, чего не видно в unit-файле:
процесс клиента нужно запускать пользователем службы и с явным `CURRENCY_DB`
(`ssh vps sudo -n -u currency env CURRENCY_DB=/var/lib/currency-monitor/currency.db java -jar …`),
иначе он создаст себе пустую базу рядом с собой.

**Проверка.** `:currency-monitor:test` — 57 проверок (разбор ответа ЦБ с номиналом и не-2xx,
хранилище на настоящем SQLite, границы окна сводки, поведение при отсутствии предыдущего курса
и при нуле в нём, периодичность планировщика на подменных часах, отмена, часовые сводки
и суточное изменение по ним, форма ответов инструментов). `:server:test` — 15 (маршруты курсов
на настоящем MCP-процессе и подставном ЦБ), `:app:shared:testAndroidHostTest` — 36
(лента закреплённого чата: минутная строка, сводка на смене часа, обрезка, шапка с суточной
картиной, служебные строки не уходят в историю модели). Весь набор — 278 проверок (284 записи
по XML: в шести файлах демонстрационных тестов XML дублируется), падений нет, два пропуска
(живые прогоны `demo.live` в `:agent`), APK собирается. Живьём: разовое обновление сходило
к настоящему ЦБ и записало EUR 95.8709, USD 84.3414, GEL 32.1693; подставной источник
с меняющимся курсом наполнил историю, служба поднялась на fat JAR и кадром протокола отдала
оба ответа — последние курсы и сводку за `DAY` с текущим, предыдущим, изменением, минимумом,
максимумом, средним и числом замеров; сервер приложения поднял дочерний процесс курсов,
и живая модель по обычной просьбе сама запросила `get_currency_summary`, затем
`get_currency_rates`, и ответила числами из базы, которых не знает иначе. Закреплённый чат
проверен на запущенном эмуляторе: строка на минуту с растущим курсом, а после посева двух
закрытых часов в базу службы карточка показала суточное изменение, посчитанное сервисом
по сохранённым сводкам (EUR 95,0 → 96,0, +1,0526%), и честное «сохранено 2 ч из 24».

**Отдельная просьба владельца приложения, выполненная в этот же день:** убрана подпись «Ты молодец»
в конце каждого ответа. Она жила в поле `sign_off` профиля (день 12) — из профиля по умолчанию
и из профиля на сервере значение убрано, поле осталось и по-прежнему правится в шторке «Профиль».
Проверено живьём: `GET /v1/profile` отдаёт профиль без подписи, а ответ живой модели на вопрос
приходит без концовки.

**Вторая часть задания — закреплённый чат курсов в приложении** (там же, в ветке `task-18`).
Лента курсов живёт в обычном чате, но закреплена и устроена иначе: писать в неё нельзя, модель
в ней не отвечает, а строка появляется раз в минуту — значит, и собирать курсы служба должна
раз в минуту (`CURRENCY_INTERVAL=PT1M`), а не раз в час.

- **Закрепление — признак чата, а не сравнение с его именем:** `Chat.pinned` (миграция 5→6),
  список сортируется «закреплённые сверху», у такого чата нет поля ввода, полосы задачи
  и кнопки удаления, а `sendMessage` для него выходит сразу — иначе модель ответила бы в ленте,
  где нет ни вопроса, ни места для ответа. Строки монитора носят роль `MONITOR` и отсеиваются
  фильтром истории модели: курс, напечатанный минутой, не становится «репликой» для следующего
  запроса.
- **Лента наполняется, пока приложение открыто:** цикл живёт в области видимости приложения
  и раз в минуту читает `GET /v1/currency`, печатая «время · EUR … · USD … · GEL …» (время —
  из метки сервера: виден момент, когда курсы посчитал сервис). Лента обрезается до 240 строк,
  суточную картину показывает шапка, а не вся лента.
- **Раз в час — сводка, и она хранится.** После каждого состоявшегося обновления служба
  закрывает прошедший час сводкой в ту же базу (`currency_hourly_summaries`, ключ «час + валюта»,
  `INSERT OR REPLACE`): суточная картина должна быть полной независимо от того, было ли
  приложение открыто, поэтому считает её служба, а не клиент по своей ленте. Третий инструмент
  `get_currency_change(hours)` отдаёт изменение по окну из последних **закрытых** часов,
  честно сообщая, сколько часов окна действительно наблюдалось (`hoursCovered`, `from`, `to`,
  `note`), — недобор не выдаётся за сутки. В ленте на смене часа той же сводкой печатается
  «Сводка за час ЧЧ:00–ЧЧ:00», а при открытии чата карточка-шапка читает сутки и говорит,
  чего не хватает («сохранено 2 ч из 24»).
- **Сервер приложения отдаёт тело ответа инструмента как есть** (`GET /v1/currency`,
  `GET /v1/currency/change?hours=N`; 400 на недопустимый `hours` по публичным границам самого
  инструмента, 502 при недоступной сессии). Второй модели тех же чисел на сервере нет: она
  разошлась бы со службой в том, что считать «последним закрытым часом». Клиент изменение
  не считает и не может — в общем коде KMP нет ни `BigDecimal`, ни библиотеки дат, а `Double`
  в деньги здесь не заводят; он печатает цифры ровно те, что пришли, меняя только точку
  на запятую (масштаб с конечными нулями на проводе теряется: `JsonPrimitive` печатает
  `BigDecimal.toString()`, и это осознано — строка заставила бы модель считать по тексту).

Проверено на запущенном эмуляторе поверх базы прошлых дней (заодно миграция 5→6): «Курсы валют»
стоит первым с подписью «закреплён», кнопки удаления нет, поля ввода и полосы задачи в чате нет,
в ленте — по строке на минуту с растущим курсом; после посева двух закрытых часов в базу службы
карточка показала изменение, посчитанное сервисом по сохранённым сводкам (EUR 95,0 → 96,0,
+1,0526%), и «сохранено 2 ч из 24». Подробности — `docs/task-18-currency-monitor.md`, §17–§21.

### task-19

День 19. Композиция MCP-инструментов: цепочку «курсы → сводка → файл» собирает модель

День 18 дал агенту третий MCP-сервер (курсы валют) — и один инструмент. День 19 проверяет
другое: сервер объявляет **три независимых инструмента**, а нужную последовательность из них
собирает **модель** по обычной просьбе, без зашитого порядка и без кода, который знал бы про
все три шага сразу.

**Новый модуль `:mcp-pipeline`** — четвёртый сервер инструментов и второй, который читает базу
службы курсов (только на чтение, через `SqliteCurrencyRateRepository`). Он не внутри
`:currency-monitor` (тот собирает данные и живёт на ВМ службой, этот пишет отчёты на машине
человека) и не внутри `:mcp` (там общая часть объявления инструментов — ею новый модуль
пользуется, а не заменяет её). Флага `--mcp` у точки входа нет: работы без клиента у пайплайна
не существует, поэтому запуск без аргументов и есть сервер, а база открывается лениво — в режиме
`--list-tools` список берётся из объявлений.

**Три инструмента — три отдельных объявления:**

- `getExchangeRates(base?, currencies?)` — последние курсы из истории, ответ JSON целиком:
  `base`, `updatedAt` (момент самого свежего значения, а не время ответа), `rates`, `missing`
  (валюты, о которых спросили, а истории у них нет). База — аргумент: история хранится к рублю,
  но вопрос «сколько долларов стоит евро» законен, и пересчёт делается там, где есть оба курса
  (шесть знаков, `HALF_UP`; курс базы к самой себе — ровно единица, а не `1.000000`). Валюта без
  истории в курсы не попадает: ноль был бы утверждением о курсе, которого в данных нет.
- `summarizeRates(rates)` — принимает документ первого шага целиком и отдаёт текст: момент, база,
  число валют, размах и по строке на валюту с пометками «дороже всех» / «дешевле всех». Порядок
  валют — как в документе, числа — как пришли (с запятой в дробной части), размах печатается без
  хвостовых нулей. Строка принимается наравне с числом: документ может составить и модель.
- `saveToFile(name?, content)` — пишет текст в каталог отчётов и отвечает путём, размером и
  SHA-256. Имя от модели проверяется (разделители каталогов, абсолютный путь, `..` и пустое имя —
  отказ, а не укорочение до имени файла), каталог создаётся записью, файл перезаписывается, имя
  по умолчанию — `rates-ГГГГ-ММ-ДД-ЧЧММ.md`.

**Порядок не зашит нарочно.** Один инструмент «сделай отчёт» не проверял бы ничего: передача
данных между инструментами существует ровно там, где их вызывают по отдельности. В описаниях
сказано, чей ответ принимает следующий шаг, — этого хватает, чтобы цепочка собралась, и мало,
чтобы собраться без модели. Отказы инструментов — результат с `isError` и причиной словами
(недопустимая база, незнакомая валюта, пустая история, неразобранный документ, имя с каталогом),
потому что причина уходит модели и она может исправить вызов.

**Проверка.** `:mcp-pipeline:test` — 20 проверок: инструменты по отдельности (курсы и пересчёт,
разбор документа и отказы, запись файла и проверка имени) и цепочка на настоящем процессе MCP
с временной базой (три инструмента объявлены; документ первого шага уходит второму, текст
второго — третьему, файл на диске равен сводке). Живая демонстрация `./gradlew
:server:pipelineDemo -Pdemo.live=1`: модель `deepseek-v4-flash` по просьбе «получи текущие курсы
USD, EUR и GEL относительно рубля, сформируй краткую сводку и сохрани её в файл» позвала
инструменты в порядке `getExchangeRates` → `summarizeRates` → `saveToFile` (три раунда,

### task-20

День 20. Оркестрация MCP: один агент, несколько серверов, длинный workflow

Дни 16–19 дали агенту по серверу инструментов за раз. День 20 убирает границу: агент получает
**один список инструментов нескольких MCP-серверов**, сам выбирает нужные, а маршрут каждого
вызова (какому серверу он принадлежит) держит оркестратор. Порядок шагов не зашит — длинную
цепочку собирает модель по описаниям инструментов.

**Новый сервер `:mcp-report`** (четвёртый в проекте): `createReport(title, sections)` собирает
markdown из заголовка и секций, `saveReport(content, filename?)` пишет файл в свой каталог
(`REPORTS_DIR`) и отвечает абсолютным путём. Флага `--mcp` у него нет: работы без клиента не
существует. В `:mcp-github` добавлены `getRepository(repository)` и
`getRecentCommits(repository, limit)` — без них просьбу «найди репозиторий и покажи коммиты»
выполнить было нечем.

**Единый реестр и имена вызовов** (`server/.../orchestration/McpToolRegistry.kt`). Имя, которое
видит модель, — `сервер__инструмент` (`github__getRecentCommits`): одинаковые имена у разных
серверов возможны (запись файла умеют и пайплайн, и сервер отчётов), и выбирать между ними должен
не код, а модель. Разделитель — двойное подчёркивание, а не точка: имена функций в API провайдера
обязаны совпадать с `^[a-zA-Z0-9_-]+$`, и список с точками отклоняется целиком (`400 Invalid
'tools[0].function.name'` — проверено живым запросом). Повторная запись того же имени реестр
не удваивает: сессию сервера могут поднять заново.

**Оркестратор** (`server/.../orchestration/McpOrchestrator.kt`) делает ровно одно: по имени вызова
находит сервер, выполняет вызов и отвечает результатом; выбор инструмента остаётся за моделью.
Срок вызова — минута (длинный workflow не должен держаться за один зависший вызов). Отказы —
структурой `{"success": false, "error": {"code", "server", "tool", "message"}}` с кодами
`MCP_SERVER_UNAVAILABLE`, `MCP_UNKNOWN_TOOL`, `MCP_TOOL_TIMEOUT`, `MCP_TOOL_ERROR`, `MCP_CALL_FAILED`,
`MCP_EMPTY_RESULT`; отказ самого инструмента тоже заворачивается в эту форму — в его тексте не
сказано, чей это отказ. Успешный результат отдаётся текстом инструмента как есть: следующий шаг
принимает его аргументом. Каждый вызов печатается одной строкой протокола — номер запроса, номер
вызова, инструмент, сервер, размеры аргументов, длительность, исход: по этим строкам
восстанавливается весь workflow одного запроса.

**Предел раундов** `MAX_TOOL_ROUNDS` поднят с трёх до пятнадцати: три хватало на один сервер,
а длинная цепочка дня 20 обрывалась бы на середине. Бесконечный цикл по-прежнему невозможен.

**Передача данных между серверами идёт через агента**: результат одного уходит аргументом
следующему, серверы друг о друге не знают.

**Проверка.** Живой прогон `./gradlew :server:orchestrationDemo -Pdemo.live=1`: модель
`deepseek-v4-flash`, три сервера инструментов настоящими процессами по протоколу MCP (GitHub —
подставной API, курсы — временная база, отчёты — временный каталог). Модель получила девять
инструментов трёх серверов и прошла цепочку сама: `currency→get_currency_rates`,
`github→get_repositories`, `github→getRecentCommits`, `report→createReport`, `report→saveReport`
(пять вызовов, три сервера, ни одного зашитого шага); числа из ответа сервера курсов
(95.8709 / 84.3414 / 32.1693) нашлись в записанном отчёте рядом с репозиторием `kmp-agent`
из GitHub MCP. Подробности — `docs/task-20-orchestration.md`.

### task-21

День 21. Индексация документов: embeddings, две стратегии chunking и сравнение поиска

Локальный конвейер `Document → ChunkingStrategy → DocumentChunk → EmbeddingProvider → IndexedChunk
→ VectorStore` собран в отдельном модуле **`:indexing`** (Kotlin/JVM). Один и тот же набор
документов индексируется **обеими** стратегиями в два независимых индекса. Перенесённого текста
книги в проекте нет: и корпус дня, и загруженные документы приходят из PDF, а страницы, заголовки
и абзацы извлекаются из вёрстки (§ «Интерфейс»). У отчёта (`indexReport`) есть фикстура —
четыре главы части IV «Принципы организации компонентов» книги «Чистая архитектура»
в `indexing/src/test/resources/corpus`: 56 569 символов (7 445 токенов) и 35 разделов, неизменный
текст для сравнения стратегий от прогона к прогону. Ни PDF дня, ни главы фикстуры в репозиторий
не попадают — авторское право, `.gitignore`: файлы лежат рядом с кодом на машине, где идёт прогон.

**Стратегии.** `FixedSizeChunker(chunkSize = 1500, overlap = 200)` — baseline: склеивает файлы
документа и режет окном, границы файлов, заголовков и абзацев для неё не существуют.
`StructuralChunker(maxChunkSize = 2400)` разбирает Markdown на блоки (заголовки, fenced-код,
абзацы), начинает новый чанк на каждом разделе, укладывает блоки жадно, а слишком длинный раздел
делит по абзацам, а не по символам; границу файла не пересекает никогда. Заголовок, за которым нет
текста (заголовок части перед главой, заголовок, разорванный разрывом страницы), чанком не
становится: он открывает чанк следующего раздела, потому что искать в чанке без текста нечего,
а по косинусу короткий чанк обгоняет содержательный.

**Embeddings и индекс.** Провайдеров два, оба локальные и оба за интерфейсом `EmbeddingProvider`.
`HashingEmbeddingProvider` (512) — детерминированный офлайн-базовый (hashing trick: слова +
символьные триграммы, субфинейный TF, L2-норма): воспроизводим, не зависит ни от сети, ни от
ключей API, на нём идёт `indexReport`. Второй — модель через локальный демон **Ollama** в отдельном
модуле **`:indexing-ollama`** (`POST /api/embed`, по умолчанию `bge-m3`, 1024 измерения, размерность
берётся у модели пробным вектором): близость смысловая, а не лексическая, поэтому вопрос,
сформулированный не словами книги, доходит до ответа. Модуль вынесен из `:indexing` потому, что
конвейер объявлен модулем без клиента и сети, а здесь HTTP и адрес демона; HTTP — клиентом JDK,
без третьей библиотеки. Выбор — окружением, не кодом: `INDEXING_EMBEDDING` = `auto` (по умолчанию)
| `ollama` | `hashing`, `INDEXING_OLLAMA_URL`, `INDEXING_OLLAMA_MODEL`; `auto` берёт модель, если
демон отвечает (`GET /api/version`), и хеширование, если нет, — с причиной в строке провайдера
на странице, а не молча.

Вектор хранится вместе с текстом и метаданными в JSON-файле (`JsonVectorStore`, запись сквозная);
после индексации оба файла перечитываются с диска, и поиск идёт по сохранённым данным. Поиск —
косинусная близость, Top-K по убыванию. Размерность вектора — часть данных индекса: индекс,
посчитанный одной моделью, ищется только ею, а смена модели означает перестройку индекса.

**Сравнение.** Десять русских запросов выполняются по обоим индексам. Релевантность считается по
содержанию (чанк содержит ≥0.6 слов эталонного раздела), а не по метаданным: у фиксированной
стратегии `section` пуст по построению, и оценка по нему мерила бы метаданные, а не поиск — по той
же причине не проверяется и `source` (чанк, пересёкший границу файлов, содержит ответ, а дефект его
метаданных виден отдельной строкой отчёта).

**Результат прогона** (`./gradlew :indexing:indexReport`, 2026-10-06): 44 чанка у Fixed Size против
44 у Structural при настройках по умолчанию; токенов в чанках 8 612 (×1.16 к документу — перекрытие
дублирует текст) против 7 445 (×1.00); средний размер 1 481 против 1 284; фиксированных чанков через границу файлов — 3,
структурных — 0; разделы размечены у 0% и 100% чанков (35 разделов). Поиск: Top-1 3/10 против 3/10,
Top-3 5/10 против 7/10, MRR 0.38 против 0.47. Найдено 9 мест, где фиксированная граница прошла
внутри логически цельного фрагмента — в том числе внутри слова (`…Maven, Leinin` / `gen и RVM…`) и
между заголовком раздела и его текстом. Вывод по числам: структурная нарезка чаще держит ответ
в первых трёх чанках и полностью сохраняет метаданные, а на первое место чаще не выходит никто
(3 из 10 у обеих) — на разделах фикстуры соседние чанки говорят теми же словами, а локальный
лексический embedding их почти не различает. Fixed Size дешевле, не зависит от разметки и даёт
перекрытие 200 символов.

**Интерфейс** (`./gradlew :indexing-ui:run`, http://127.0.0.1:8099) — отдельный модуль
**`:indexing-ui`**: Ktor и одна страница из ресурсов. Корпус дня — **встроенный PDF романа
«Бесы»** (`indexing-ui/src/main/resources/book.pdf`, страницы 1–40): вопрос дня задан заранее,
и ответ для него лежит в первой главе — внутри этого отрезка, поэтому документом дня служит сам
файл, а не перенесённый текст книги — копия разошлась бы с оригиналом, и эталон считался бы
по копии. В корпус входят не все страницы книги, а отрезок вокруг ответа: его начало — первая часть
романа и история Степана Трофимовича Верховенского, то есть и ответ, и соседний с ним текст,
который поиск видит как похожий. Файл под авторским
правом, в репозиторий он не попадает (`.gitignore`, как и главы фикстуры для отчёта); страница
разбирает его один раз при первом запуске и дальше поднимает корпус готовым файлом в `documents/`.

Страница — путь из трёх шагов: **загрузите PDF → постройте индекс → запустите поиск вопроса дня**;
порядок виден по доступности кнопок (без документа индексация недоступна, без индекса — поиск),
и загрузка индексацию не запускает — настройки выбираются между шагами. Документ дня помечен
в корпусе словом «ресурс дня», так что первый шаг уже пройден и начинать можно со второго; свой
PDF добавляется рядом теми же полями. Вопрос дня и ответ на него заданы заранее и не редактируются:
поля ввода у вопроса нет, страница показывает и вопрос («Почему Степан Трофимович
стал воспитателем сына Варвары Петровны?»), и ответ задания, а рядом — абзацы документа, которые на этот вопрос отвечают,
и текст страниц файла, где ответ лежит. Абзац должен быть близок к лучшему (не слабее половины его оценки),
а не просто иметь одно общее слово с ответом: на стр. 7–8 общие слова с ответом есть у трёх
абзацев, а отвечает из них один, и «отвечает» по одному слову значило бы «отвечает» почти везде. Формулировки вопроса
и ответа — слова задания, в книге их дословно нет; поэтому рядом стоит и то, что о том же самом
говорит книга. Настройки нарезки (`chunk`, `overlap`, `max_chunk`)
редактируются на странице и уходят в запрос индексации — их проверяют конструкторы чанкеров,
отвергнутые настройки ничего не меняют, а если поля разошлись с настройками построенного индекса,
страница подсказывает, что индекс нужно построить заново. Рядом — поля «Ссылка на PDF» и
«Локальный файл PDF»: документ снаружи (по ссылке или выбранный в браузере) разбирается постранично
(PDFBox), сохраняется в `documents/` рабочего каталога (то есть переживает перезапуск) и
индексируется — строки вёрстки склеиваются в абзацы медианным правилом, страницы попадают
в метаданные чанков, а заголовки размечаются по кеглю: основной текст романа набран 20 pt,
титулы — 33 pt, части — 28 pt, главы — 23 pt, и `section` у чанков структурной стратегии называет
место в книге так же, как называла бы разметка. Заголовок, разорванный вёрсткой на две строки,
склеивается обратно, если продолжение начинается со строчной буквы: правило отделяет продолжение
от следующего названия, за «Глава первая» у романа идёт «Вместо введения…». Цена правила — название
первой главы, разорванное перед именем собственным («…биографии многочтимого / Степана Трофимовича
Верховенского»): оно остаётся двумя заголовками, но, поскольку чанк на заголовке без текста
не начинается, а имя раздела берётся у первого из самых глубоких заголовков группы, главой
по-прежнему называется «Глава первая». Оба входа ведут в один разбор: проверки
размера и заголовка `%PDF-` общие, имя файла нормализуется в имя файла корпуса (кириллица
сохраняется, «../» — нет). Эталон дня задан страницами PDF (стр. 7–8): текст этих страниц читается
из документа дня, поэтому место ответа не может разойтись с данными, а попаданием считается чанк,
лежащий на этих страницах, — правило одно для обеих стратегий, и фиксированная не проигрывает
из-за отсутствия разделов. Абзацы, которые отвечают на вопрос, ищутся среди этих страниц по словам
ответа задания, а не вопроса: показать нужно ответ, а не строку, похожую на формулировку вопроса.
Их может быть несколько — `AnswerFragment.matches` возвращает все абзацы с общими словами в порядке
следования в тексте, а поиск по чанкам показывает по-прежнему один лучший абзац (он режется окном
вокруг предложения с наибольшим числом общих слов, и у пересказа задания общих словоформ с книгой
почти нет — поэтому рядом всегда стоит весь текст стр. 7–8). Под каждым результатом страница показывает разбор
близости — вектор чанка из индекса, вектор вопроса, слагаемые по общим измерениям с подписями
признаков (слова и триграммы) и сверку «similarity = косинус по этим векторам = сумма вкладов»;
у вектора модели признаков нет, и вместо подписей ячейка говорит «без подписей», а не выдумывает
имена. Корпус показан с числом
символов и токенов (по документу и по файлам), журнал фаз и статус — с числом кусочков и токенов
в них («документ поделён на 94 кусочка (FIXED_SIZE, 21 963 токена) и 61 кусочек (STRUCTURAL,
18 980)» на корпусе дня: 39 размеченных страниц, 121 945 символов, 18 980 токенов); окно 800
с перекрытием 100 даёт вместо этого 175 и 137 кусочков. Кнопка «Запустить индексацию» запускает обе стратегии в фоне,
страница опрашивает ход работы (фаза, `done`/`total`, процент, журнал фаз с таймингами)
и после готовности отвечает на вопрос дня, показывая для каждой стратегии ранг, similarity,
`source`, `section`, страницу книги и фрагмент чанка, в котором лежит ответ; эталон со страницами
ответа и их текстом виден отдельно, а в выдаче отмечается чанк, попавший на эти страницы.
Рядом с выдачей стоит строка провайдера («Ollama bge-m3 — провайдер ollama, 1 024 измерений…»).
На корпусе дня (94 и 61 кусочек) мера отвечает по словам, которые у ответа задания и книги общие
(«Степан Трофимович», «Варвара Петровна», «предложение», «сына»), и провайдеры отвечают по-разному.
У модели эталонные чанки первые в обеих стратегиях: фиксированная начинает со стр. 8 (0.649)
и держит следом стр. 7–8 (0.636), структурная — со стр. 8 (0.651) и возвращается к эталону
на четвёртом месте (стр. 8–9, 0.595), а третьим-вторым в обеих идёт стр. 25 — то же приглашение,
но без «почему». У хеширования эталонные чанки восьмой и девятый (0.324 и 0.301), а наверху —
стр. 17 (0.367 и 0.387): там о сыне Степана Трофимовича сказано, что он видел его дважды. То есть
лексическая мера отвечает «где эти слова есть», модель — «где об этом сказано»; ранга эталон
не боится: ответ задания, абзацы ответа и текст стр. 7–8 показаны отдельно и всегда. Цена
модели — время: 14 с на те же 155 чанков против 0.4 с у хеширования (155 запросов к демону), поиск
же остаётся одним вектором вопроса. Шкала близости — свойство меры (у хеширования вес задаёт
частота внутри чанка, короткий чанк получает близость выше при тех же общих словах; у модели своя
шкала), поэтому числа внутри одной выдачи сравнимы, а между провайдерами и между стратегиями
с разной длиной чанков — лишь грубо.

Модель поднимается отдельно и по желанию: `brew services start ollama` — демон на `127.0.0.1:11434`,
`ollama pull bge-m3` — 1.2 ГБ и 1024 измерения; `./gradlew :indexing-ui:run` в режиме `auto`
подхватит её сам и напечатает выбор в консоль запуска. Проверки провайдера — `./gradlew
:indexing-ollama:test` (протокол Ollama на подставном сервере, живого демона не требуют).
Подробности — `docs/task-21-indexing.md`.

### task-22

День 22. RAG: два агента на одном вопросе — с базой дня 21 и без неё

Агент над индексом дня 21 собран в отдельном модуле **`:rag`** (Kotlin/JVM). Путь запроса —
`Question → embedding → поиск по индексу → Top-K = 3 → контекст с метаданными → LLM → Answer`:
вопрос превращается в вектор тем же провайдером, что индексировал корпус, поиск идёт по готовому
файлу индекса (`--rebuild` собирает его заново, при каждом запросе переиндексации нет), а в запрос
уходят три фрагмента целиком с подписью `файл · стр. N · Глава · чанк #N`. База — тот же корпус,
что у дня 21: встроенный PDF романа «Бесы», страницы 1–40, разобранный тем же разбором в тот же
`book.md` (39 размеченных страниц, 121 945 символов, 18 980 токенов, 61 чанк структурной нарезки);
отдельного текста для дня 22 не заводится — вторая копия книги разошлась бы с первой.

**Два режима — один агент.** Различаются ровно две вещи: блок найденных фрагментов и системное
правило «опирайся только на фрагменты и не дополняй их тем, что помнишь; если ответа во фрагментах
нет — скажи об этом». Всё остальное совпадает дословно (задание «отвечай кратко, три–пять
предложений», текст вопроса, модель, `temperature = 0.0`, `maxTokens`), потому что иначе сравнение
мерило бы разницу промптов, а не пользу поиска. Режим без RAG к поиску не обращается вовсе —
не «обращается и не подставляет»: контракт `SourceFinder` и тест с падающим источником фиксируют,
что в его `Answer` пустая выдача и нулевое время поиска.

**Десять контрольных вопросов** с заранее записанными ожиданиями (`Controls.questions`): ответ
словами, ключевые факты, страницы книги и глава. Правила подбора — проверяемость (у каждого ответа
есть место в корпусе, подтверждённое тестом), разнообразие мест (страницы 8–33, обе главы среза,
разные лица), разная достижимость памятью модели и разные типы ожидания (числа, имена, отношения,
деталь быта, сцена из нескольких предложений). Два вопроса стоят отдельно: **q09** — там, где
при Top-K = 3 поиск до ответа не доходит (готовая поисковая ошибка), **q10** — вопрос, ответа
на который **в базе нет**: правильным поведением считается признать нехватку сведений, а не
вспоминать роман дальше среза. Оценка 0–2 считается по фактам, а не по сходству с формулировкой
(признак — основа слова, поэтому «тростью» и «трость» засчитываются одинаково), попадание источника
в Top-K считается по тексту фрагментов, а не по номерам страниц, и идёт отдельной метрикой.

**Сравнение.** Средняя оценка каждого режима, Source Hit Rate (у скольких вопросов с ответом
в базе ожидаемый текст попал в Top-K), счёт по вопросам, разделение исходов на **поисковые
и генеративные ошибки** (порядок проверок намеренный: сначала поиск — правильный ответ по памяти
при пустой выдаче закрывается как поисковая ошибка), токены и время. Similarity сохраняется
и печатается у каждого фрагмента, но метрикой не является: у косинуса нет порога, за которым
начинается правильный ответ. Прогон десяти вопросов в двух режимах занимает около трёх минут
и пишет `report.md` (таблица оценок и ответы целиком) и `log.md` (путь запроса по шагам: вопрос,
вектор и время поиска, выдача Top-K целиком, контекст, ушедший в модель, и ответ) в `build/rag/`.

**Результат прогона** (`./gradlew :rag:ragDemo -Pdemo.live=1`, 2026-10-07, `deepseek-v4-flash`,
`bge-m3`, Top-3): средняя оценка **без RAG 0,4 из 2** (4 из 19 фактов) против **1,7 из 2**
(16 из 19 фактов) с RAG; **Source Hit Rate 8 из 9 (88 %)**; по вопросам с RAG выше в 8, столько же
в 2, ниже в 0; верно 8, ошибок поиска 1, ошибок генерации 1. Ошибка поиска — q09, у которого нужный
чанк четвёртый по близости (лечится поиском, а не промптом), ошибка генерации — q02, где текст был
в выдаче, а ответ назвал половину фактов. Отдельно виден q10: без базы модель уверенно рассказала
судьбу Петра Степановича по памяти (смерть Шатова, самоубийство Кириллова — всё это дальше среза)
и получила 0, с базой ответила «в приведённых фрагментах ответа на этот вопрос нет» и получила 2.
Тот же набор, прогнанный через страницу (208,7 с), дал близкие числа — 0,5 и 1,5 из 2 при том же
Source Hit Rate: `temperature = 0.0` снижает разброс, но сервер не детерминирован, и от прогона
к прогону меняются формулировки ответов (направление вывода при этом одно и то же — ни одного
вопроса, где с базой хуже).

**Интерфейс** (`./gradlew :rag-ui:run`, http://127.0.0.1:8098) — отдельный модуль **`:rag-ui`**:
Ktor и одна страница из ресурсов (порт и каталог задаются `RAG_UI_PORT` и `RAG_UI_DIR`; каталог
намеренно отдельный, чтобы отчёты страницы не перезаписали отчёты прогона в консоли). На ней
корпус дня, состояние индекса с кнопкой его сборки, таблица десяти вопросов с галочками, поле
Top-K и запуск с прогрессом (один прогон за раз: новый запуск заменяет идущий и чистит данные
предыдущего, а кнопка «Остановить» прекращает работу и оставляет посчитанное). Результат по каждому
вопросу — **два конвейера рядом, по звеньям** (вопрос → вектор → поиск → Top-K → контекст → модель → ответ → сверка),
с промежуточными результатами: размерность вектора вопроса, время поиска, найденные фрагменты
с близостью, страницами и разделом, текст запроса, ушедший в модель, и конечный результат —
ответ, сверка фактов «засчитано N из M» и оценка. В колонке без RAG звено поиска честно говорит,
что поиска не было, а не показывает пустые страницы. Метрики страница не пересчитывает — показывает
те же числа, что посчитал `Report.summary`, и после каждого вопроса переписывает свои `report.md`
и `log.md`. Прогон всей страницы на десяти вопросах — 208,7 с (181,6 с без RAG и 19,8 с с RAG,
из них поиск 0,55 с).

### task-23

День 23. Улучшенный RAG: Query Rewrite, фильтрация по близости и реранкинг

День 23 добавляет к RAG дня 22 три этапа между вопросом и контекстом:
`Question → Query Rewrite → Retrieval Top-K → Similarity Filter → Reranking → Final Top-K → LLM →
Grounded Answer + Sources`. Конвейер живёт в том же модуле **`:rag`** и реализует тот же интерфейс
`SourceFinder`, что поиск дня 22, — поэтому агент из дня 22 не изменился ни на строку, а исходный
вопрос по-прежнему уходит в модель: переписанный запрос служит только поиску и наружу выходит
в трейсе отчёта. Прогон идёт в **трёх режимах** на одном индексе, одной модели и тех же десяти
контрольных вопросах дня 22 — без базы (нижняя граница), базовый RAG (день 22) и улучшенный, — иначе
разница между колонками была бы разницей прогонов, а не этапов.

**Query Rewrite** — интерфейс `QueryRewriter` с парой `original`/`rewritten` и вариант `llm`:
модель по системному правилу составляет из вопроса одну строку ключевых слов (сохранить смысл,
не выдумывать факты, раскрыть местоимения, сохранить имена). Вариант `none` остаётся доступным:
без него нельзя отделить вклад переписывания от вклада фильтра и второго этапа. Ответ модели
приводится в порядок (снимаются метки «Запрос:», склеиваются строки), пустой ответ читается как
«переписывания не случилось», и это помечается в трейсе — искать по пустой строке было бы неверно.

**Два Top-K и порог.** `--retrievalTopK=10` (кандидаты для фильтра и второго этапа) и
`--finalTopK=3` (контекст) — независимые параметры; разбор аргументов запрещает `finalTopK >
retrievalTopK`, потому что конвейер молча отдал бы меньше, чем просят. `SimilarityFilter` отсекает
кандидатов ниже порога `--threshold=`, и порог — часть конфигурации прогона, а не число в коде:
задание просит подобрать его на своей модели и своих вопросах, поэтому `--sweep=0.40,0.50,0.60`
считает таблицу «что порог сделал с выдачей» (сколько осталось, сколько отсеяно, сколько отсеяно
**ошибочно**, сколько контекстов опустело) и «что из этого вышло» (попадание после фильтра, после
второго этапа, средняя оценка ответов). Выдача при подборе считается один раз на вопрос: иначе
разница между строками таблицы включала бы разницу выдач, которые эмбеддинги не гарантируют
побитово. Если после фильтра не осталось ничего, модели не подставляется пустой блок фрагментов —
ей говорится прямо, что фрагментов нет, и она не отвечает по памяти (это же поведение проверяется
вопросом q10).

**Reranking** — интерфейс `Reranker` (`rank(question, candidates): Rerank`), поэтому алгоритм
меняется без правок конвейера: `--rerank=heuristic` (по умолчанию), `llm` или `none`. Эвристика
оценивает кандидата как 0,5 × доля значимых слов вопроса + 0,4 × доля имён собственных + 0,1 ×
близость поиска, сравнивая слова по началу словоформы от основы в пять букв («Лебедкиным» в вопросе
и «Лебедкина» в книге — одно слово); она детерминирована и не стоит обращений к модели, а вклад
LLM-варианта измеряется сравнением. LLM-вариант делает **один** запрос на вопрос (кандидаты
нумеруются, модель отвечает «номер=оценка»); если ответ не разобрался, кандидаты остаются
с близостью, а в отчёт попадает пометка — прогон с поломанным порядком хуже прогона без второго
этапа.

**Трейс и классификация ошибок.** По каждому кандидату сохраняются близость, отметка фильтра,
оценка и позиция после второго этапа, а ранг поиска, ранг реранка и номер в контексте различаются
намеренно: «был четвёртым по близости, порог прошёл, реранкер опустил на шестое — в Top-3 не попал»
читается только по трём разным числам. Правильный фрагмент определяется по тексту (в нём есть
ожидаемый факт), и по цепочке «нашёлся / прошёл порог / попал в Top-3» ошибка относится к этапу:
`RETRIEVAL` — проблема поиска, эмбеддинга или запроса, `FILTER` — порог высок для этой выдачи,
`RERANK` — второй этап опустил нужный фрагмент. `report.md` печатает сравнение по вопросам
с колонкой «Где потерялся», раздел «Кандидаты и этапы» со всеми кандидатами и итоговые метрики
(Hit@10 после поиска, попадание после фильтра, Hit@3 после второго этапа, отсеяно и ошибочно
отсеяно), `log.md` — путь запроса по этапам (`Rewrite → Retrieval → Filter → Reranking → Final
Top-K → LLM → ответ`) с временем каждого шага, `rewrite.md` (с `--rewrite-check`) — две выдачи
на вопрос: по исходному запросу и по переписанному, с местами правильного фрагмента, потерянными
и выдуманными именами.

**Что показал прогон.** На тех же десяти вопросах дня 22 (индекс 61 чанк, `bge-m3`, модель
`deepseek-v4-flash`) улучшенный режим без переписывания запроса доносит правильный фрагмент
до контекста у 9 вопросов из 9 против 8 из 9 у базового и лечит главный случай дня: у q09 нужный
чанк стоял восьмым по близости и в Top-3 дня 22 не попадал — первый Top-K из десяти принёс его
в кандидаты, а второй этап поднял на первое место (0 из 2 → 2 из 2). Порог подобран свипом: 0,40
оставляет 9,4 кандидата из 10 и не отсекает ни одного правильного, тогда как 0,45 теряет два
правильных фрагмента, а 0,60 — почти всю выдачу.

Переписывание на этом наборе не окупается, и это измеренный результат: в двух прогонах оно помогло
0–1 раз и навредило 2–3 из 10, а в основном прогоне стоит одного правильного фрагмента (q04 отсеян
порогом 0,40 — переписанный запрос даёт систематически более низкие близости, а порог подобран
на исходных вопросах). Причина видна в `build/rag/rewrite.md`: вопросы набора самодостаточны, нужные
имена в них уже есть, и переписывание только заменяет формулировку вопроса набором ключевых слов.
Поэтому Query Rewrite реализован и измерен как отдельный этап с флагом (`--rewrite=none` — измеренно
лучший вариант на этом наборе). Второй этап на модели на этой модели работает как близость: она
выставляет оценку одному фрагменту из десяти («4=10»), поэтому рабочим выбран эвристический; сырой
ответ модели при этом виден в `build/rag-llm/log.md`, а не теряется.

Числа — в `build/rag/` (основной прогон), `build/rag-norewrite/` (без переписывания),
`build/rag-llm/` (второй этап на модели), `build/rag/sweep.md` (подбор порога) и
`build/rag/rewrite.md` (проверка переписывания).

Подробности — `docs/task-23-rewrite-rerank.md`.

### task-24

День 24. Grounded RAG: цитаты, источники и режим «не знаю»

День 24 не меняет поиск — он делает ответ **проверяемым**. Конвейер дня 23 остаётся как есть
(`Question → Query Rewrite → Retrieval → Filter → Rerank → Final Top-K`), но между выдачей и ответом
встают три вещи: проверка достаточности контекста **до** обращения к модели, требование цитат в ответе
и программная проверка каждой цитаты по тексту чанка. Прогон `--grounded` спрашивает **две модели
ответа на одной выдаче** каждого вопроса — предыдущий режим (ответ дня 23 без источников и цитат)
и grounded-режим (ответ с источниками, цитатами и проверками), поэтому разница между колонками
относится к проверкам дня 24, а не к поиску; вопросы — те же десять из дня 22.

**Источники собирает система, а не модель.** Модель называет только номер фрагмента контекста,
а файл, главу (`section`), `chunk_id`, страницы и близость подставляет `SourceRef.of` из метаданных
индекса: придумать главу или страницу она не может по построению — этих полей в её ответе нет.
Ссылка на фрагмент, которого модель не получала, — не источник, а выдуманная ссылка: утверждение
в ответ не попадает, а счётчик в отчёте показывает, сколько таких ссылок было.

**Цитата — это фрагмент чанка, а не пересказ.** Ответ приходит JSON-объектом
(`response_format: json_object`, но разбор всё равно проверяет формат: параметр повышает долю
разобранных ответов, а не заменяет проверку), и каждая цитата нормализуется и ищется в тексте
процитированного чанка подстрокой; многоточие делит цитату на части, и каждая часть ищется
отдельно, а цитата короче трёх слов или пятнадцати символов подтверждением не считается — пара слов
совпадёт почти с любым чанком. Утверждение без подтверждённой цитаты в ответ не попадает, и если
подтверждённых не осталось, режим отвечает отказом.

**Режим «не знаю» — отдельный исход, и он наступает до модели.** `Sufficiency.check` сравнивает
лучшую близость **контекста** (фрагменты, прошедшие фильтр) с тем же порогом 0,40, что подобран
парой день-23-свипов: контекста нет, всё отсеяно порогом или лучший фрагмент слабее порога — система
отказывается, не спрашивая модель вовсе, и просит уточнить вопрос. Отказ не несёт ни источников,
ни цитат (§10: иначе он выглядел бы как ответ). На строгом пороге 0,60 это видно вживую: девять
вопросов из десяти — отказы до модели, без единой выдуманной ссылки и цитаты.

**Что показал прогон** (`build/rag24`, порог 0,40, 61 чанк `bge-m3`, `deepseek-v4-flash`): у всех
8 обычных ответов есть источник (9 источников на 8 ответов) и цитата — 23 цитаты, и **все 23
подтвердились** в тексте своих чанков; выдуманных ссылок и невалидных цитат нет ни одной. Answer
Accuracy 6 из 10 — как и у предыдущего режима (4 верных ответа + 2 уместных отказа), Correct
Abstention Rate 2 из 2, лишних отказов нет. Названных фактов при этом меньше (12 из 19 против 14):
grounded отвечает осторожнее и короче, а часть сведений остаётся внутри приведённых цитат,
но не в утверждениях — это видно по разбору в `report.md` и это честный итог дня: проверяемость
выросла до 100 %, точность осталась прежней, а резерв — в полноте ответа, не в проверке. Первая
версия промпта была ещё короче (3 верных ответа): правило «назови все сведения фрагментов, которые
отвечают на вопрос, и на каждое дай свою цитату» подняло результат до 4.

**Прогон на странице можно остановить, а новый запуск чистит прошлый.** Кнопка «Остановить»
отменяет работу — прогон или пересборку индекса — и оставляет на экране то, что успело посчитаться,
вместе с уже записанными файлами: видно, на каком вопросе прогон встал. Новый запуск идущим прогоном
не отвергается: он его вытесняет и стирает данные предыдущего, потому что страница показывает один
прогон — тот, что идёт или остановлен последним. Вытесненный прогон не дописывает поверх нового:
работа помечена номером, и записи с чужим номером отбрасываются — ни ответа, ни файла.

Числа — в `build/rag24/{report.md,log.md}` (основной прогон) и `build/rag24-strict/` (порог 0,60).

Подробности — `docs/task-24-grounding.md`.

  answer is still visible after the app is restarted.

* [/app/shared](./app/shared/src) is for code that will be shared across your Compose Multiplatform applications.
  It also holds the GitHub side of the UI: the sheet that connects to the GitHub MCP server, shows
  whether the server found credentials on the machine (who is authorized, with which scopes and from
  which source) and lets one re-check them, lists the tools it declares (with their arguments and
  allowed values) and calls one by hand
  (`ui/components/GitHubSheet.kt`), and the card that prints a tool command and its answer in the feed
  (`ui/components/ChatBubble.kt`) — both for a call the human made and for one the model chose.
  It also holds the pinned currency chat: the feed that prints a rate line every minute and the
  card above it that shows the change over the day (`ui/components/CurrencyChangeCard.kt`,
  `data/CurrencyFeed.kt`), the chat that cannot be written to (no input field, no model answer,
  `data/CurrencyChat.kt`) and the monitor that fills it while the app is open
  (`repository/ChatRepository.kt`).
  It contains several subfolders:
  - [commonMain](./app/shared/src/commonMain/kotlin) is for code that’s common for all targets.
  - Other folders are for Kotlin code that will be compiled for only the platform indicated in the folder name.
    For example, if you want to use Apple’s CoreCrypto for the iOS part of your Kotlin app,
    the [iosMain](./app/shared/src/iosMain/kotlin) folder would be the right place for such calls.
    Similarly, if you want to edit the Desktop (JVM) specific part, the [jvmMain](./app/shared/src/jvmMain/kotlin)
    folder is the appropriate location.

* [/core](./core/src) is for the code that will be shared between all targets in the project.
  The most important subfolder is [commonMain](./core/src/commonMain/kotlin). If preferred, you
  can add code to the platform-specific folders here too.

* [/agent](./agent/src/main/kotlin) is a separate module with the LLM agent logic: the `LlmAgent` itself,
  the `LlmClient` transport contract, the Ktor `DeepSeekClient` implementation, the message assembly
  and the DeepSeek API DTOs. The server depends on it and only adapts HTTP. It also holds the state
  stores: the `InvariantStore`/`ProfileStore`/`MemoryStore` contracts with their in-memory and
  file-backed implementations (`agent/.../{invariants,profile,memory}/JsonFile*Store.kt`), because
  both the app server and the MCP server read them. It knows nothing about MCP: tools reach it as a
  plain contract (name, description, argument schema, call), so the protocol and the transport stay
  outside the agent.

* [/mcp](./mcp/src/main/kotlin) is the MCP layer of the project, a separate module on purpose —
  neither the agent nor the app server owns it. It holds the client (`McpClient.kt`): it starts an MCP
  server as a child process, speaks stdio JSON-RPC to it and returns the tools that server declares;
  the local MCP server (`ProjectMcpServer.kt`): the project data declared as read-only MCP tools;
  and the part both servers share (`DeclaredTool.kt`, `StdioServer.kt`, `McpAgentTools.kt`): tool
  declarations with their schemas, the stdio server loop and the adapter that turns MCP tools into
  agent tools. It depends on `:agent` for those data types; `:server` does not depend on it at all.

* [/mcp-github](./mcp-github/src/main/kotlin) is the second MCP server: the GitHub tools. Two tools —
  `get_repositories` (`visibility` = `all`/`public`/`private`), reading `GET /user/repos`, and
  `github_access`, reporting who is authorized, with which scopes and where the credentials came from.
  The access is looked up on the machine when a tool is called (`GitHubCredentials.kt`): the
  `GITHUB_TOKEN` environment variable, the file named by `GITHUB_TOKEN_FILE`, the macOS keychain,
  `~/.config/ai-challenge/github.token`, `gh auth token`, then `git credential fill`; the token never
  leaves this process, and `GITHUB_API_BASE` lets tests point the server at a stub. GitHub errors come
  back as `isError` results, and the server never crashes. It shares the `:mcp` part and does not
  depend on `:server`.

* [/currency-monitor](./currency-monitor/src/main/kotlin) is the third MCP server and the only one
  that owns data over time: it collects EUR/RUB, USD/RUB and GEL/RUB from an external source
  (`remote/`, the CBR by default), keeps the history in SQLite (`storage/`, one row per update,
  the rate as text so `BigDecimal` survives), updates it on a schedule (`scheduler/`, a minute
  apart by default, the first update immediately, and every update closes the past hour into a
  stored hourly summary) and answers three MCP tools from it (`mcp/`): `get_currency_rates`,
  `get_currency_summary` with a required `period` of `DAY`/`WEEK`/`MONTH` and
  `get_currency_change` with a required `hours` (`summary/`, the change is built from the stored
  hourly summaries, so the daily picture is complete whether or not the app was running).
  `Application.kt` is the entry point and its four modes: no arguments — the service (scheduled
  collection plus the stdio protocol, alive after stdin ends), `--mcp` — the process a client owns,
  `--once` — a single update, `--list-tools` — print the declarations without a database or network.
  It runs on a server as a plain `java -jar` (`deploy/currency-monitor.service`).

* [/server](./server/src/main/kotlin) is for the Ktor server application: HTTP routes, server plugins
  and the client-facing request/response models. It stays a plain HTTP app: MCP did not replace it,
  and they serve different consumers (HTTP — the app and the human, MCP — the agent). It is also the
  one place that attaches MCP tools to chat requests (`GitHubTools.kt`, `CurrencyTools.kt`): it keeps
  one long-lived session with each MCP server and hands the tools to the agent, so the model can call
  them on its own (the currency session is opened lazily and its command can be pointed elsewhere with
  `CURRENCY_MCP_COMMAND`). Two currency routes hand the app the same numbers the agent sees:
  `GET /v1/currency` and `GET /v1/currency/change?hours=N` return the tool's answer body as it is
  (400 for an out-of-range `hours` — the bounds come from the tool itself, 502 when the session
  cannot be started).

### Running the apps

Use the run configurations provided by the run widget in your IDE's toolbar. You can also use these commands and options:

- Android app: `./gradlew :app:androidApp:assembleDebug`
- Server: `./gradlew :server:run`
- MCP connection demo (the client connects to the project MCP server, prints its tools): `./gradlew :mcp:mcpDemo`
- MCP server tools, no connection (the server process prints what it declares and exits): `./gradlew :mcp:mcpTools`
- MCP server as a service: `./mcp/mcp-server.sh start` (background, logs and protocol frames in `mcp/build/mcp-server`), `./mcp/mcp-server.sh status` (checks the protocol, not just the process), `./mcp/mcp-server.sh stop`; also `restart`, `logs`, `frames`, `tools`, `--data-dir DIR`, and `--server project|github|currency` to pick which server the script owns (`github` takes `GITHUB_TOKEN`/`GITHUB_API_BASE` from the environment, `currency` builds `:currency-monitor:fatJar` and runs it as the service)
- MCP server for a third-party client (fat jar, speaks stdio on its own stdout): `./gradlew :mcp:fatJar` then `java -cp mcp/build/libs/mcp-1.0.0-all.jar com.osvin.aichallenge.mcp.ProjectMcpServerKt` (add `--list-tools` to print the tools instead of serving)
- GitHub tools demo (the agent picks the MCP tool by a plain request; live model, stub GitHub API): `./gradlew :server:githubDemo -Pdemo.live=1`
- Currency service tools, no connection: `./gradlew :currency-monitor:mcpTools` (prints all three tools; `period` is required with `DAY | WEEK | MONTH`, `hours` is required as a whole number of hours from 1 to 720)
- One currency update and exit (`CURRENCY_API_BASE`, `CURRENCY_DB`, `CURRENCY_INTERVAL` come from the environment; exit code 1 if nothing was saved): `./gradlew :currency-monitor:currencyOnce`
- Currency service as a standalone jar (this is what runs on a server): `./gradlew :currency-monitor:fatJar` then `java -jar currency-monitor/build/libs/currency-monitor-1.0.0-all.jar` (no arguments — the service: minute collection plus stdio protocol, it keeps living after stdin ends; `--mcp` — the process a client owns, exits with it; `--once` — one update; `--list-tools` — print the tools, no database and no network). Deployment units and install commands: `currency-monitor/deploy/currency-monitor.service`
- Pipeline tools (chain of three: rates → summary → file), no connection: `./gradlew :mcp-pipeline:mcpTools`; the chain itself on a live model: `./gradlew :server:pipelineDemo -Pdemo.live=1`; as a standalone process (`PIPELINE_OUTPUT_DIR`, `CURRENCY_DB` from the environment): `./gradlew :mcp-pipeline:fatJar` then `java -jar mcp-pipeline/build/libs/mcp-pipeline-1.0.0-all.jar`
- Orchestration of several MCP servers (day 20): `./gradlew :server:orchestrationDemo -Pdemo.live=1` (long workflow through three servers, assembled by the model); report server alone: `./gradlew :mcp-report:mcpTools`, as a process: `./gradlew :mcp-report:fatJar` then `java -jar mcp-report/build/libs/mcp-report-1.0.0-all.jar` (`REPORTS_DIR`, `REPORT_MCP_COMMAND` from the environment)
- Document indexing (day 21): `./gradlew :indexing:indexReport` — индексирует набор документов обеими стратегиями, печатает статистику, 10 запросов по двум индексам, сравнение стратегий и вывод; отчёт и оба индекса (JSON) кладутся в `indexing/build/index/` (каталог можно задать: `--args="/tmp/index"`)
- Indexing UI (day 21): `./gradlew :indexing-ui:run` — страница на http://127.0.0.1:8099: кнопка запуска индексации корпуса с прогрессом и разбор эталонного вопроса (top_k, страница книги и фрагмент с ответом по обеим стратегиям). Порт и каталог индексов задаются переменными `INDEXING_UI_PORT` и `INDEXING_UI_INDEX_DIR`; чем считать векторы — `INDEXING_EMBEDDING` (`auto` | `ollama` | `hashing`), `INDEXING_OLLAMA_URL`, `INDEXING_OLLAMA_MODEL` (для модели нужен демон: `brew services start ollama` и `ollama pull bge-m3`)
- Ollama embedding provider (day 21): `./gradlew :indexing-ollama:test` — 3 проверки протокола на подставном сервере, живого демона и модели не требуют
- RAG comparison (day 22): `./gradlew :rag:ragDemo -Pdemo.live=1` — десять контрольных вопросов в двух режимах (20 запросов к модели, около трёх минут), средняя оценка каждого режима, Source Hit Rate и разделение ошибок на поисковые и генеративные; без флага печатает подсказку. Отчёты — `build/rag/report.md` (таблица и ответы целиком) и `build/rag/log.md` (путь запроса: вопрос → вектор → Top-K → контекст → ответ); база, индекс и Top-K задаются `--args="--dir=/tmp/rag --topK=5 --strategy=fixed --rebuild --only=q09"`
- Improved RAG ablations (day 23): те же настройки с одним отличием — `--args="--dir=build/rag-norewrite --rewrite=none"` (вклад переписывания) и `--args="--dir=build/rag-llm --rerank=llm"` (второй этап на модели)
- Improved RAG (day 23): тот же `./gradlew :rag:ragDemo -Pdemo.live=1` идёт уже в трёх режимах (без базы / базовый RAG / улучшенный с Query Rewrite, порогом и реранкингом) и печатает попадание по этапам и итог по каждому вопросу; `--args="--retrievalTopK=10 --finalTopK=3 --threshold=0.40 --rewrite=llm|none --rerank=heuristic|llm|none"` задают конвейер, а `--args="--sweep=0.40,0.45,0.50,0.60 --rewrite-check"` добавляет подбор порога (таблица «что порог сделал с выдачей и с ответами» → `build/rag/sweep.md`, 30 ответов) и проверку переписывания (две выдачи на вопрос, потерянные и выдуманные имена → `build/rag/rewrite.md`, 10 переписываний). В `build/rag/report.md` к прежней таблице добавлены колонки Hit@10 после поиска, попадания после фильтра, Hit@3 после второго этапа и «где потерялся правильный фрагмент», в `log.md` — разделы этапов с временем каждого
- Grounded RAG (day 24): тот же `./gradlew :rag:ragDemo -Pdemo.live=1 --args="--dir=build/rag24 --grounded"` — на каждый вопрос одна выдача и два ответа (предыдущий и grounded), печать по вопросу и метрики дня (§17); в `report.md` — таблица §18, ответы с источниками и цитатами и разбор проверок, в `log.md` — путь запроса по этапам (§19) с решением о достаточности и результатом проверки каждой цитаты. `--plain-text` отключает `response_format: json_object` (прогон с ним и без него — два условия одного режима), `--threshold=0.60` показывает отказы до модели, `--only=q01,q10` ограничивает набор
- RAG UI (day 23–24): `./gradlew :rag-ui:run` — страница на http://127.0.0.1:8098: таблица десяти вопросов с галочками, настройки конвейера (Top-K базового режима, Retrieval Top-K, Final Top-K, порог, вариант переписывания, вариант второго этапа), кнопки прогона, остановки и сборки индекса. «Остановить» прекращает работу и оставляет на странице то, что успело посчитаться, а новый запуск заменяет идущий прогон и очищает результаты предыдущего — на странице всегда один прогон: тот, что идёт или остановлен последним. По каждому вопросу — **три конвейера рядом** (без базы / базовый RAG / улучшенный RAG) и полный трейс этапов: исходный вопрос и переписанный запрос, Retrieval Top-N таблицей (близость, прошёл или отсечён порогом, оценка второго этапа, позиция до → после, номер в контексте), фильтр, реранкинг, финальный Top-K, контекст, ответ со сверкой фактов и оценкой 0–2 и классификация потери («не найден поиском / отсечён порогом / проиграл на втором этапе»). Под таблицей — метрики дня 22 (средние, Source Hit Rate) и метрики этапов (средние трёх режимов, попадания Hit@N → после фильтра → Hit@K, цена фильтра, потери, счёт реранкинга и переписывания). Порт и каталог отчётов задаются переменными `RAG_UI_PORT` и `RAG_UI_DIR`; векторы — теми же `INDEXING_EMBEDDING`, `INDEXING_OLLAMA_URL`, `INDEXING_OLLAMA_MODEL`, что у дня 21 День 24 добавлен к каждому вопросу раскрывающимся блоком **«Grounded-ответ»**: ответ, источники (файл, глава `section`, `chunk_id`, страницы, близость, оценка второго этапа, номер фрагмента), цитаты с утверждениями, решение о достаточности контекста с числами, таблица проверки цитат («цитата в чанке: да/нет» и причина) и итог по вопросу; над таблицей — сводка §17 (Answer Accuracy, Source Coverage, Quote Coverage, Grounded Answer Rate, Correct Abstention Rate, факты против предыдущего режима, выдуманные ссылки и невалидные цитаты). Числа страница не считает: они приходят из тех же `GroundingSummary` и `GroundedCheck`, что и в отчёт, а ответы и проверки пишутся в `report-day24.md` и `log-day24.md` рядом с отчётами дня 23
- Currency tools for the app server when the service runs on another machine: `CURRENCY_MCP_COMMAND='ssh vps sudo -n -u currency env CURRENCY_DB=/var/lib/currency-monitor/currency.db java -jar /opt/currency-monitor/currency-monitor.jar --mcp' ./gradlew :server:run` (the database belongs to the service user and the default path is relative, so both the user and the path are named in the command; otherwise the child creates an empty database of its own)
- Web app:
  - Wasm target (faster, modern browsers): `./gradlew :app:webApp:wasmJsBrowserDevelopmentRun`
  - JS target (slower, supports older browsers): `./gradlew :app:webApp:jsBrowserDevelopmentRun`
- iOS app: open the [/app/iosApp](./app/iosApp) directory in Xcode and run it from there.
