# День 17. MCP-сервер для GitHub и вызов инструмента агентом — устройство

День 16 подключил агента к MCP и показал список инструментов. День 17 доводит это до работы:
появляется второй MCP-сервер (он ходит в GitHub REST API), а **агент сам** вызывает инструмент,
когда этого требует обычная просьба, и отвечает по его данным.

## 2. Что установлено и что из этого следует

Новый модуль `:mcp-github`. Отдельный, а не инструмент внутри `:mcp`: у сервера проекта данные —
правила и профиль, у сервера GitHub — сеть и токен, и в одном модуле они получили бы один fat
JAR и одну точку входа. Общая часть (объявление инструмента, сборка сервера, режимы запуска на
stdio) при этом не скопирована: она вынесена в `:mcp` (`DeclaredTool.kt`, `StdioServer.kt`), и
второй сервер ею пользуется. Копия разошлась бы с первой на первой же правке запуска.

Ktor-клиент — только `ktor-client-core` + `ktor-client-cio`: серверный движок (Netty) не нужен,
сервер общается с клиентом по stdio, а наружу сам ходит как клиент.

## 3. Сервер GitHub: где границы

**Токен читается в момент вызова, а не при старте.** Сервер поднимают и для `--list-tools`,
где GitHub не нужен; падать из-за отсутствия переменной окружения на старте значило бы
запрещать знакомство с инструментом до настройки. Поэтому `GitHubConfig.requireToken()`
бросает `GitHubApiException` с готовым текстом, а инструмент превращает её в `isError`
одним местом. Возврат `null` вместо исключения означал бы проверку на каждом шаге — и рано
или поздно забытую.

**Адрес API — параметр, а не константа** (`GITHUB_API_BASE`, по умолчанию
`https://api.github.com`). Это не «гибкость на будущее»: токена GitHub в окружении этого
проекта нет, поэтому проверка идёт на подставном API на localhost, и адрес должен быть
подменяемым. Код-путь при этом тот же, что с настоящим GitHub.

**Модель отделена от ответа GitHub.** Публичный `GitHubRepository` — с именами полей из
задания (`fullName`, `url`), а `GitHubRepositoryResponse` (internal) разбирает ответ GitHub
(`full_name`, `html_url`) и превращается в модель. Если повесить `@SerialName` на саму модель,
её собственный JSON-вывод уехал бы модели-потребителю с именами GitHub, а не с обещанными:
одна аннотация обслуживала бы два разных формата.

**Видимость берётся из `visibility`, а если поля нет — из `private`.** GitHub отвечает
`visibility` не во всех случаях (старые ответы, отдельные маршруты), а `private` есть всегда.
Фильтровать по флагу `private` в обход видимости не стали: тогда третья видимость GitHub
(`internal`) попала бы в «приватные», хотя инструмент обещает только публичные и приватные,
а `all` и так отдаёт всё.

**Пагинация по `Link: rel="next"` с ограничением `MAX_PAGES = 10`.** Ограничение защищает от
замкнутой ссылки: без него сервер ходил бы в GitHub вечно, а пользователь не дождался бы
ответа. Сто репозиториев на страницу (верхняя граница GitHub) — предел, который инструмент
и не обещает превысить.

**Ошибка GitHub — результат вызова, а не исключение.** 401 («токен не принят»), 403 («нет прав
или исчерпан лимит»), прочие не-2xx (код и тело), сеть («сеть до GitHub недоступна»), нет
токена — всё это `CallToolResult(isError = true)` с причиной словами. Иначе исключение ушло бы
клиенту как отказ инструмента, которого он не вызывал, и до модели не дошло бы вовсе.

**Неизвестный `visibility` отвергается до обращения к API.** Ходить в сеть за тем, что всё
равно будет отфильтровано в пустоту, — это потраченный лимит запросов и ложное ощущение, что
аргумент принят. Отказ перечисляет допустимые значения, поэтому модель может исправиться.

## 4. Цикл вызова инструмента в агенте

Агент про инструменты не знает ничего, кроме их контракта: имя, описание, схема аргументов и
функция вызова (`AgentTool`). Ни MCP, ни процессов, ни сессий в `:agent` нет — иначе протокол
оказался бы внутри домена, и смена транспорта трогала бы агент.

Цикл в `LlmAgent.run`:

1. объявления инструментов уходят в запрос — **только если инструменты есть** (пустой список
   в теле запроса стоил бы токенов и менял поведение модели без причины);
2–4. модель просит вызовы → агент выполняет их и добавляет в переписку **сообщение ассистента
   с вызовами и ответ на каждый вызов** (`role = "tool"`, `tool_call_id`), после чего повторяет
   запрос. Пара «вызов — результат» обязательна: без сообщения ассистента API не примет ответ,
   без ответа модель повторит тот же вызов;
5. когда вызовов нет — приходит текст, и он отдаётся наверх.

Решения, которые здесь пришлось принять:

- **Раундов конечное число** (`AppConfig.MAX_TOOL_ROUNDS = 3`), после них инструменты больше
  не предлагаются. Модель может просить инструмент бесконечно («позови ещё раз, вдруг
  получится»), и без предела запрос пользователя кончился бы не ответом, а расходом. Три, а не
  один: цель раунда может зависеть от результата предыдущего — сначала узнать, что доступно,
  потом попросить нужное.
- **Завершение не зависит от поведения модели.** Если вызов приходит в ответ на запрос без
  объявлений, он не выполняется, а работа кончается ответом модели (в логе — «раунды
  исчерпаны»). Иначе цикл зависел бы от чужого поведения и мог не кончиться вовсе.
- **Неизвестный инструмент и упавший инструмент — ответ модели, а не отказ запроса.** Причина
  уходит в переписку, и модель либо отвечает без данных, либо исправляет вызов. Так падение
  внешнего сервиса не отменяет ответ на вопрос, который от него не зависел.
- **Аргументы разбираются мягко**: пустая строка — «аргументов нет» (у инструмента есть
  умолчания), а неразобранная строка — отказ с причиной. Молча звать инструмент с пустыми
  аргументами значило бы отдать модели выдумку инструмента вместо данных.
- **Переполнение окна проверяется перед каждым раундом**, а не только перед первым: ответы
  инструментов удлиняют переписку, и переполниться она может уже после первого обмена.
- **Расход суммируется по раундам** (`promptTokens`/`replyTokens` — суммы, `tokens.tools.tokens`
  — все раунды кроме первого), иначе отчёт показывал бы расход меньше настоящего: каждый вызов
  инструмента — это ещё один полный запрос со всей перепиской.
- **Отмена не превращается в ответ инструмента** (и отменённый запрос не продолжается ещё одним
  обращением к API), **`EmptyReplyException` — только для финального текста**: у раунда с
  вызовом текста нет по правилам протокола.

Один нюанс формата пришлось предусмотреть отдельно: у ответа с вызовами `content` приходит
`null`, и разбор падал бы ровно там, где начинается вызов инструмента. Поле `content` получило
умолчание, а клиентский разбор — `coerceInputValues = true` (`ChatMessage`, `Application.client`,
живой клиент демонстрации). Тип `type` в объявлении и в вызове помечен `EncodeDefault`: он
совпадает с умолчанием, но провайдер ждёт его всегда, и пропуск — отказ, а не экономия байтов.

## 5. Подключение к серверу приложения

`:server` получил зависимости `:mcp` (клиент протокола и адаптер) и `:mcp-github` (классы сервера
инструментов — они запускаются из своего же classpath).

`GitHubTools` держит **одну долгую сессию** на всё время работы сервера: MCP-сервер — отдельный
процесс на JVM, и поднимать его на каждый вопрос значило бы платить за запуск и рукопожатие в
каждом ответе. Инструменты запоминаются вместе с сессией, переспрашиваются только после
переподключения. Под замком — потому что запросы идут параллельно: без него два одновременных
вопроса подняли бы два процесса, и один остался бы сиротой.

**Недоступный сервер инструментов не отменяет ответ**: причина уходит в лог, вопрос идёт модели
без инструментов, а попытка повторяется на следующем запросе — обычно причина временная. Обратное
решение (считать ответ без инструментов недостоверным) превращало бы недоступность GitHub в
недоступность ассистента.

Сессия закрывается на `ApplicationStopped`: процесс сервера инструментов подняли мы, поэтому его
завершение — наша забота, иначе он пережил бы остановку приложения.

Ответ маршрута несёт отчёт об инструментах (`tokens.tools`: что вызывалось, сколько раундов,
сколько токенов), и он же виден в клиентском логе (`app/shared/.../ToolsReport.kt`) — рядом со
строками про память, задачу и инварианты.

## 6. Что отброшено

- **Отдельный модуль под общий код серверов** вместо выноса в `:mcp`: общий код — это объявление
  инструмента и запуск на stdio, и они уже лежат в `:mcp`; ещё один модуль добавил бы слой без
  потребителя.
- **Инструмент GitHub внутри `:mcp`**: у него появляется `GITHUB_TOKEN`, которого у сервера
  проекта нет вовсе, и своя сеть — в общем модуле это была бы одна точка входа с чужими
  настройками.
- **Копия fat-JAR сборки во втором модуле** — она привела бы к двум правкам одной механики;
  вынесена в отдельную задачу `fatJar` в обоих модулях (§4 в README, `### task-17`).
- **Клиент MCP в `:agent`**: инструменты в агент приходят контрактом, а протокол остаётся
  снаружи; зависимость направлена `:mcp` → `:agent`.
- **Токен в конфиге сервера приложения**: токен уезжает серверу инструментов окружением
  процесса, сам сервер приложения его не читает — значит, не может попасть ни в лог, ни в ответ.
- **Вызов инструментов на стороне клиента** (в `app/shared`): решение о вызове принимает модель,
  и принимать его в клиенте значило бы повторить логику агента в UI.
- **Инструменты как подсказка в промпте** (заранее вложить репозитории в запрос): это и есть то,
  что заменяет MCP, — данные ехали бы в каждом запросе, даже когда не нужны, и устаревали бы.

API подставляется переменной `GITHUB_API_BASE`). Инструмент на каждом этапе обёрнут записью

## 9. Что осталось непроверенным

- **Живой GitHub.** Токена GitHub в окружении нет и `gh` не установлен, поэтому настоящий
  `https://api.github.com` не вызывался ни разу: проверено на подставном API тем же кодом
  (адрес — параметр). Не проверены, соответственно, настоящие лимиты запросов, ответ 403 с
  заголовком `X-RateLimit-*` и пагинация на живом `Link`.
- **Живой сервер приложения (`:server:run`).** На момент первой части дня порт 8080 занимал наш
  же устаревший процесс, поднимать сервер было негде; поэтому демонстрация гоняла тот же
  `GitHubTools` напрямую, а не через HTTP-маршрут. Теперь сервер поднят из текущего кода и
  маршруты проверены живьём (§16): непроверенным остаётся только окружение вокруг — HTTPS, прокси
  и внешний клиент перед сервером.
- **Экран приложения.** Проверен на эмуляторе (§16): подключение и отключение кнопкой, список
  инструментов, ручной вызов, вызов инструмента моделью, переживание перезапуска. На физическом
  устройстве и на iOS приложение не запускалось; JS- и wasm-таргеты `app/shared` не собираются
  (`Unresolved reference 'System'` — ограничение записано ещё в `docs/task-16-mcp.md`), поэтому
  браузер как способ посмотреть интерфейс недоступен.
- **Поведение модели при большем числе инструментов.** Живьём проверены три просьбы и один отказ;
  выбор между двумя и более инструментами (сервер проекта + сервер GitHub одновременно) не
  проверялся: сегодня сервер приложения подключает только инструменты GitHub.

## 10. Вторая часть дня: соединение по кнопке и вызовы инструментов в чате

Первая часть дня довела инструменты GitHub до модели, но подключение было невидимым: сессию
поднимал первый же запрос к модели, а из интерфейса не было видно ни того, что GitHub подключён,
ни того, какие инструменты доступны, ни чем они отвечают. Отчёт о вызовах уезжал строкой в
клиентский лог. Задание требует большего: **соединение с GitHub устанавливает человек кнопкой,
интерфейс предлагает набор инструментов, а команда инструмента печатается в чате и исполняется**.

| Требование | Где сделано | Чем подтверждается |
| --- | --- | --- |
| Кнопка устанавливает соединение | `GitHubSheet.kt` («Подключить»), `POST /v1/github/connect`, `GitHubTools.connect` | §16: живое подключение из шторки, `connected=true` в `GET /v1/github` |
| Соединение видно и его можно разорвать | `GET /v1/github`, `POST /v1/github/disconnect`, `GitHubSheet` («Отключить») | §16: состояние, имя и версия сервера, отключение кнопкой |
| Интерфейс предлагает набор инструментов | `GitHubTool`, `GitHubToolArgument` в контракте; `GitHubToolSection` в шторке | §16: `get_repositories` с описанием, типом, обязательностью и значениями `visibility` |
| Команда инструмента печатается в чате | `ToolCallRecord` (аргументы вызова), `ChatMessage.tools`, `ToolCallCard` | §16: карточки `get_repositories {}` и `get_repositories {"visibility": "private"}` в ленте |
| Команда исполняется | `POST /v1/github/call` (ручной путь), маршрут чата с `tools` (агентский путь) | `GitHubRoutesTest`, `GitHubToolsClientTest`, §16 |

## 11. Контракт HTTP сервера приложения

Четыре маршрута, все — состояния одного соединения, а не CRUD по инструментам:

| Маршрут | Ответ | Смысл |
| --- | --- | --- |
| `GET /v1/github` | `GitHubConnection` | снимок: подключено ли, кто ответил, какие инструменты |
| `POST /v1/github/connect` | `GitHubConnection` (200) / `ErrorResponse` (502) | подключение; тело — `GitHubConnectRequest(token?)` |
| `POST /v1/github/disconnect` | `GitHubConnection` (200) | отключение; тела нет и не читается |
| `POST /v1/github/call` | `GitHubCallResponse` (200) / 404 / 409 | прямой вызов инструмента человеком |

**Коды ответа различают три разных положения дел** (решение `GitHubCall` в §12): инструмент
ответил — 200, даже если ответил отказом (`failed=true`: вызов состоялся, инструмент словами
сказал, почему данных нет); инструмента с таким именем сервер не объявлял — 404; соединения нет
— 409. Отдать все три одним кодом значило бы заставить интерфейс разбирать текст причины, чтобы
понять, показывать ли кнопку «Подключить».

**Поля с умолчаниями помечены `@EncodeDefault`.** Глобальная настройка Json у Ktor пишет только
не-умолчания, поэтому «не подключено» уехало бы как `{}` без `connected`, пустой список
инструментов исчез бы вовсе, а клиент читает контракт по именам полей. Это исключение
(`GitHubModels.kt`) сделано точечно на полях контракта, а не глобально: в остальном проекте
экономия умолчаний желательна, и менять её ради одного ответа значило бы менять формат всем.

## 12. Соединение поднимает человек: устройство сервера

`GitHubTools` из первой части дня знал одно действие — «дай инструменты». Теперь их пять
(`connection`, `connect`, `disconnect`, `tools`, `call`), и все под одним `Mutex`: запросы к
серверу идут параллельно, а снимок, попавший между закрытием и подъёмом сессии, показал бы
половину одного и половину другого.

**Ленивого подключения больше нет: без сессии `tools()` отдаёт пустой список.** Решение выглядит
шагом назад (раньше первый вопрос сам поднимал процесс), но именно оно делает состояние видимым:
при ленивом подключении «GitHub подключён» — это скрытое следствие того, что кто-то однажды
спросил модель, и человек не может отличить «инструментов нет» от «ещё не подключались».
Одновременно уходит и вторая неявность: чужой процесс больше не запускается за спиной у
человека — его запускает кнопка. Плата — подключение перестало быть бесплатным для того, кто
забыл нажать кнопку; потому в ответе 409 и в шторке прямо сказано, что делать.

**Подключение возвращает не исключение, а `GitHubConnect`**: `Connected` со снимком или
`Rejected` с причиной. Причину показывает шторка, и падать из-за неё запрос не должен — по той же
логике, по которой недоступный GitHub не отменяет ответ чата (первая часть дня). Маршрут
превращает `Rejected` в 502: сервер инструментов — вышестоящий сервис, и «не удалось
подключиться» — это именно ошибка шлюза, а не ошибка запроса клиента.

**Рукопожатие и списки — до записи в поля.** `listTools()` и `agentTools()` вызываются на ещё не
сохранённой сессии; если любая из выборок падает, поднятый процесс гасится, а поля остаются
пустыми. Запись в `session` последней строкой — это и есть защита от сироты: `session` не может
стать «подключённой» без процесса, потому что список инструментов не пришёл. Тот же порядок
закрывает и вторую дыру: переподключение после смерти процесса сначала закрывает мёртвую сессию
(`closeSession()`), иначе транспорт копился бы на каждое переподключение.

**Отмена перебрасывается, а не превращается в отказ.** `CancellationException` — это оборванный
запрос пользователя, а не «GitHub недоступен»; записать его в состояние значило бы показывать
человеку отказ сервиса, которого не было. Отдельно поэтому же `closeSession()` перебрасывает
отмену, а прочие сбои закрытия уводит в лог: сбой транспорта не значит, что сессия жива, и
нажатие «Отключить» не должно возвращать 500 при фактически закрытом соединении.

**Инструменты кэшируются двумя формами:** `declared: List<McpTool>` для снимка и
`modelTools: List<AgentTool>` для вызовов. Из `McpTool` уезжают типы, обязательность и
допустимые значения аргументов — их печатает шторка; в `AgentTool` этих полей нет, зато его
`call` уже связан с живой сессией. Держать одну форму и выводить вторую значило бы либо звать
`listTools()` на каждый снимок, либо терять подробности схемы в интерфейсе.

**Прямой вызов идёт тем же кодом, что вызов моделью**: `call(name, arguments)` ищет инструмент
среди объявленных и зовёт его `call`. Отдельного пути «для кнопки» нет намеренно — иначе ручной
вызов и вызов моделью разошлись бы в проверке аргументов и в обработке ошибок, и расхождение
нашлось бы на первом же инструменте со схемой.

**`fun Application.module(githubTools: GitHubTools = GitHubTools())`** — параметр вместо
глобального `val githubTools`, который был в первой части. Это шов для проверки маршрутов на
настоящем MCP-процессе (`GitHubRoutesTest` подставляет свой `GitHubTools` с подставным GitHub) и
заодно убирает изменяемое глобальное состояние: маршрут чата получает те же инструменты
(`.copy(tools = githubTools.tools())`), что и шторка, поэтому «в чате одни инструменты, в шторке
другие» невозможно по построению.

## 13. Клиент: шторка, карточка вызова и служебная роль

**Кнопка «GitHub» — в той же шапке, что «Память», «Инварианты» и «Профиль»** (`ChatTopBar`):
подключение инструментов — настройка агента, а не действие чата, и отдельное место в интерфейсе
заставило бы искать её отдельно. Подпись короткая намеренно: действий в шапке уже четыре, и
«Инструменты GitHub» выдавили бы заголовок чата, ради которого шапка и нужна.

**У шторки нет своего состояния подключения** (`GitHubSheet`): снимок приходит с сервера через
`GitHubRepository.github`, и после подключения, отключения и вызова видно то, что ответил сервер.
Копия состояния на клиенте расходилась бы с сервером после первого же вызова с другой стороны
(например, после вопроса в чате, где сессия могла умереть) — поэтому после ответа на сообщение
клиент заново спрашивает `GET /v1/github`.

**Токен — обычное `remember`, а не `rememberSaveable`, и не уходит в состояние экрана.** Секрету
незачем переживать пересоздание экрана, а после подключения он не нужен вовсе: дальше соединение
живёт на сервере. Пустое поле — не ошибка, а выбор сервера (взять `GITHUB_TOKEN` из своего
окружения): вторую ветку «нет токена» на клиенте не пишут именно потому, что токен берёт сервер,
и выдумывать его поведение на клиенте значило бы разойтись с ним.

**Аргументы вводятся строкой JSON, а не полями по одному.** Так вызов выглядит ровно так, как его
присылает модель, и не нужны ни подстановка значений с проверкой типа, ни второй разбор схемы на
клиенте. Поле одно на инструмент с ключом по имени: список инструментов переспрашивается при
переподключении, и без ключа набранная строка переехала бы на чужой инструмент. Подсказка к полю
собирается из объявления самого инструмента, а не пишется литералом: литерал рано или поздно
назвал бы поле, которого у инструмента нет, и человек набирал бы по подсказке заведомо неверный
вызов.

**Вызов инструмента печатается карточкой в ленте** (`ToolCallCard`). Карточка одна на два места —
под ответом ассистента и вместо пузыря ответа инструмента: это один и тот же след работы, и
вторая отрисовка разошлась бы с первой на первой же правке формата. Команда печатается
моноширинно, потому что это имя и аргументы вызова, а не речь.

**Роль `MessageRole.TOOL` — служебная запись, а не реплика.** У ответа инструмента текста нет
вовсе, поэтому пузырь на его месте был бы пустым: вместо пузыря печатается карточка, а сам текст
остаётся пустым. Из истории, уезжающей модели, записи `TOOL` отсеиваются
(`filter { it.role != MessageRole.TOOL }`): переписка для модели собирается из реплик человека и
ассистента, и вставленная в неё служебная запись читалась бы как реплика, которой не было, —
модель отвечала бы на собственный отчёт о вызове.

**Почему вызовы хранятся в сообщении, а не в отчёте на экране.** Вызов относится к конкретному
ответу, и после перезапуска приложения по нему видно, откуда взялись данные. Поэтому
`ChatMessage.tools: List<ToolCallRecord>`, а не список на экране: список на экране исчез бы при
пересоздании, а отчёт пришлось бы связывать с сообщением вручную.

**`ToolCallRecord` получил `arguments` и `result`** (`:agent`, и его клиентский двойник). До этого
лента не смогла бы напечатать команду: текст вызова жил только в логе сервера. `result` обрезается
тем же `forLog()` (2 000 символов), что и лог, — одна политика на лог и ленту, иначе на экране
оказался бы ответ длиннее, чем сервер согласен печатать; модели при этом уходит ответ целиком.
`command()` собирается из имени и аргументов, а пустые аргументы печатаются как `{}`: пустая
строка на месте команды читалась бы как «имя инструмента без вызова».

**Ошибка аргументов не уходит на сервер.** `callGitHubTool` разбирает строку в `JsonObject` до
запроса: пустая строка — пустой объект (у инструмента есть умолчания), неразобранная или не
объект — причина в `githubError` и запрос не отправляется. Отправить её серверу значило бы
получить 400 с разбором чужого формата вместо указания на конкретную опечатку.

## 14. Хранение: миграция Room 4 → 5

Вызовы лежат колонкой `toolCalls` (nullable TEXT) в `chat_messages`, а не отдельной таблицей:
вызовы принадлежат сообщению и читаются всегда вместе с ним, поэтому отдельная таблица добавила
бы соединение ради связи «один-ко-многим», у которой не бывает второго потребителя. Схема БД
поднята до версии 5 с `MIGRATION_4_5` (`ALTER TABLE chat_messages ADD COLUMN toolCalls TEXT`):
умолчания колонки нет намеренно — «нет вызовов» и «вызовы ещё не читали» различать незачем, а
разбор `null` даёт пустой список. Сериализация — тот же kotlinx-json, что и в остальном
проекте; в `androidApp` он добавлен явной зависимостью (`app/shared` отдаёт его как
`implementation`), иначе JSON-колонка просто не компилируется.

## 15. Что отброшено (вторая часть дня)

- **Ленивое подключение на первом запросе** (как было в первой части): «подключено» стало бы
  невидимым состоянием, а процесс — запускаться за спиной у человека (§12).
- **Типизированные поля аргументов в шторке** (по одному полю на аргумент с выбором значений):
  потребовало бы разбора JSON-схемы на клиенте и разошлось бы с сервером на первом же
  инструменте со вложенным объектом.
- **Отдельная таблица вызовов в Room**: соединение ради связи без второго потребителя (§14).
- **Записи `TOOL` в истории для модели**: служебная запись читалась бы как реплика, которой не
  было (§13).
- **Форма `GitHubToolArgument`, собранная на клиенте из схемы**: типы и значения уже приходят
  готовыми от сервера инструментов (§12).
- **Один код ответа на все отказы вызова** (404 и 409): интерфейс разбирал бы текст причины,
  чтобы понять, показывать ли кнопку «Подключить» (§11).
- **Хранение токена на устройстве** (в настройках или `rememberSaveable`): токен нужен один раз,
  на подключении, и его хранение было бы единственной причиной, по которой он может утечь (§13).
- **Автоподключение при старте приложения**: сервер приложения поднимают и без GitHub, а
  поднимать чужой процесс на старте значило бы платить за него всегда и падать на его ошибке
  тогда, когда GitHub не нужен.
