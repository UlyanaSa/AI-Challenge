# День 17. MCP-сервер для GitHub и вызов инструмента агентом — устройство

День 16 подключил агента к MCP и показал список инструментов. День 17 доводит это до работы:
появляется второй MCP-сервер (он ходит в GitHub REST API), а **агент сам** вызывает инструмент,
когда этого требует обычная просьба, и отвечает по его данным.

## 2. Что установлено и что из этого следует

Новый модуль `:mcp-github`. Отдельный, а не инструмент внутри `:mcp`: у сервера проекта данные —
правила и профиль, у сервера GitHub — сеть и токен, и в одном модуле они получили бы один fat
JAR и одну точку входа. Общая часть (объявление инструмента, сборка сервера, режимы запуска на
stdio) при этом не скопирована: она вынесена в `:mcp` (`DeclaredTool.kt`, `StdioServer.kt`), и
второй сервер ею пользуется. Копия разошлась бы с первой на первой же правке запуска.

Ktor-клиент — только `ktor-client-core` + `ktor-client-cio`: серверный движок (Netty) не нужен,
сервер общается с клиентом по stdio, а наружу сам ходит как клиент.

## 3. Сервер GitHub: где границы

**Токен читается в момент вызова, а не при старте.** Сервер поднимают и для `--list-tools`,
где GitHub не нужен; падать из-за отсутствия переменной окружения на старте значило бы
запрещать знакомство с инструментом до настройки. Поэтому `GitHubConfig.requireToken()`
бросает `GitHubApiException` с готовым текстом, а инструмент превращает её в `isError`
одним местом. Возврат `null` вместо исключения означал бы проверку на каждом шаге — и рано
или поздно забытую.

**Адрес API — параметр, а не константа** (`GITHUB_API_BASE`, по умолчанию
`https://api.github.com`). Это не «гибкость на будущее»: токена GitHub в окружении этого
проекта нет, поэтому проверка идёт на подставном API на localhost, и адрес должен быть
подменяемым. Код-путь при этом тот же, что с настоящим GitHub.

**Модель отделена от ответа GitHub.** Публичный `GitHubRepository` — с именами полей из
задания (`fullName`, `url`), а `GitHubRepositoryResponse` (internal) разбирает ответ GitHub
(`full_name`, `html_url`) и превращается в модель. Если повесить `@SerialName` на саму модель,
её собственный JSON-вывод уехал бы модели-потребителю с именами GitHub, а не с обещанными:
одна аннотация обслуживала бы два разных формата.

**Видимость берётся из `visibility`, а если поля нет — из `private`.** GitHub отвечает
`visibility` не во всех случаях (старые ответы, отдельные маршруты), а `private` есть всегда.
Фильтровать по флагу `private` в обход видимости не стали: тогда третья видимость GitHub
(`internal`) попала бы в «приватные», хотя инструмент обещает только публичные и приватные,
а `all` и так отдаёт всё.

**Пагинация по `Link: rel="next"` с ограничением `MAX_PAGES = 10`.** Ограничение защищает от
замкнутой ссылки: без него сервер ходил бы в GitHub вечно, а пользователь не дождался бы
ответа. Сто репозиториев на страницу (верхняя граница GitHub) — предел, который инструмент
и не обещает превысить.

**Ошибка GitHub — результат вызова, а не исключение.** 401 («токен не принят»), 403 («нет прав
или исчерпан лимит»), прочие не-2xx (код и тело), сеть («сеть до GitHub недоступна»), нет
токена — всё это `CallToolResult(isError = true)` с причиной словами. Иначе исключение ушло бы
клиенту как отказ инструмента, которого он не вызывал, и до модели не дошло бы вовсе.

**Неизвестный `visibility` отвергается до обращения к API.** Ходить в сеть за тем, что всё
равно будет отфильтровано в пустоту, — это потраченный лимит запросов и ложное ощущение, что
аргумент принят. Отказ перечисляет допустимые значения, поэтому модель может исправиться.

## 4. Цикл вызова инструмента в агенте

Агент про инструменты не знает ничего, кроме их контракта: имя, описание, схема аргументов и
функция вызова (`AgentTool`). Ни MCP, ни процессов, ни сессий в `:agent` нет — иначе протокол
оказался бы внутри домена, и смена транспорта трогала бы агент.

Цикл в `LlmAgent.run`:

1. объявления инструментов уходят в запрос — **только если инструменты есть** (пустой список
   в теле запроса стоил бы токенов и менял поведение модели без причины);
2–4. модель просит вызовы → агент выполняет их и добавляет в переписку **сообщение ассистента
   с вызовами и ответ на каждый вызов** (`role = "tool"`, `tool_call_id`), после чего повторяет
   запрос. Пара «вызов — результат» обязательна: без сообщения ассистента API не примет ответ,
   без ответа модель повторит тот же вызов;
5. когда вызовов нет — приходит текст, и он отдаётся наверх.

Решения, которые здесь пришлось принять:

- **Раундов конечное число** (`AppConfig.MAX_TOOL_ROUNDS = 3`), после них инструменты больше
  не предлагаются. Модель может просить инструмент бесконечно («позови ещё раз, вдруг
  получится»), и без предела запрос пользователя кончился бы не ответом, а расходом. Три, а не
  один: цель раунда может зависеть от результата предыдущего — сначала узнать, что доступно,
  потом попросить нужное.
- **Завершение не зависит от поведения модели.** Если вызов приходит в ответ на запрос без
  объявлений, он не выполняется, а работа кончается ответом модели (в логе — «раунды
  исчерпаны»). Иначе цикл зависел бы от чужого поведения и мог не кончиться вовсе.
- **Неизвестный инструмент и упавший инструмент — ответ модели, а не отказ запроса.** Причина
  уходит в переписку, и модель либо отвечает без данных, либо исправляет вызов. Так падение
  внешнего сервиса не отменяет ответ на вопрос, который от него не зависел.
- **Аргументы разбираются мягко**: пустая строка — «аргументов нет» (у инструмента есть
  умолчания), а неразобранная строка — отказ с причиной. Молча звать инструмент с пустыми
  аргументами значило бы отдать модели выдумку инструмента вместо данных.
- **Переполнение окна проверяется перед каждым раундом**, а не только перед первым: ответы
  инструментов удлиняют переписку, и переполниться она может уже после первого обмена.
- **Расход суммируется по раундам** (`promptTokens`/`replyTokens` — суммы, `tokens.tools.tokens`
  — все раунды кроме первого), иначе отчёт показывал бы расход меньше настоящего: каждый вызов
  инструмента — это ещё один полный запрос со всей перепиской.
- **Отмена не превращается в ответ инструмента** (и отменённый запрос не продолжается ещё одним
  обращением к API), **`EmptyReplyException` — только для финального текста**: у раунда с
  вызовом текста нет по правилам протокола.

Один нюанс формата пришлось предусмотреть отдельно: у ответа с вызовами `content` приходит
`null`, и разбор падал бы ровно там, где начинается вызов инструмента. Поле `content` получило
умолчание, а клиентский разбор — `coerceInputValues = true` (`ChatMessage`, `Application.client`,
живой клиент демонстрации). Тип `type` в объявлении и в вызове помечен `EncodeDefault`: он
совпадает с умолчанием, но провайдер ждёт его всегда, и пропуск — отказ, а не экономия байтов.

## 5. Подключение к серверу приложения

`:server` получил зависимости `:mcp` (клиент протокола и адаптер) и `:mcp-github` (классы сервера
инструментов — они запускаются из своего же classpath).

`GitHubTools` держит **одну долгую сессию** на всё время работы сервера: MCP-сервер — отдельный
процесс на JVM, и поднимать его на каждый вопрос значило бы платить за запуск и рукопожатие в
каждом ответе. Инструменты запоминаются вместе с сессией, переспрашиваются только после
переподключения. Под замком — потому что запросы идут параллельно: без него два одновременных
вопроса подняли бы два процесса, и один остался бы сиротой.

**Недоступный сервер инструментов не отменяет ответ**: причина уходит в лог, вопрос идёт модели
без инструментов, а попытка повторяется на следующем запросе — обычно причина временная. Обратное
решение (считать ответ без инструментов недостоверным) превращало бы недоступность GitHub в
недоступность ассистента.

Сессия закрывается на `ApplicationStopped`: процесс сервера инструментов подняли мы, поэтому его
завершение — наша забота, иначе он пережил бы остановку приложения.

Ответ маршрута несёт отчёт об инструментах (`tokens.tools`: что вызывалось, сколько раундов,
сколько токенов), и он же виден в клиентском логе (`app/shared/.../ToolsReport.kt`) — рядом со
строками про память, задачу и инварианты.

## 6. Что отброшено

- **Отдельный модуль под общий код серверов** вместо выноса в `:mcp`: общий код — это объявление
  инструмента и запуск на stdio, и они уже лежат в `:mcp`; ещё один модуль добавил бы слой без
  потребителя.
- **Инструмент GitHub внутри `:mcp`**: у него появляется `GITHUB_TOKEN`, которого у сервера
  проекта нет вовсе, и своя сеть — в общем модуле это была бы одна точка входа с чужими
  настройками.
- **Копия fat-JAR сборки во втором модуле** — она привела бы к двум правкам одной механики;
  вынесена в отдельную задачу `fatJar` в обоих модулях (§4 в README, `### task-17`).
- **Клиент MCP в `:agent`**: инструменты в агент приходят контрактом, а протокол остаётся
  снаружи; зависимость направлена `:mcp` → `:agent`.
- **Токен в конфиге сервера приложения**: токен уезжает серверу инструментов окружением
  процесса, сам сервер приложения его не читает — значит, не может попасть ни в лог, ни в ответ.
- **Вызов инструментов на стороне клиента** (в `app/shared`): решение о вызове принимает модель,
  и принимать его в клиенте значило бы повторить логику агента в UI.
- **Инструменты как подсказка в промпте** (заранее вложить репозитории в запрос): это и есть то,
  что заменяет MCP, — данные ехали бы в каждом запросе, даже когда не нужны, и устаревали бы.

## 9. Что осталось непроверенным

- **Живой GitHub.** Токена GitHub в окружении нет и `gh` не установлен, поэтому настоящий
  `https://api.github.com` не вызывался ни разу: проверено на подставном API тем же кодом
  (адрес — параметр). Не проверены, соответственно, настоящие лимиты запросов, ответ 403 с
  заголовком `X-RateLimit-*` и пагинация на живом `Link`.
- **Живой сервер приложения (`:server:run`).** Порт 8080 занят чужим процессом, поднимать
  сервер негде; поэтому демонстрация гоняет тот же `GitHubTools` напрямую, а не через HTTP-маршрут.
  Маршрут отличается от демонстрации двумя строками (передача инструментов в `AgentOptions` и
  закрытие на остановке) и покрыт компиляцией и `:server:test`.
- **Экран приложения.** Инструменты в клиентском логе (`ToolsReport`) показаны строкой отчёта;
  на устройстве экран не проверялся (эмулятор не запускался) — проверка ограничена host-тестами
  `app/shared` и сборкой APK.
- **Поведение модели при большем числе инструментов.** Живьём проверены три просьбы и один отказ;
  выбор между двумя и более инструментами (сервер проекта + сервер GitHub одновременно) не
  проверялся: сегодня сервер приложения подключает только инструменты GitHub.
