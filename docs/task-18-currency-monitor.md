# День 18. Сервис мониторинга курсов валют — устройство

Сервис ходит за курсами евро, доллара и лари к рублю, складывает историю в SQLite, отдаёт
её MCP-инструментами и живёт на VPS обычным `java -jar`. Вторая часть той же задачи —
закреплённый чат в приложении: он раз в минуту печатает текущие курсы, а при открытии
показывает изменение за сутки, собранное из сохранённых часовых сводок (§17–§21). Ниже —
что решили, почему именно так и чем это проверено.

## 1. Что просит задание и чем это подтверждается

| Пункт задания (§17) | Чем закрыт |
|---|---|
| 1. Backend запущен на VPS | Развёрнут на виртуальной машине провайдера и работает службой systemd: автозапуск при загрузке, история на диске, сбор с настоящего ЦБ по расписанию (§12) |
| 2. Планировщик независимо от клиента | Сбор идёт циклом по расписанию, а не по вызову инструмента; служба без аргументов не выходит по концу ввода (`Application.kt`). Проверено на живом процессе: обновления шли до подключения клиента |
| 3. Раз в час EUR/RUB, USD/RUB, GEL/RUB | `CurrencyScheduler` собирает по интервалу из `CURRENCY_INTERVAL` (по умолчанию минута — её требует закреплённый чат, §18; дневному источнику хватает `PT1H`, §12); один обход дал три курса и три строки в истории. Периодичность проверена тестами с подменными часами (`CurrencySchedulerTest`) |
| 4. Значения сохраняются в SQLite | `SqliteCurrencyRateRepository`, таблица `currency_rates`; проверено и прогоном, и разбором файла базы снаружи |
| 5. История курсов сохраняется | Строка на каждое обновление, без перезаписи прежних; несколько прогонов подряд дали растущую историю с разными значениями |
| 6. Агрегация минимум за 24 часа | `CurrencySummaryService`: `DAY` = 24 часа, плюс `WEEK` и `MONTH` — величины из задания, а не «на будущее» |
| 7. MCP предоставляет `get_currency_rates` | Инструмент объявлен и отвечает; проверено кадром протокола и агентом |
| 8. MCP предоставляет `get_currency_summary` | Инструмент объявлен с обязательным `period` (`DAY`/`WEEK`/`MONTH`); проверено кадром протокола и агентом |
| 9. Агент вызывает MCP-инструмент | Живой прогон: модель запросила `get_currency_summary`, затем `get_currency_rates`, получила результаты и ответила по ним |
| 10. Агент отвечает по накопленным данным | В ответе агента числа, которых нет ни в его знаниях, ни в вопросе: их отдал подставной источник в базу, а базу прочитал инструмент |

## 2. Что установлено до проектирования

Курсы к рублю нужны от источника, который отдаёт их без ключа и без регистрации. Проверено
живьём: ЦБ РФ (`https://www.cbr-xml-daily.ru/daily_json.js`) отдаёт за раз весь файл курсов,
в нём `Valute.EUR.Value = 95.8709`, `USD = 84.3414`, `GEL = 32.1693` — по одной единице валюты.
Frankfurter для рубля JSON не отдаёт вовсе, `open.er-api.com` — обратные курсы (рублей за
доллар он не считает), поэтому источник один — ЦБ.

Из этого следуют два факта, которые определили устройство:

- **Курс ЦБ — дневной.** За час двух разных значений от него не получить. Значит, история из
  одинаковых значений — нормальное состояние сервиса, а не признак поломки, и «изменение»
  в сводке нельзя считать как «разница с точкой час назад» (см. §8).
- **ЦБ называет курс за `Nominal` единиц** (для евро, доллара и лари — за одну, для иены —
  за сто). Номинал учитывается в разборе, иначе один и тот же рублёвый курс значил бы разное
  для разных валют.

## 3. Границы: почему отдельный модуль

`:currency-monitor` — третий модуль MCP рядом с `:mcp` (общая часть) и `:mcp-github`. Отдельный
потому, что у сервиса курсов своё время жизни и своя команда запуска: его поднимают на VPS
службой и он живёт там между подключениями клиентов, тогда как `:mcp-github` бесполезен без
аккаунта и запускается вокруг вызова. Общая часть — объявления инструментов и stdio-цикл —
берётся из `:mcp` (`DeclaredTool.kt`, `StdioServer.kt`), как у сервера GitHub: объявление одно
и на регистрацию, и на консольный список, и на схему для клиента, поэтому «показал одно,
объявил другое» невозможно по построению. Границы `:mcp-github` тоже не двигались: два чужих
источника данных (аккаунт GitHub и курсы ЦБ) в одном модуле получили бы один fat JAR и одну
точку входа с чужой настройкой.

Пакеты внутри модуля повторяют слои задания (`currency/`, `scheduler/`, `storage/`, `remote/`,
`summary/`, `mcp/`), чтобы схема из §17 читалась по дереву файлов.

## 4. Поток данных

```text
Currency API (ЦБ)
      ↑  каждый час
 CurrencyScheduler ──→ CurrencyService ──→ CurrencyRateRepository ──→ SQLite
                                              ↑
                                    CurrencySummaryService
                                              ↑
                                     MCP Server (stdio)
                                              ↑
                                            Agent
                                              ↑
                                            User
```

Обновление идёт сверху вниз: планировщик будит службу, та спрашивает провайдера, проверяет
и кладёт в историю. Чтение идёт снизу вверх: инструмент зовёт службу (последние курсы) или
сервис сводки (агрегация), и те читают ту же историю. Обе стороны сходятся на репозитории,
поэтому «сбор» и «чтение» не могут разойтись в понимании данных: и то и другое проходит
через одни и те же методы хранилища.

## 5. Хранение: одна таблица, текст, UTC

```sql
CREATE TABLE currency_rates (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    currency TEXT NOT NULL,
    rate_to_rub TEXT NOT NULL,
    received_at TEXT NOT NULL
);
CREATE INDEX idx_currency_rates_currency_received_at
    ON currency_rates (currency, received_at);
```

- **Курс — текстом.** `TEXT` для `rate_to_rub` — не небрежность: колонка `REAL` вернула бы
  95.8709 уже другим числом (двоичная дробь), а курс — деньги; текст хранит ровно то, что
  пришло, и читается обратно в `BigDecimal` без потерь. Масштаб — 6 знаков (`HALF_UP`), поэтому
  значения в базе одной длины и сравнить запись с расчётной можно без сюрпризов.
- **Момент — ISO-8601 UTC с секундной точностью.** `received_at` пишется как
  `2026-09-28T08:52:32Z` (`Instant.truncatedTo(SECONDS)`): доли секунды в текстовом виде
  сломали бы главное — порядок строк как текста становился бы не тем же, что порядок
  по времени (`…32.9Z` сортировалось бы после `…32.10Z`). Округление до секунды убирает
  и случайные различия внутри одного обновления, и разнобой в разборе диапазонов.
- **Строчка на каждое обновление, без дедупликации.** Так требует §7 задания: «история»
  означает, что каждая полученная величина остаётся. Соблазн писать только изменения
  («столько же — не пишем») отброшен: тогда «за сутки данных нет» и «за сутки курс не менялся»
  выглядели бы одинаково — пустотой, — а различить их нельзя по определению. Плата — при
  дневном курсе ЦБ в истории стоят одинаковые значения за соседние часы; сводка это переживает
  (см. §8).
- **Одно обновление — одна транзакция.** Три курса одного обхода попадают в базу вместе или
  не попадают вовсе: половина обновления в истории выглядела бы как курс, полученный
  в другую дату, — момент у всех строк общий, и это часть смысла записи.
- **Прагмы и один писатель.** `journal_mode=WAL` и `busy_timeout=5000` задаются при открытии:
  файл истории открывают и снаружи (посмотреть `sqlite3`), а короткая блокировка чтением не
  должна превращаться в отказ записи. Методы хранилища `synchronized` — соединение JDBC одно,
  а обращения к нему приходят и от планировщика, и от инструментов на разных корутинах.
  Соединение ленивое: сервис поднимают и в режиме `--list-tools`, где база не нужна, и создавать
  файл истории ради списка объявлений не стоит.
- **JDBC, а не Room и не ORM.** Таблица одна, запросов три (`save`, `latest`, `previous`,
  `between`), а Room — Android-библиотека с обработкой аннотаций на этапе сборки: в JVM-модуле
  без Android-плагина её нет. ORM над одной таблицей добавил бы слой перевода в SQL и обратно
  без единого вопроса, на который он бы отвечал.

## 6. Источник: разбор без `Double`

- **Ответ ЦБ разбирается вручную** (`JsonPrimitive.content` → `BigDecimal`), а не через
  `@Serializable`-DTO: готового сериализатора `BigDecimal` в kotlinx.serialization нет, объявить
  десятичное поле нечем, а `Double` испортил бы значение.
- **Номинал учитывается делением** `Value / Nominal` с масштабом 6. Незнакомые валюты ответа
  игнорируются: сервис собирает те три, что просило задание, и не падает от новых ключей
  в чужом файле. Отсутствие отслеживаемой валюты в ответе — не ошибка, а пустое место: служба
  записывает то, что пришло, а чего не хватило, видно вызывающему.
- **Момент получения берётся из часов сервиса**, а не из даты публикации ЦБ: история отвечает
  на вопрос «когда сервис это узнал», а дата публикации — «на когда курс назначен». Смешать
  их в одной колонке значило бы потерять ответ на первый вопрос. Часы — параметр, поэтому
  проверка разбора не зависит от текущего времени.
- **Сеть, не-2xx, неразобранный ответ — разные тексты отказа**, все — `CurrencyRateException`
  значением наружу: по тексту видно, чинить связь, ждать или смотреть формат. Тело ответа
  в текст ошибки не попадает — там может лежать чужая страница.
- **HTTP-клиент — параметр** (`MockEngine` в проверках, CIO в работе), и закрывает его тот,
  кто создал: иначе закрытие провайдера утащило бы чужой клиент.

## 7. Планировщик

Первое обновление делается **немедленно**, дальше пауза `interval` после окончания предыдущего.
Ждать час до первой записи значило бы, что `get_currency_rates` всё это время отвечает «история
пуста», а службу запускают ради данных сейчас. Пауза отсчитывается от конца обновления, а не
по границе часа: у поставщика свои часы публикации, и выравнивание по ним связало бы расписание
с моментом запуска процесса, ничего не давая взамен.

Цикл обёрнут в `try/catch` не потому, что служба бросает (она возвращает отказ значением),
а потому, что он обязан пережить то, чего от неё не ждут: сбой хранилища, ошибку разбора,
ошибку в самом планировщике. Упавший цикл молча прекратил бы сбор, и заметно это стало бы
только по устаревшей истории. `CancellationException` при этом пробрасывается: проглотить
отмену — значит оставить корутину жить после `cancel()`. Своих потоков и `Thread.sleep` нет —
ожидание на `delay` отменяется сразу.

**Интервал по умолчанию — минута** (`CurrencyConfig.DEFAULT_INTERVAL`): закреплённый чат
показывает движение курса по минутам (§20), а при часовом сборе лента из одинаковых значений
не отвечала бы на вопрос, что с курсом сейчас. Плата названа прямо: минутный сбор — это до 1440
обращений к источнику в сутки, тогда как ЦБ обновляет курс раз в день и различий между двумя
соседними минутами в его ответе нет. Поэтому тот же интервал вынесен в настройку
(`CURRENCY_INTERVAL`), а рядом в unit-файле написано, что вежливее к чужому источнику поставить
`PT1H` (§12): интервал выбирает тот, кто знает, как часто обновляется источник.

**После каждого состоявшегося обновления планировщик закрывает прошедший час сводкой** (§18).
Расписание сбора и расписание сводок — одно и то же: развести их по разным циклам значило бы
иметь два мнения о том, когда час кончился, и сводка иногда описывала бы час, по которому
сбор ещё шёл. Неудачное закрытие часа сбор не отменяет — следующее обновление попробует снова,
и `INSERT OR REPLACE` по ключу «час + валюта» не даст копий (§18).

## 8. Агрегация

`CurrencySummaryService` считает по окну `[сейчас − период, сейчас]`, обе границы входят
в него: курс, полученный ровно сутки назад, ещё принадлежит суткам.

- **«Предыдущий» курс берётся из истории целиком, а не из окна.** Иначе у службы, работающей
  вторые сутки, изменение за сутки всегда было бы неизвестным — точка «до окна» лежала бы
  за его границей, хотя она есть. Это же решение делает осмысленным `DAY` при дневном курсе ЦБ.
- **Масштаб ответа — 4 знака** (`HALF_UP`), меньше, чем в истории: сводка описывает период,
  а не повторяет записи. Масштаб и режим округления задаются явно — `divide` без них бросает
  `ArithmeticException` на непредставимой дроби, а `setScale` без режима падает на сужении;
  умолчания означали бы падение на живых данных.
- **Неопределённое — `null`, а не ноль.** Нет истории — нет `currentRate`, `minRate`, `maxRate`,
  `averageRate`; нет точки «до окна» или предыдущий курс нулевой — нет `change` и
  `changePercent` (делить на ноль нельзя, и «бесконечно много процентов» — не ответ).
  Ноль на месте неизвестного читался бы как «курс равен нулю».
- **Отказ хранилища не глотается**: у сводки нет разумного пустого ответа взамен истории, и
  недоступную историю нельзя выдавать за «период без данных». Инструмент показывает отказ.
- **Порядок валют — `Currency.entries`**, а не порядок ключей карты: ответ инструмента
  и объявление домена не должны разъезжаться.

## 9. Инструменты MCP

Инструменты — из `:mcp`-контракта `DeclaredTool`, поэтому регистрация, консольный список
и схема для клиента берутся из одного объявления. Их три, а имена объявлений — публичные
константы `CurrencyMcpServer.RATES_TOOL`, `SUMMARY_TOOL`, `CHANGE_TOOL`: те же имена называет
сервер приложения в своих маршрутах (§19), и литерал в двух местах разошёлся бы молча.

- `get_currency_rates` — без аргументов: последние сохранённые курсы и момент получения
  (`{"updatedAt": …, "rates": {"EUR": …, "USD": …, "GEL": …}}`). Пустая история — не отказ:
  приходит `updatedAt: null`, пустой `rates` и подсказка `note` о том, что данных ещё нет.
- `get_currency_summary` — обязательный `period` со значениями `DAY | WEEK | MONTH`
  (24 часа, 7 суток, 30 суток). Обязательный и с перечислением, а не со значением по умолчанию:
  «сводка за какой-то период» не отвечает на вопрос, умалчивание периода читалось бы как
  «за сутки» там, где человек имел в виду месяц, а перечисление в схеме не даёт модели выдумать
  `MONTHLY` или `90d`. Ответ — по валюте: текущий и предыдущий курс, изменение в рублях
  и процентах, минимум, максимум, среднее и число замеров.
- `get_currency_change` — обязательный `hours` (целое число часов от 1 до 720, приходит строкой
  и разбирается `toIntOrNull`): изменение за окно из **последних закрытых** часов по сохранённым
  сводкам (§18). Отказ вместо умалчивания: не число, меньше 1 или больше 720 — ответ с текстом
  «допустимое значение — целое число часов от 1 до 720», а не молчаливая подмена окна.
  Неполное окно не выдаётся за полное: `hoursCovered` говорит, сколько часов действительно
  наблюдалось, `from`/`to` — границы покрытого промежутка, `note` — что данных меньше
  запрошенного. Границы `MIN_CHANGE_HOURS`/`MAX_CHANGE_HOURS` — тоже публичные константы:
  по ним сервер приложения отсекает недопустимый `hours` до вызова инструмента (§19).

Числа в ответе — `BigDecimal` (в JSON это число, а не строка с кавычками), момент — строка
ISO-8601 UTC.

## 10. Режимы процесса

Один процесс на всё — и на сбор, и на инструменты: MCP на stdio — это процесс, которым владеет
подключившийся клиент, и разнеси мы сбор и инструменты по процессам, история писалась бы одним,
а читалась другим. Режимы (`Application.kt`):

- **без аргументов — служба.** Сбор идёт, и тот же процесс отвечает по протоколу, пока его
  читают. По концу ввода служба **не выходит**: на VPS клиента может не быть вовсе, а сбор
  обязан продолжаться — это и есть «независимо от клиентского приложения». Ждёт сигнала
  остановки.
- **`--mcp` — процесс для клиента.** Тот же сбор, но по концу ввода процесс выходит: его
  владелец — подключившийся клиент, а не служба. Так его поднимает сервер приложения, локально
  и по ssh.
- **`--once` — одно обновление и выход** (код 0 — курсы записаны, 1 — обновления не было).
  Тот же путь, что у планировщика: иначе «одно обновление» проверяло бы не то, что работает
  по часам. Код возврата нужен скриптам и планировщику заданий на VPS.
- **`--list-tools` — список объявлений и выход**, без базы и без сети: список берётся
  из объявлений, поэтому печатается и там, где истории ещё нет.

**Планировщик стартует внутри лямбды `runStdioServer`, а не до неё.** До этого вызова стандартный
вывод ещё не забран под протокол, и первые строки логов (у logback по умолчанию — поток вывода)
уехали бы клиенту вместо кадров, а клиент потерял бы рукопожатие. Тем же порядком первое
обновление не начинается раньше, чем сервер готов отвечать.

Опечатка в режиме — отказ запуска с кодом 2 и списком режимов: иначе процесс молча встал бы
службой и ждал кадров из ввода, а человек решил бы, что команда зависла. Настройки — только
из окружения (`CURRENCY_API_BASE`, `CURRENCY_DB`, `CURRENCY_INTERVAL`), не из аргументов: сервис
запускают и служебно, и процессом-ребёнком, а ребёнку аргументы назначает тот, кто его поднял,
и настройка жила бы в двух местах. Пустая переменная считается отсутствием — `CURRENCY_DB=`
в скрипте иначе означала бы файл с пустым именем. Неразобранный `CURRENCY_INTERVAL` — отказ
запуска, а не молчаливая подмена часом: ноль означал бы цикл без пауз, который сам себя съест
запросами к чужому API.

База и HTTP-клиент закрываются в `finally`: службу останавливают сигналом, и незакрытая база —
это не сброшенные на диск записи и занятый файл при следующем запуске.

## 11. Подключение к агенту

`server/src/main/kotlin/com/osvin/aichallenge/CurrencyTools.kt` — то же место, где к запросу
подключаются инструменты GitHub: сессия с MCP-сервером долгая (поднимать процесс на каждый
вопрос значило бы платить за запуск и рукопожатие в каждом ответе), создаётся **лениво**
на первом запросе и закрывается на `ApplicationStopped` — процесс подняли мы, иначе он пережил
бы остановку приложения.

Отличие от GitHub одно и сознательное: у сервиса курсов нет доступа, который человек настраивает
кнопкой, и нет состояния, которое надо показать в интерфейсе, поэтому кнопки и шторки в UI
у него нет, а сессия поднимается сама. Панель для GitHub существует потому, что там есть что
показывать (кто вошёл, с какими правами, откуда взят токен) и что выбирать (значения аргумента).
Здесь аргумент всего один и с перечислением, а состояние — данные в истории, которые человек
и так видит в ответе агента.

Команда запуска локально — `:currency-monitor` в classpath и `--mcp`. На VPS сервис живёт
отдельно, поэтому команду можно задать переменной `CURRENCY_MCP_COMMAND`, например
`ssh vps sudo -n -u currency env CURRENCY_DB=/var/lib/currency-monitor/currency.db java -jar
/opt/currency-monitor/currency-monitor.jar --mcp`. Пустая или незаданная
переменная — локальный запуск; недоступный процесс инструментов не отменяет ответ, а попадает
в лог: вопрос идёт модели без инструментов, и попытка повторяется на следующем запросе.
Обратное решение превращало бы недоступность источника курсов в недоступность ассистента.
Пользователь и база названы в команде не для красоты: база принадлежит `currency`, а путь
по умолчанию — относительный, поэтому без них процесс создал бы себе пустую базу рядом с собой
и отвечал бы «истории нет» (на живом сервере это и выяснилось, §12).

Мелочь, которую пришлось поправить в `:mcp`: `localMcpServerConfig` получил параметр
`args` — раньше команда собиралась без аргументов, и режим `--mcp` было негде передать.

## 12. Развёртывание на VPS

Собирается один файл: `./gradlew :currency-monitor:fatJar` →
`currency-monitor/build/libs/currency-monitor-1.0.0-all.jar`, внутри манифест с `Main-Class`,
поэтому запуск ровно такой, как в задании: `java -jar currency-monitor.jar`. Байткод собирается
под Java 21 (версия класса 65), и это самая старая JVM, на которой он пойдёт, — на машине
разработки стоит 25, на сервере ставится 21.

Установка (инструкция лежит комментарием в самом unit-файле):

```bash
./gradlew :currency-monitor:fatJar
scp currency-monitor/build/libs/currency-monitor-1.0.0-all.jar vps:/tmp/
scp currency-monitor/deploy/currency-monitor.service vps:/tmp/
ssh vps 'sudo install -d /opt/currency-monitor
         sudo install -m 0644 /tmp/currency-monitor-1.0.0-all.jar /opt/currency-monitor/currency-monitor.jar
         sudo install -m 0644 /tmp/currency-monitor.service /etc/systemd/system/
         sudo useradd --system --no-create-home --shell /usr/sbin/nologin currency
         sudo install -d -o currency -g currency /var/lib/currency-monitor
         sudo systemctl daemon-reload && sudo systemctl enable --now currency-monitor'
```

`currency-monitor/deploy/currency-monitor.service` — служба systemd: `ExecStart=/usr/bin/java
-jar /opt/currency-monitor/currency-monitor.jar`, `CURRENCY_DB=/var/lib/currency-monitor/currency.db`,
`CURRENCY_INTERVAL=PT1M`, `Restart=on-failure`. Рабочий каталог задан явно, потому что база
по умолчанию лежит рядом с процессом — история должна быть там, где её видно, а не в каталоге,
который выбрал systemd. Проверка после установки: `systemctl status`, затем
`journalctl -u currency-monitor -n 20` — в логе видно источник, путь истории, интервал и первый
сбор; `sqlite3 … 'select count(*) from currency_rates'` — растущее число строк, и
`sqlite3 … 'select * from currency_hourly_summaries'` — закрытые часы (§18).

В unit-файле стоит минута — темп ленты закреплённого чата (§20). Для источника с дневным курсом
это до 1440 обращений в день ради ряда, который почти не меняется, поэтому рядом в файле
написано, что вежливее к чужому API поставить `PT1H`: лента станет часовой, нагрузка упадёт
в шестьдесят раз, а служба и инструменты работают с любым темпом. Умолчание в коде — та же
минута (§7): приложение ставит перед собой в первую очередь требование задачи, а выбор темпа
для конкретного источника оставляет тому, кто службу разворачивает.

### Что развёрнуто и чем проверено

Развёрнуто на виртуальной машине провайдера (Ubuntu 25.10, x86_64, 1 vCPU, 1.9 ГБ, systemd;
доступ по ключу, который выдал провайдер; в командах выше слово `vps` заменяло её адрес).
JRE поставлен из пакета `openjdk-21-jre-headless`, `sqlite3` — для проверок снаружи.

- **Служба работает и переживает перезагрузку.** `is-active` = `active`, `is-enabled` =
  `enabled`, `User=currency`, `NRestarts=0`. После `systemctl reboot` машина вернулась, служба
  поднялась сама (новый `MainPID`), собрала курсы через две секунды после старта и продолжила
  по минутному расписанию (`10:13:18`, затем `10:14:18`); история в файле уцелела. Выключение
  прошло по `SIGTERM` (`status=143`) — как и задано в unit-файле, чтобы JVM закрыла базу.
  То есть `enable` проверен загрузкой, а не только установкой.
- **Сбор идёт от настоящего ЦБ по расписанию.** В логе первого запуска: источник
  `https://www.cbr-xml-daily.ru`, история `/var/lib/currency-monitor/currency.db`,
  «обновление каждые PT1M», сбор сразу (`EUR/RUB = 95.870900`, `USD/RUB = 84.341400`,
  `GEL/RUB = 32.169300`), «в историю записано строк: 3», «следующее обновление курсов через
  PT1M»; второй сбор — ровно через минуту (`10:08:48` → `10:09:48`), третий и следующие так же.
  В `currency_rates` строки растут по три за обновление, момент получения — UTC.
- **Служба живёт без клиента.** В логе есть «Соединение закрыто: сбор курсов продолжается
  по расписанию»: systemd не даёт процессу ввода, и по концу ввода служба не выходит — это
  требование «независимо от клиентского приложения», проверенное на живой ВМ.
- **Протокол отвечает с развёрнутого jar.** В `java -jar … --mcp` поданы кадры рукопожатия,
  `tools/list` и `tools/call`: пришли три инструмента, а `get_currency_rates` — с курсами
  из базы службы (`updatedAt` и три значения). Значит, файл на сервере — рабочий сервер
  инструментов, а не только «jar, который запускается».
- **Клиент приложения ходит на сервер по ssh.** Локальный `:server:run` с
  `CURRENCY_MCP_COMMAND`, указывающим на ВМ, ответил на `GET /v1/currency` курсами **из базы
  на ВМ** (`updatedAt 2026-09-28T10:11:51Z`). Этим же проверено, что `--mcp`-процесс читает ту
  же базу, что и служба: вторая запись в неё не мешает (WAL), и `INSERT OR REPLACE` в сводках
  остаётся ключом, а не копиями.
- **Закрытие часа на развёрнутом jar.** На одноразовой базе в `/tmp` (база службы не трогалась)
  засеяны строки прошедшего часа; первый же тик службы закрыл час: в `currency_hourly_summaries`
  появились строки по валютам — первый и последний курс часа, изменение, проценты и число
  замеров, — а строка, попавшая в текущий час, в сводку не вошла. У самой базы службы сводок
  пока нет: первый закрытый час появится на ближайшей границе часа, и до тех пор пустая таблица
  сводок — правильное состояние, а не сбой.

Мелочь, которую видно только на живом сервере: **`--mcp`-процесс клиента надо запускать тем же
пользователем, что и службу** (`sudo -n -u currency … java -jar … --mcp`) — база принадлежит
пользователю `currency`, а WAL требует записи и на чтении. В unit-файле это не видно, потому что
там процесс и так запущен службой; в команде клиента пользователя надо назвать явно, иначе
процесс молча создаст себе *другую* пустую базу в своём каталоге и будет отвечать «истории нет».

Клиент подключается к сервису на VPS командой
`ssh vps sudo -n -u currency env CURRENCY_DB=/var/lib/currency-monitor/currency.db java -jar
…/currency-monitor.jar --mcp` через `CURRENCY_MCP_COMMAND`. Тогда сбор и история живут в службе,
а клиент получает процесс, который читает ту же базу: вторая копия сборщика на той же базе
писала бы параллельно.

  ответ, неположительный курс), инструменты (форма ответа, пустая история, отказ хранилища,
  период), часовые сводки (границы закрытого часа, повтор обхода не плодит копий, чтение
  окна сводок, суточное изменение по сводкам, недобор окна, отказ на недопустимых `hours`).
- Весь набор: 278 проверок (284 записи по XML — в шести файлах демонстрационных тестов XML
  дублируется), падений нет, два пропуска (живые прогоны `demo.live` в `:agent`); APK собирается.
- Живой источник: разовое обновление сходило к настоящему ЦБ и записало EUR 95.8709,
  USD 84.3414, GEL 32.1693 с моментом получения в UTC; схема и индекс в файле базы проверены
  снаружи (`sqlite3`).
- Подставной источник (тот же код-путь, но значения меняются на каждый запрос, `Nominal` лари
  = 10): три прогона наполнили историю, служба под `mcp/mcp-server.sh start --server currency`
  поднялась на fat JAR, в логе — источник, путь истории, интервал, первый сбор и время
  следующего; кадром протокола получены оба ответа — последние курсы с моментом и сводка
  за `DAY` с текущим, предыдущим, изменением, минимумом, максимумом, средним и числом замеров.
- Живой агент: сервер приложения поднял дочерний процесс курсов (`--mcp`) на той же базе,
  модель по обычной просьбе запросила `get_currency_summary`, затем `get_currency_rates`,
  и в ответе появились числа из подставного источника — их нет ни в вопросе, ни в знаниях
  модели, значит данные пришли из истории через MCP-инструмент. Второй вопрос («покажи текущий
  курс…») вызвал `get_currency_rates` и тоже ответил значениями из базы.
- В интерфейсе приложения карточки вызова на этот вопрос **нет**, и это не дефект: карточка
  рисуется там, где вызов сделал человек из шторки GitHub (`callGitHubTool` записывает вызов
  служебной строкой), а вызовы, сделанные моделью внутри ответа сервера, в ленту клиента
  не приходят — сервер возвращает только текст ответа. Отчёт о вызове модели остаётся в логе
  сервера, что для дня 18 и требовалось (агент вызывает инструмент), а показ чужих вызовов
  в ленте — отдельная работа, не из этого задания.

## 14. Что отброшено

- **`Double` для курсов.** Курс — деньги; 95.8709 в двоичной дроби возвращается уже другим
  числом, и сравнение с расчётным значением перестало бы быть точным.
- **Дедупликация истории** («пишем только изменения») — тогда «за сутки данных нет» и «за сутки
  курс не менялся» стали бы неразличимы.
- **`previousRate` из окна сводки** — у сервиса, работающего вторые сутки, изменение за сутки
  всегда было бы неизвестным.
- **Дата публикации ЦБ вместо момента получения** — потеряли бы ответ на вопрос «когда сервис
  это узнал», а история нужна именно для него.
- **Cron и внешний планировщик** — расписание внутри процесса не требует ни второй точки входа,
  ни правки crontab там, где службу ставят одним unit-файлом; вдобавок `--once` уже даёт способ
  звать обновление из чужого планировщика, если он всё-таки есть.
- **ORM и Room** — одна таблица и три запроса.
- **Шторка и кнопка подключения в интерфейсе** — у сервиса курсов нет ни настраиваемого доступа,
  ни состояния, которое надо показывать; кнопка заставляла бы нажимать её ради того, что и так
  работает.
- **Отдельный процесс на каждый вопрос агента** — платили бы за запуск JVM и рукопожатие
  MCP в каждом ответе.
- **Значение периода по умолчанию** — умалчивание читалось бы как «за сутки» там, где человек
  имел в виду месяц.

## 16. Что осталось непроверенным

- **Долгая работа на сервере.** Служба развёрнута и проверена на живой ВМ (§12): сутки её
  работы не ждали, поэтому ни один закрытый час не прожит от начала до конца, и суточная
  и недельная сводки считаются только по посевам и тестам. Всё, что для этого нужно, на месте
  и проверено: сбор идёт по расписанию и на настоящем ЦБ (минутные тики в логе), часы
  закрываются сводками, история переживает перезагрузку машины, а служба поднимается сама.
- **Провайдер ВМ, а не «железо» задачи.** Развёртывание сделано на виртуальной машине
  с Ubuntu 25.10 (x86_64, OpenJDK 21). Отличий от чужого VPS остаётся два: там может не
  оказаться systemd — тогда unit-файл не подойдёт, а служба запускается тем же `java -jar`,
  — и другой адрес для клиента.
- **Недельная и месячная сводки на живых данных**: окна `WEEK` и `MONTH` считает тот же метод,
  что и `DAY` (он проверен живьём и тестами), но истории длиной в месяц у сервиса ещё нет.
- **Предупреждение JVM при загрузке нативной библиотеки SQLite** (`A restricted method in
  java.lang.System has been called … --enable-native-access=ALL-UNNAMED`): это шум JDBC-драйвера
  в потоке ошибок, протоколу он не мешает и в ответах не появляется; снимается флагом JVM
  на новых JDK, но флаг обязателен не на всех, поэтому в unit-файл не добавлен.
- **Настоящий `GEL/RUB` — кросс-курс ЦБ**, а не курс грузинского рынка: сервис отдаёт то, что
  публикует источник, и это стоит помнить, читая ответ агента.
- **Экран приложения** в первой части не менялся, и карточка вызова инструмента из ответа
  сервера в ленту не приходит (см. §13). Во второй части экран менялся, и закреплённый чат
  проверен на запущенном эмуляторе (§21).

## 17. Вторая часть: закреплённый чат — что просит и чем закрыто

| Требование | Чем закрыто |
|---|---|
| Служба собирает курсы раз в минуту | `CurrencyConfig.DEFAULT_INTERVAL = PT1M` и `CURRENCY_INTERVAL=PT1M` в unit-файле; живой прогон — по минутной строке на ленте с меняющимся курсом (§21) |
| Чат — только лента курсов: писать нельзя, модель не отвечает | Признак `Chat.pinned`: у закреплённого чата нет поля ввода и полосы задачи, `sendMessage` для него выходит сразу, а `ChatRepository.deleteChat` его не удаляет (§20) |
| При открытии чата — изменение за сутки | Карточка `CurrencyChangeCard` первой строкой ленты читает `GET /v1/currency/change?hours=24` (§19, §20) |
| Раз в час — сводка изменения, и она хранится | `CurrencyHourlySummaryService.closeHour` закрывает прошедший час в таблицу `currency_hourly_summaries` после каждого состоявшегося обновления (§18) |
| Суточная картина строится на сохранённых часовых сводках | `get_currency_change(hours)` считает по строкам сводок, а не по первичной истории; в ленте — окно из последних **закрытых** часов (§18, §19) |

## 18. Часовые сводки: что хранится и когда час закрывается

```sql
CREATE TABLE currency_hourly_summaries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    hour TEXT NOT NULL,              -- начало часа, ISO-8601 UTC
    currency TEXT NOT NULL,
    first_rate TEXT NOT NULL, last_rate TEXT NOT NULL,
    change_rate TEXT NOT NULL, change_percent TEXT,   -- NULL: у нулевого курса процента нет
    min_rate TEXT NOT NULL, max_rate TEXT NOT NULL, average_rate TEXT NOT NULL,
    samples INTEGER NOT NULL
);
CREATE UNIQUE INDEX idx_currency_hourly_summaries_hour_currency
    ON currency_hourly_summaries (hour, currency);
```

- **Сводки хранит служба, и в той же базе, что историю.** Суточная картина должна быть полной
  независимо от того, было ли приложение открыто: считай её клиент по своей ленте, у телефона
  за сутки просто не нашлось бы столько строк, а у второго устройства была бы своя картина
  тех же курсов. Одна база — одно мнение о том, что было.
- **Ключ сводки — час и валюта**, и это ключ, а не украшение: час закрывается заново на каждом
  обходе, пока по нему есть записи, и повтор обязан заменять строку (`INSERT OR REPLACE`) —
  иначе один и тот же час попал бы в суточное изменение столько раз, сколько обходов прошло.
- **Час закрывается после состоявшегося обновления**, а не отдельным таймером: сбор и есть
  событие, после которого про час известно всё. Своего расписания у сводок нет — иначе у службы
  было бы два мнения о том, когда час кончился. Неудачное закрытие не отменяет сбор: следующее
  обновление попробует снова, а `INSERT OR REPLACE` не даст копий.
- **Закрывается только прошедший час** — окно `[начало часа, начало часа + 1 час − 1 секунда]`
  от `hourStart(now) − 1 час`: текущий час ещё идёт, и сводка по нему была бы снимком середины.
- **Считаются те же величины, что в сводке за период**: `change = последний lastRate − первый
  firstRate`, проценты от первого курса, минимум и максимум по сводкам окна, среднее — взвешенное
  числом замеров часа. Общие округление и проценты вынесены в `SummaryNumbers.kt`, которым
  пользуются обе считающие части: две копии `HALF_UP` с масштабом 4 разошлись бы молча.
- **Чтение — окно целых часов до последнего закрытого.** Сколько часов окна действительно
  наблюдалось, сервер говорит сам (`hoursCovered`, `from`, `to`, `note`), а не округляет
  недобор до полного окна: у только что установленного приложения суточной картины нет,
  и выдать два часа за сутки значило бы соврать числами.

## 19. Инструмент `get_currency_change` и маршруты сервера приложения

Инструмент объявлен как остальные (`DeclaredTool`, см. §9): обязательный `hours`, границы
1…720, ответ с валютами и честным покрытием окна.

Сервер приложения (`server/src/main/kotlin/…/CurrencyTools.kt`) получил вызов инструмента
**по имени** и отказ значением: `CurrencyTools.call(name, arguments)` возвращает `Answered`
с телом ответа инструмента или `Unavailable` с причиной. Сессия с MCP-сервером поднимается
лениво и тем же `tools()`, поэтому маршрут ничего не знает про stdio.

- `GET /v1/currency` — тело ровно то, что ответил `get_currency_rates`; 502, если сессию поднять
  не удалось (в теле — причина).
- `GET /v1/currency/change?hours=N` — тело ровно то, что ответил `get_currency_change`; 400
  на не-число и на `hours` вне границ инструмента, 502 при недоступности сессии.

**Числа на проводе — числа.** `JsonPrimitive` из `BigDecimal` печатает `toString()`, поэтому
масштаб с конечными нулями теряется: `95.0000` уезжает как `95.0`. Строкой число отдавать
нельзя — по нему считает модель, — а дописывать нули на клиенте значило бы показывать точность,
которой сервер не называл. Клиент печатает цифры ровно те, что пришли, меняя только разделитель
на запятую (§20).

**Второй модели тех же чисел на сервере нет**: маршрут отдаёт тело ответа инструмента как есть
(`respondText(json, ContentType.Application.Json)`). Посчитай сервер изменение сам — он
и служба разошлись бы в том, что считать «последним закрытым часом», и расхождение вылезло бы
только на живых данных. По той же причине границы `hours` берутся из публичных констант
инструмента (`MIN_CHANGE_HOURS`/`MAX_CHANGE_HOURS`), а не из литералов в маршруте.

**Клиент изменение не считает** и не может: в общем коде KMP нет ни `BigDecimal`, ни
библиотеки дат, а `Double` в деньги здесь не заводят (§14). Он показывает то, что посчитал
сервис, — и это же снимает вопрос о двух ответах на один вопрос.

## 20. Приложение: закреплённый чат

**Чат закреплён признаком, а не именем.** `Chat.pinned` — поле модели (`MIGRATION_5_6`:
`ALTER TABLE chats ADD COLUMN pinned INTEGER NOT NULL DEFAULT 0`), список сортируется
`ORDER BY pinned DESC, updatedAt DESC`. Сравнение с `CurrencyChat.ID` в интерфейсе разошлось бы
с базой при первом же переносе строки, а признак работает и для будущего второго закреплённого
чата. Подпись строки — «закреплён · сессия …», кнопки удаления у неё нет, и `deleteChat`
закреплённый чат не удаляет: стирание ленты можно было бы принять за обычное действие.

**Писать в этот чат нельзя.** У закреплённого чата `ChatScreen` не рисует ни поля ввода,
ни полосы задачи, а `ChatRepository.sendMessage` выходит сразу: иначе модель ответила бы
в ленте курсов, где нет ни вопроса, ни места для ответа. Служебные строки ходят мимо истории
модели: роль `MessageRole.MONITOR` отсеивается фильтром истории (`role != TOOL && role !=
MONITOR`), поэтому курс, напечатанный минутой, не становится «репликой» для следующего запроса.
Отрисовывается такая строка служебной карточкой, а не репликой человека.

**Лента ведётся самим приложением.** `ChatRepository.runCurrencyMonitor` живёт в области
видимости приложения (`ChatViewModel.startCurrencyMonitor`, запуск защищён от повторного):
приложение открыто — минута тикает, закрыто — цикл умирает вместе с областью. Будильников
и фоновых служб нет намеренно: задание просит ленту, которую видно, а не сбор в фоне, и второй
сборщик рядом со службой курсов — это второй писатель в ту же базу. Удар читает
`GET /v1/currency`, печатает строку «время · EUR … · USD … · GEL …» (время берётся из метки
сервера: виден момент, когда курсы посчитал сервис, а не когда тикнул телефон) и обрезает ленту
до 240 последних строк — суточную картину показывает шапка, а не вся лента.

**Сводка часа в ленте.** На смене часа удар дополнительно спрашивает
`GET /v1/currency/change?hours=1` и печатает «Сводка за час ЧЧ:00–ЧЧ:00» со строками по валютам —
это видимый след тех самых сохранённых сводок (§18). Час, прошедший без тика, сводкой
не задним числом не закрывается: монитор его не наблюдал, и «сводка» за него была бы пересказом.
Неудачное чтение сводки не повторяется через минуту — час уже сменился, и вторая попытка назвала
бы тем же именем следующий час; причина уходит в лог.

**Шапка — карточка `CurrencyChangeCard`** первой строкой ленты: при открытии чата
`ChatViewModel.loadCurrencyChange` читает окно в 24 часа. Карточка честно говорит, чего
не хватает («за сутки данных не хватило: сохранено 2 ч из 24»), а валюте без наблюдений
печатает прочерк и слова «наблюдений нет» — «без изменения» на месте двух прочерков читалось бы
как «курс стоял на месте», хотя сервер курса в этом окне и не видел. Отказ не стирает уже
прочитанный снимок: числа остаются, а рядом появляется причина, потому что убрать их значило бы
сделать вид, что они не читались.

**Числа печатаются как пришли** (`DecimalText`): сериализатор берёт `JsonPrimitive.content`
как есть и отвергает `JsonNull`, а `line()` меняет только точку на запятую. Своих вычислений
у клиента нет — и быть не может (§19).
