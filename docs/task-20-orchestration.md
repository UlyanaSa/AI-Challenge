# День 20. Оркестрация MCP: один агент, несколько серверов — устройство

Дни 16–19 дали агенту по серверу инструментов за раз. День 20 убирает эту границу: агент получает
**один список инструментов нескольких MCP-серверов**, сам выбирает нужные, а маршрут каждого вызова
(какому серверу он принадлежит) держит оркестратор. Порядок шагов не зашит: длинный workflow
собирает модель по описаниям инструментов.

## 1. Что просит задание и чем подтверждается

| Требование | Где сделано | Чем подтверждается |
| --- | --- | --- |
| Минимум два независимых MCP-сервера, желательно три | `:currency-monitor`, `:mcp-github`, `:mcp-report` (новый) + `:mcp-pipeline` четвёртым | живой прогон `:server:orchestrationDemo`, вывод `:mcp-report:mcpTools` |
| Сервер отчётов: `createReport` и `saveReport` | `mcp-report/.../mcp/CreateReportTool.kt`, `SaveReportTool.kt` | тот же живой прогон, раздел «Отчёт» |
| Единый реестр инструментов всех серверов | `server/.../orchestration/McpToolRegistry.kt` | `[orchestrator] сервер …: инструментов N` в логе прогона |
| `McpOrchestrator`: tool → server → execution → result | `server/.../orchestration/McpOrchestrator.kt` | строки протокола вызовов: `tool=… server=… duration=… success=…` |
| LLM сам выбирает инструмент, порядок не зашит | описания инструментов + цикл агента | просьба дня в демонстрации: имён инструментов и порядка в ней нет |
| Несколько последовательных вызовов в одном запросе | `AppConfig.MAX_TOOL_ROUNDS = 15` | прогон: 5 вызовов подряд (в другом прогоне — 6) |
| Один workflow использует инструменты двух и более серверов | реестр + оркестратор | маршрут прогона: currency → github → report |
| Результат одного сервера используется при вызове другого | агент передаёт ответ аргументом | в файле отчёта есть и курсы, и репозитории (см. §6) |
| Обработка ошибок структурированным результатом | `McpOrchestrator.failure` | коды `MCP_SERVER_UNAVAILABLE`, `MCP_UNKNOWN_TOOL`, `MCP_TOOL_TIMEOUT`, `MCP_TOOL_ERROR`, `MCP_CALL_FAILED`, `MCP_EMPTY_RESULT` |
| Ограничение числа итераций | `AppConfig.MAX_TOOL_ROUNDS = 15` | `AgentToolTest` (предел раундов) |
| Логирование, по которому восстанавливается workflow | `McpOrchestrator.log` | `requestId=1 iteration=4 tool=getRecentCommits server=github duration=11ms success=true` |

Имена инструментов в задании приведены как пример: в проекте у каждого сервера свои имена, и реестр
работает с любыми. Новые инструменты названы как в задании (`getRepository`, `getRecentCommits`,
`createReport`, `saveReport`).

## 2. Серверы

- **`:mcp-report`** — новый, четвёртый сервер: `createReport(title, sections)` собирает markdown
  из заголовка и секций (`sections` — JSON-массив объектов `{"title", "content"}` одной строкой),
  `saveReport(content, filename?)` пишет файл в свой каталог (`REPORTS_DIR`) и отвечает абсолютным
  путём. Отдельный сервер, а не инструмент пайплайна: у отчётов свой предмет (любые данные, не
  только курсы), своя настройка каталога и своя точка входа. Флага `--mcp` нет: работы без клиента
  у него не существует.
- **`:mcp-github`** — к `get_repositories` и `github_access` добавлены `getRepository(repository)`
  и `getRecentCommits(repository, limit)` (лимит 1..100, по умолчанию 10): без них просьбу
  «найди репозиторий и покажи коммиты» выполнить было нечем.
- **`:currency-monitor`** — инструменты курсов как были (день 18): их трое.
- **`:mcp-pipeline`** — цепочка дня 19 осталась четвёртым сервером в том же реестре.

## 3. Реестр и имена вызовов

`McpToolRegistry` хранит по каждой паре «сервер + инструмент» одну запись и отвечает на вопрос
«чей это вызов». Повторная запись того же имени не заменяет прежнюю и не удваивает список:
сессию сервера могут поднять заново, и вторая копия того же инструмента ничего не добавляет.

Имя вызова, которое видит модель, — `сервер__инструмент` (`github__getRecentCommits`). Признак
сервера нужен потому, что одинаковые имена у разных серверов возможны (запись файла умеют и
пайплайн, и сервер отчётов), и выбирать между ними должен не код, а модель — по описанию, в
котором назван сервер.

**Разделитель — двойное подчёркивание, а не точка, хотя точка читалась бы привычнее.** Имена
функций в API провайдера обязаны совпадать с `^[a-zA-Z0-9_-]+$`: список инструментов с точками
отклоняется целиком (`400 Invalid 'tools[0].function.name'` — проверено живым запросом). Двойное
подчёркивание, а не одиночное: одиночное встречается внутри имён (`get_currency_rates`), и
`currency_get_currency_rates` разбиралось бы на сервер и инструмент неоднозначно.

## 4. Оркестратор

`McpOrchestrator` делает ровно одно: по имени вызова находит сервер, выполняет вызов и отвечает
результатом. Выбор инструмента остаётся за моделью — сложи выбор и маршрут в одном месте, и код
снова знал бы, какой шаг нужен следующим.

- **Срок вызова — минута.** Длинный workflow состоит из вызовов, и один зависший вызов иначе
  держал бы весь ответ.
- **Отказы — структурой**: `{"success": false, "error": {"code", "server", "tool", "message"}}`.
  Код отличает «сервера нет» от «инструмента нет» и «сервер не успел», причина уходит модели
  словами, и она может исправить вызов. Отказ самого инструмента тоже заворачивается в эту форму:
  в его тексте не сказано, чей это отказ.
- **Успешный результат отдаётся как есть**, текстом инструмента: следующий шаг принимает его
  аргументом, и обёртка вокруг данных сломала бы передачу между серверами.
- **Протокол**: одна строка на вызов — номер запроса, номер вызова, инструмент, сервер, размеры
  аргументов, длительность и исход. Размеры, а не значения: аргументом идёт ответ предыдущего
  инструмента целиком, и строка протокола превратилась бы в простыню; по `rates:155` при этом
  видно, что второму шагу ушёл документ, а не пустая строка.

Пример строк живого прогона:

```
requestId=1 iteration=1 tool=get_currency_rates server=currency arguments=нет duration=7ms success=true
requestId=1 iteration=2 tool=get_repositories server=github arguments=нет duration=15ms success=true
requestId=1 iteration=4 tool=getRecentCommits server=github arguments=repository:11,limit:1 duration=11ms success=true
requestId=1 iteration=6 tool=saveReport server=report arguments=filename:38,content:1124 duration=11ms success=true
```

## 5. Агент и предел раундов

Цикл агента не изменился: он предлагает модели список инструментов и выполняет то, что она просит,
пока она не ответит текстом или не кончатся раунды. Изменился предел — `MAX_TOOL_ROUNDS` поднят
с трёх до пятнадцати: три хватало на один сервер, а длинный workflow дня 20 обрывался бы на
середине, и человек получал бы ответ «не успел». Пятнадцати шагов хватает самому длинному
сценарию задания с запасом, а бесконечный цикл по-прежнему невозможен.

## 6. Передача данных между серверами

Серверы друг о друге не знают: результат одного уходит аргументом следующему **через агента**.
Доказательство — файл отчёта: в нём есть и курсы, которые вернул Currency MCP, и репозитории
с коммитами из GitHub MCP. Проверка живого прогона сравнивает числа из ответа сервера курсов
с содержимым записанного файла, а не с выдуманными значениями: курсы служба берёт из сети,
и собственные числа в проверке разошлись бы с её данными.

## 7. Живой прогон

`./gradlew :server:orchestrationDemo -Pdemo.live=1` — модель `deepseek-v4-flash`, три сервера
инструментов подняты настоящими процессами по протоколу MCP (GitHub — с подставным API, курсы —
с временной базой, отчёты — с временным каталогом). Просьба — дословно из задания: «Получи текущие
курсы USD, EUR и GEL относительно рубля. Затем найди мои репозитории, найди репозиторий kmp-agent,
получи последние 5 коммитов. После этого создай общий отчёт с курсами валют и активностью GitHub
и сохрани его в файл.»

Модель получила девять инструментов трёх серверов (`github__…` четыре, `currency__…` три,
`report__…` два) и прошла цепочку сама:

```
currency→get_currency_rates, github→get_repositories, github→getRecentCommits,
report→createReport, report→saveReport
```

Пять вызовов, три сервера, ни одного зашитого шага. Курсы из ответа Currency MCP
(95.8709 / 84.3414 / 32.1693) нашлись в записанном отчёте рядом с репозиторием `kmp-agent`
из GitHub MCP — данные двух серверов встретились в одном файле. Ответ человеку: «Готово!
Отчёт создан и сохранён.»

В другом прогоне модель выбрала шесть вызовов (добавила `getRepository` к `getRecentCommits`) —
порядок и набор шагов определяет она, поэтому проверка держится за суть: вызовов несколько,
серверов три, порядок «курсы → GitHub → отчёт», в отчёте есть данные обоих серверов.

## 8. Как запускать

```
./gradlew :server:orchestrationDemo -Pdemo.live=1  # живой workflow через три сервера
./gradlew :mcp-report:mcpTools                     # инструменты сервера отчётов без клиента
./gradlew :mcp-report:fatJar                       # сервер отчётов отдельным процессом
```

Сервер отчётов поднимается приложением сам (ленивой сессией, как курсы и пайплайн). Если отчёты
пишутся не рядом с приложением, команда запуска задаётся переменной
`REPORT_MCP_COMMAND` (как `CURRENCY_MCP_COMMAND` и `PIPELINE_MCP_COMMAND`); каталог отчётов
сервера — `REPORTS_DIR`.
