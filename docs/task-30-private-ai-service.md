# День 30. Приватный AI-сервис на локальной модели: ключ, лимиты, метрики, контейнер

Дни 27–29 сделали локальную модель и настроили её под кейс, но пользовались ею только из веб-чата
этой же машины: `LLM_PROVIDER=local` и `http://127.0.0.1:11434`. День 30 превращает это в
**сервис**: отдельная поверхность `/api/…` рядом с `/v1/…`, вход по ключу, ограничения частоты и
параллельности, потолки контекста, метрики, запуск в контейнере и клиент, который к сервису
подключается настраиваемо — адресом, ключом, моделью и рамками запроса.

Поверхность `/v1/…` при этом не тронута: это вторая дверь в тот же дом, а не переделка первой.

## 2. Поверхность `/api/…`

| Метод и путь | Что делает | Ключ | Лимит частоты |
| --- | --- | --- | --- |
| `GET /api/health` | живость сервиса и демона, загружена ли модель | не нужен | нет |
| `GET /api/metrics` | снимок работы | нужен | нет |
| `GET /api/models` | имена моделей демона | нужен | да |
| `POST /api/chat` | ответ модели в сессию | нужен | да |
| `POST /api/chats` | новая сессия | нужен | да |
| `GET /api/chats` | список чатов | нужен | да |
| `GET /api/chats/{id}` | история сессии | нужен | да |
| `DELETE /api/chats/{id}` | удаление сессии с историей | нужен | да |

Ливость отвечает без ключа намеренно: клиент по ней различает «сервер не отвечает» и «ключ
неверный», и без этого различия человек правил бы адрес там, где надо вписать ключ.

Коды отказов (тело всегда `{code, message, requestId}`, `requestId` — восемь
шестнадцатеричных символов, по нему ищут строку в логе):

| Код | Код ответа | Когда |
| --- | --- | --- |
| `invalid_request` | 400 | тело не разобрано, нет `chatId` или `message` |
| `context_overflow` | 400 | обязательная часть запроса не влезает в окно |
| `unauthorized` | 401 | ключа нет или он не подходит |
| `chat_not_found` | 404 | сессии нет (в том числе при указании несуществующего прошлого чата) |
| `model_unavailable` | 404 | демон ответил, но модели у него нет |
| `rate_limited` | 429 | исчерпан лимит частоты; в ответе `Retry-After` |
| `empty_reply` | 502 | модель вернула пустой текст (бюджет ушёл в рассуждения) |
| `ollama_unavailable` | 503 | демон не ответил |
| `overloaded` | 503 | очередь генераций заполнена или время ожидания вышло; `Retry-After` |
| `service_not_configured` | 503 | не задан ключ доступа или выбран не локальный провайдер |
| `timeout` | 504 | модель не успела ответить |
| `internal_error` | 500 | сбой сервиса |

## 3. Ключ доступа

Ключ приходит заголовком `X-API-Key` или `Authorization: Bearer …`, сравнивается постоянным по
времени способом (`MessageDigest.isEqual`), причём **все** настроенные ключи сравниваются без
раннего выхода: по времени ответа иначе читалось бы, какой ключ угадан. Ключей может быть
несколько (`SERVICE_API_KEYS` через запятую) — «несколько клиентов на один сервис».

Ключ никогда не попадает в лог, даже обрезанным: строка лога уходит в общий вывод контейнера, а
ключ — это доступ. Вместе с ключом не логируется и переписка: в лог идёт только
`requestId`, путь, код и длительность:

```
[service] requestId=3debc666 path=/api/models status=401 duration=0ms
```

Сервис без заданного ключа не отвечает никому, кроме `/api/health` (`503 service_not_configured`) —
пустой ключ не должен включать поверхность без защиты.

## 4. Лимиты: частота, параллельность, очередь

Три разных ограничения, потому что они защищают разные вещи: **частота** (10 запросов в минуту на
ключ, скользящее окно 60 с) защищает от одного настойчивого клиента, **параллельность** (2) — от
перегрузки одной локальной модели, **очередь** (4 ждущих, ожидание 15 с) даёт шанс тем, кто пришёл
в момент занятости, вместо мгновенного отказа. Метрика `generations.queued` считает только реально
ждущих: занявший место в очереди в неё не входит.

Нагрузочный прогон `build/day30/load.py` (одна машина, Ollama рядом с сервисом):

| Одновременных запросов | Стенные, мс | Успехов | Отказов | Пик очереди | RSS, МБ | CPU |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 993 | 1 | 0 | 0 | 75 | 1,1 % |
| 5 | 3 533 | 5 | 0 | 3 | 93 | 1,3 % |
| 10 | 21 866 | 1 | 9 (4×502 `empty_reply`, 5×503 `overloaded`) | 4 | 118 | 1,0 % |

Тот же прогон на инстансе с `OLLAMA_THINK=false` (та же модель, та же машина):

| Одновременных запросов | Стенные, мс | Успехов | Отказов | Пик очереди | RSS, МБ | CPU |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 165 | 1 | 0 | 0 | 114 | 17,4 % |
| 5 | 282 | 5 | 0 | 0 | 151 | 32,1 % |
| 10 | 432 | 6 | 4 (503 `overloaded`) | 0 | 170 | 26,9 % |

Вывод, который и есть смысл этих двух таблиц: **предел упирается в модель, а не в сервис**.
Рассуждающая сборка тратит бюджет в ход мысли (отсюда 502 `empty_reply` на десяти запросах), и
сервис здесь ни при чём; с выключенным рассуждением десять одновременных укладываются в 432 мс,
шесть из них приняты (2 места + 4 в очереди), остальные получают честный `503` с `Retry-After`,
а не висят.

Сценарий «15 запросов за минуту» (лимит 10): `10×200` и `5×429`, стенные 120 мс — отказы
мгновенные, потому что считаются до обращения к модели.

## 5. Контекст: потолки и усечение

Клиент может просить меньше, но не больше: `contextWindow` обрезается до `SERVICE_MAX_CONTEXT_TOKENS`
(4096), `maxTokens` — до `SERVICE_MAX_GENERATION_TOKENS` (512), температура — до 2.0. Обрезается,
а не отвергается: клиент получает ответ по потолку, а не отказ вместо него.

Бюджет окна считается как «окно минус резерв под ответ», поэтому ответ всегда влезает. Из истории
выбрасываются только несистемные сообщения, начиная со старых, а обязательная инструкция сервиса
и текущий вопрос не выбрасываются никогда. Если не влезает даже обязательная часть — 400
`context_overflow` (проверено запросом с `contextWindow: 999999`: потолок сервера важнее просьбы
клиента). Усечение видно в ответе (`trimmedMessages`): при окне 1024 ряд получился 0, 0, 5, 7, 9.

Отказ по контексту и отказ по бюджету не оставляют следа в истории: запись идёт одной парой
«вопрос — ответ» только после успешного ответа. Иначе в беседе остался бы вопрос без ответа, и
следующая генерация отвечала бы на два вопроса сразу. По той же причине отмена запроса клиентом
оставляет в истории ноль сообщений.

**Пустой ответ модели — отказ, а не ответ.** У думающей сборки бюджет уходит в рассуждения, `usage`
приходит полным, а текст — пустым. Ответ `status: ok` с пустой строкой клиент показал бы как
утверждение модели, которого не было, поэтому сервис отвечает `502 empty_reply` и прямо называет
лечение: поднять `maxTokens` или выключить рассуждение (`OLLAMA_THINK=false`).

## 6. Метрики

`GET /api/metrics` под ключом (не под лимитом частоты: панель не должна исчезать в момент
перегрузки). Снимок из прогона:

| Группа | Значения из прогона |
| --- | --- |
| `requests` | `total 208`, `success 157`, `failed 51` |
| `latency` | `averageMs 4530`, `p95Ms 9556`, `samples 84` |
| `generations` | `active 0`, `queued 0`, `maxConcurrent 2`, `queueLimit 4` |
| `rateLimit` | `rejections 0`, `limitPerMinute 1000` (инстанс функциональных проверок) |
| `tokens` | `prompt 13772`, `completion 16425`, `total 30197` |
| `sessions` | `count 61`, `messages 74` |
| `resources` | RSS 25,6 ГБ / 25,8 ГБ, `systemCpuLoad 0.38`, `processors 12` |

p95 считается по кольцу последних 500 генераций: держать все замеры ради процентиля — память
на то, что уже не изменится. Память машины и загрузка процессора берутся только у
`com.sun.management.OperatingSystemMXBean`; на другой JVM этих счётчиков нет, и поле остаётся
пустым — ноль здесь был бы враньём («память не занята» вместо «неизвестно»).

## 7. Клиент: шторка «Приватный сервис» и четыре состояния

Режим чата переключается настройкой («Сейчас» / «Сервис»), а не сборкой: поля адреса, ключа,
модели, температуры, `maxTokens` и окна контекста живут в шторке, ключ показывается скрытым.
Настройки переживают перезапуск клиента целиком, **включая ключ** (web — `localStorage`, Android —
`SharedPreferences` файла `ai-challenge-settings`): цена решения названа прямо в шторке, потому что
ключ на диске переживёт выход из приложения и может попасть в резервную копию. Почему так, а не
«только в памяти», — в §9.

«Проверить подключение» делает два шага: живость **без** ключа, затем список моделей **с**
ключом, и различает четыре состояния:

| Состояние | Когда | Что видно в шторке |
| --- | --- | --- |
| «Подключён» | сервис ответил, выбранная модель есть в списке | «Подключён: сервис отвечает, модель qwen3:1.7b доступна» |
| «Недоступен» | сервис молчит или ответил 503 | «Недоступен: …» с причиной от сервиса |
| «Ошибка авторизации» | сервис ответил 401 | «Ошибка авторизации: Ключ доступа не предъявлен или не подходит» |
| «Модель недоступна» | сервис ответил, но выбранной модели у него нет | «Модель недоступна: qwen3:99b нет в списке моделей сервиса» |

Ниже состояния показываются модели сервиса — их видно ровно в момент, когда человек выбирает,
какое имя вписать.

Проверка идёт **по тому, что набрано в шторке**, а не по сохранённым настройкам. Это не мелочь:
первая версия читала сохранённые, и набранный, но не сохранённый ключ уходил в проверку пустым —
шторка отвечала «Ошибка авторизации» на верный ключ, то есть врала о том, что на экране. Ошибку
нашли живым прогоном в браузере (дальше ключ подтверждён на стороне сервиса: `GET /api/health`
без ключа, `GET /api/models` с ключом длиной 64 символа), и в тестах теперь есть проверка
`checkUsesPassedSettingsNotSavedOnes`.

## 8. Контейнер: Docker Compose

`Dockerfile` — многоступенчатая сборка: JDK 21 собирает `:server:jar`
(`--no-daemon --no-configuration-cache --configure-on-demand`, чтобы Android SDK не требовался),
рантайм — JRE 21 с `curl` для healthcheck, процесс не под root, данные в `/data`.

`docker-compose.yml` поднимает сервис с ключом из `.env` (без ключа запуск останавливается:
`${SERVICE_API_KEY:?…}`), `host.docker.internal` для доступа к Ollama на хосте, том `service-data`
на `/data` (история чатов, профиль, память, инварианты переживают перезапуск контейнера),
healthcheck `/api/health`, `restart: unless-stopped`, `stop_grace_period: 20s`. Ollama наружу
не публикуется — виден только API сервиса и только с ключом.

**Контейнерный путь не проверен: Docker на этой машине не установлен.** Честно: команды в
манифестах написаны и вычитаны, но ни один контейнер не собирался и не запускался. Установка —
`brew install --cask docker`, затем `docker compose up -d --build` (готового бинаря `docker`
в системе нет, и подменять эту проверку чем-то другим нельзя — она проверяемая только Docker'ом).

## 10. Как запускать

```bash
# сервис на хосте: локальная модель, ключ из файла, база в build/day30
SERVICE_API_KEY=$(cat /tmp/day30.key) \
CHAT_DB=build/day30/service-chats.db \
LLM_PROVIDER=local OLLAMA_MODEL=qwen3:1.7b \
./gradlew :server:run

# клиент: веб-приложение на http://127.0.0.1:8081 (шторка «Сервис» в шапке чата)
./gradlew :app:webApp:wasmJsBrowserDevelopmentRun

# живая приёмка сервиса (29 проверок, ~2 мин: внутри окно лимита 60 с)
python3 build/day30/verify.py            > build/day30/verify.log

# нагрузка: одновременные запросы, очередь, метрики
python3 build/day30/load.py http://127.0.0.1:8091 nothink

# приёмка продолжения дня 30: список чатов, общий чат, сводка прошлого диалога
python3 build/day30/verify-chats.py http://127.0.0.1:8082

# контейнер (на машине без Docker не выполнится — см. §8)
cp .env.example .env && docker compose up -d --build
```

## 11. Что осталось непроверенным

- **Docker Compose** — бинаря `docker` в системе нет, ни одна команда из §8 не выполнялась.
- **Облачная сборка клиента и iOS**: клиент собран и проверен для web (wasmJs) и Android-host-тестов;
  JVM- и iOS-таргеты не собирались.
- **Модель `qwen3:1.7b` даёт разный текст на одном вопросе** («Юпитер» / «Меркурий» в нагрузочных
  прогонах): числовые выводы из §4 — про пропускную способность, а не про качество ответов.
- **`GET /api/models` отдаёт только имена** (`qwen3:1.7b-q8_0`, `qwen3:1.7b`, `bge-m3:latest`):
  размер, квантизация и число параметров остаются пустыми, потому что задание запрещает второй
  HTTP-запрос к демону, а проверка здоровья разбирает только имена.
