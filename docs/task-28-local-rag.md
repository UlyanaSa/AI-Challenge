# День 28. RAG целиком на своей машине: локальная модель против облачной

День 28 ничего не добавляет к конвейеру: он проверяет, что собранная за прошлые дни система
работает **без облака вообще** — индекс, поиск, переписывание запроса, реранкинг и ответ считаются
на этой машине, — и сравнивает две генерации на одних и тех же вопросах: локальную `qwen3:1.7b`
через Ollama и облачную `deepseek-v4-flash`. Поиск при этом общий: он и раньше был локальным
(Ollama `bge-m3`), и в сравнении он — постоянная часть, а не переменная.

## 1. Что просит задание и чем подтверждается

| Требование дня 28 | Где в коде | Чем подтверждается |
| --- | --- | --- |
| RAG-система работает полностью локально | `rag/.../Api.kt`: `settings()`, `provider()`, `modelName`, `model(apiKey)`; `rag-ui/.../RagSession.kt`: `provider`, `keyMissing` | Живой прогон `LLM_PROVIDER=local ./gradlew :rag:ragDemo -Pdemo.live=1` — десять вопросов на локальной модели; в логе прогона нет ни одного обращения к облаку |
| Локальная модель отвечает вместо облачной | `LlmClientFactory` (день 27) вызывается из `Api.model` — та же фабрика, что у веб-чата | Отчёт прогона называет модель (`Модель: qwen3:1.7b`), строки лога — `[agent] Ollama qwen3:1.7b: …` |
| Ключ облака больше не обязателен для RAG | `RagCli.main`: ключ требуется только облачному провайдеру; `RagSession.keyMissing` — только при `CLOUD` | Прогон без ключа: облачный ключ в `server/.env` есть, но не читается при `LLM_PROVIDER=local`; при пустом ключе страница дня 23 запускает прогон, а не отказывает |

| Сравнение по скорости | Отчёты обоих прогонов: токены запроса и ответа, длительность прогона | Таблица скорости ниже: время прогона и обращения, токены по режимам |
| Сравнение по стабильности | Два прогона локальной модели на тех же вопросах и том же индексе | Совпадение ответов между прогонами — таблица стабильности ниже |

| Сравнение видно на странице, а не только в файлах | `rag-ui/.../CompareSession.kt`, `QuestionRunner.kt` (одна сборка агентов на прогон и на сравнение) | Живой прогон раздела «Сравнение моделей»: две модели, два повтора, три разреза и отчёты `build/rag-ui/compare/` (§8.1) |

## 2. Что в RAG было локальным и раньше, а что стало

| Часть конвейера | Кто считает | День |
| --- | --- | --- |
| Нарезка корпуса | локальный код, без модели | 21 |
| Векторы и поиск | **уже локально**: демон Ollama, модель `bge-m3` (`EmbeddingProviders.fromEnv`) | 21–22 |
| Переписывание запроса, второй этап (LLM-реранкер), ответы, проверка цитат | было облачной моделью DeepSeek | 23–24 |
| Всё перечисленное выше | **стало локальным**: `LLM_PROVIDER=local` подставляет `LocalLlmClient` и в прогон, и на страницу | 28 |

Отсюда разделение наблюдаемого в сравнении: **поиск** в обоих прогонах одинаков (один индекс,
один `bge-m3`, одна выдача — она видна в отчёте по каждому вопросу), поэтому разница в оценках
принадлежит генерации, а не поиску. Это и делает сравнение честным: переменная ровно одна.

## 3. Одно место выбора провайдера

День 27 ввёл `LlmProvider`/`LlmProviderConfig`/`LlmClientFactory` для веб-чата. День 28 не заводит
второго способа: `Api` (общий для прогона в консоли и для страницы дней 23–25) читает те же
переменные и вызывает ту же фабрику.

```
RagCli.main / RagUiApplication.main
      ↓  Api.provider()            LLM_PROVIDER: local | cloud
      ↓  Api.modelName(requested)  имя модели: в локальном режиме его задаёт транспорт
      ↓  Api.model(apiKey)         LlmClientFactory(config, http, logger).create(apiKey)
      ↓                           LOCAL → LocalLlmClient (Ollama /api/chat)
      ↓                           CLOUD → DeepSeekClient
RagAgent / GroundedAgent / LlmQueryRewriter / LlmReranker   ← видят только LlmClient
```

Тому, у кого модели две сразу, одной настройки мало, и это единственное расширение дня: сравнение
берёт клиента **по провайдеру**, а не по окружению: `Api.settingsFor(provider)` (те же переменные,
но провайдер задан параметром) и `Api.modelFor(provider, apiKey)`. Второго выбора транспорта при
этом не появляется — фабрика та же, и оба клиента сравнения собраны ею.

Здесь же вылезла ловушка, которую стоит назвать: имя модели у рук сравнения **разное**, и брать его
из одного места нельзя. `Api.modelName(requested)` в локальном режиме возвращает имя локальной
модели (`qwen3:1.7b`) — это верно для страницы, которая отвечает одной моделью, но облачной руке
такое имя отправлять нельзя: API отвечает `400 The supported API model names are … but you passed
qwen3:1.7b`, и колонка облачной модели остаётся пустой. Поэтому у страницы два поля — `model`
(кем отвечает сама страница) и `cloudModel` (имя облачной модели для сравнения, умолчание
`AppConfig.DEFAULT_MODEL`), — и облачная рука получает именно второе.

Настройки читаются из окружения и из `server/.env`, где переменная окружения важнее: файл у прогона
и у сервера один, и провайдер, положенный в него, одинаково понимается обоими.

| Переменная | Значение | Умолчание |
| --- | --- | --- |
| `LLM_PROVIDER` | `local` или `cloud`; незнакомая строка — `cloud` | `cloud` |
| `OLLAMA_URL` | адрес демона Ollama | `http://127.0.0.1:11434` |
| `OLLAMA_MODEL` | имя локальной модели | `qwen3:1.7b` |
| `OLLAMA_TIMEOUT_MS` | срок одного запроса, мс | `120000` |
| `OLLAMA_THINK` | рассуждать ли перед ответом | `true` |
| `OLLAMA_TEMPERATURE` | температура генерации | `0` |

Ключ облака нужен **только** облачному провайдеру, и это видно в двух местах, где раньше стояла
проверка «ключа нет — работать нельзя»:

- `RagCli.main`: без ключа прогон отказывается запускаться только при `cloud`; при `local` он
  идёт, потому что облачного счёта не тратит;
- `RagSession.keyMissing` (`rag-ui`): страница дней 23–25 запускает прогон без ключа, если
  провайдер локальный, — вместо прежнего «Ключ DEEPSEEK_API_KEY не найден». Страница при этом
  печатает в консоль, кем она отвечает: «Генерация: локальная модель qwen3:1.7b (демон Ollama)».

## 4. Как это запускается

```bash
# демон и модели (один раз)
brew services start ollama
ollama pull qwen3:1.7b      # генерация
ollama pull bge-m3          # векторы (нужна была уже в дни 21–22)

# прогон RAG локальной моделью: индекс, поиск, ответы — всё на этой машине
LLM_PROVIDER=local ./gradlew :rag:ragDemo -Pdemo.live=1 --args="--dir=build/rag-local"

# тот же прогон облачной моделью (для сравнения) — ключ из server/.env
./gradlew :rag:ragDemo -Pdemo.live=1 --args="--dir=build/rag-cloud"

# день 24 (ответы с цитатами и проверкой) локальной моделью
LLM_PROVIDER=local ./gradlew :rag:ragDemo -Pdemo.live=1 --args="--dir=build/rag-local --grounded"

# страница дней 23–25 локальной моделью
LLM_PROVIDER=local ./gradlew :rag-ui:run     # http://127.0.0.1:8098
```

Флаг живого прогона (`-Pdemo.live=1`) обязателен и в локальном режиме: облачного счёта такой прогон
не тратит, но идёт десятки обращений к модели и минуты времени, и случайный запуск без флага так же
нежелателен.

## 5. Сравнение: та же система, две модели

Сравнивались две генерации при **одном** поиске: локальная `qwen3:1.7b` (Ollama) и облачная
`deepseek-v4-flash`. Вопросы, настройки этапов, индекс и порядок обращений одни и те же, поэтому
разница в числах — разница моделей. Прогоны: `build/rag-local` (локальная, индекс взят готовым),
`build/rag-local-second` (локальная, повтор — для стабильности) и `build/rag-cloud` (облачная).
Отчёты с ответами целиком — `report.md` и `log.md` в каждом каталоге.

### 5.1 Качество: оценки по фактам

Оценка 0–2 считается по фактам ожидания и у всех режимов одна: 0 — ответа нет или он неверен,
1 — часть ожидаемых фактов, 2 — все. Считает её `Check`, а сводку — `Stages.summary`
(тот же код, что в прогоне дня 23, — второго набора формул нет).

| Метрика | Локальная, прогон 1 | Локальная, прогон 2 | Облачная |
| --- | --- | --- | --- |
| Средняя оценка без базы | 0,00 из 2 (0 из 19 фактов) | 0,00 (0 из 19) | **0,50** (5 из 19) |
| Средняя оценка базового RAG | 1,20 (11 из 19) | 1,00 (10 из 19) | **1,60** (15 из 19) |
| Средняя оценка улучшенного RAG | 1,10 (10 из 19) | 1,30 (13 из 19) | **1,60** (15 из 19) |
| Source Hit Rate (базовый / улучшенный) | 8/9 · 9/9 | 8/9 · 9/9 | 8/9 · 8/9 |
| Оценка выросла / та же / упала (улучшенный против базового) | 2 / 6 / 2 | 3 / 7 / 0 | 1 / 8 / 1 |
| Цена фильтра: отсеяно · из них правильных | 6 · 0 | 6 · 0 | 15 · 2 |
| Потери: поиск / порог / второй этап | 0 / 0 / 0 | 0 / 0 / 0 | 0 / 1 / 0 |

Что из этого следует:

- **Облачная модель отвечает точнее даже без базы.** Пять фактов из девятнадцати она называет
  по памяти, локальная — ни одного. Хуже того, без базы локальная модель **выдумывает**: на вопрос
  о том, что осталось у Степана Трофимовича после смерти жены, оба её прогона сочинили символику
  («серебряный набалдашник символизировал его роль в духовном мире»), которой в романе нет.
  Облачная в том же режиме дала ответ, частично совпавший с ожиданием (сын, воспитание Варварой
  Петровной), — это и есть разница 0,00 против 0,50.
- **С базой обе модели работают, но облачная ровнее**: 1,60 против 1,20 и 1,00. Разрыв меньше, чем
  без базы, — найденный текст важнее того, кто пересказывает, и это подтверждение того, что RAG
  не обесценивает слабую модель, а подтягивает её.
- **Поиск при этом общий, и это видно**: попадание источника у локальной руки даже выше (9 из 9
  против 8 из 9) — потому что **переписывать запрос и оценивать кандидатов тоже умеет модель**,
  и здесь 1.7B не проиграла: её переписывание дало 9 попаданий из 9, а облачная на одном вопросе
  испортила выдачу (потеря по порогу). Так что отставание локальной руки — отставание генерации,
  а не поиска.
- **Разница между двумя прогонами локальной модели (1,20 против 1,00) того же порядка, что разрыв
  с облачной (1,20 против 1,60)**. Это ключевое наблюдение дня: один прогон слабой модели ничего
  не доказывает, и решение «локальная или облачная» нельзя принимать по одному числу.

### 5.2 Скорость: время и токены

| Метрика | Локальная | Облачная |
| --- | --- | --- |
| Время прогона десяти вопросов | 2 мин 48 с (индекс готов) | 5 мин 6 с |
| То же, с пересборкой индекса | 2 мин 42 с (сборка 6,3 с) | 5 мин 6 с (сборка 6,4 с) |
| Токены базового RAG (запрос + ответ) | 25 122 + 3 789 | 23 820 + **2 427** |
| Токены без базы (запрос + ответ) | 856 + 3 826 | 982 + **35 617** |

- **Локальный прогон идёт быстрее почти вдвое** — 2 м 48 с против 5 м 6 с, — и это не про «модель
  на моём ноутбуке мощнее облака»: у локальной модели короче ответы и меньше контекст. Считается
  другое: 30 обращений за 168 с — это около 5–6 с на обращение, что совпадает с числами дня 27
  (4–8 с на запрос к `qwen3:1.7b` при `think=true`).
- **Облачная модель тратит больше токенов на ответ**: 2 427 против 3 789 в базовом режиме — при том,
  что ответы у неё **длиннее** по символам (290 против 212 знаков). Значит, локальная модель тратит
  токены на рассуждение, а не на ответ: у неё бюджет уходит в `think`.
- **Строка «без базы» у облачной модели — 35 617 токенов ответа на десять коротких ответов.** Это
  не ошибка счёта: число сообщает API, и у thinking-модели в него входят токены рассуждения. Отсюда
  практический вывод: по счёту за токены сравнивать модели «в лоб» нельзя, не зная, что именно
  модель положила в счёт.
- **Поиск у обеих моделей общий и по времени копеечный**: 9 обращений к векторной модели `bge-m3`
  заняли доли секунды каждое (`Retrieval.millis` в логе), а основное время съедают обращения
  к генерации.

### 5.3 Стабильность: повтор против повтора

Два прогона локальной модели на тех же вопросах, при `temperature = 0` и одном индексе:

| Что сравнивалось | Результат |
| --- | --- |
| Ответов сравнено (10 вопросов × 3 режима) | 30 |
| Совпало дословно | **24 из 30** |
| Разошлось по тексту | 6 (схожесть от 0,21 до 0,71 символов) |
| Изменилась оценка 0–2 | 2 из 30 (`q07` улучшенный 0 → 2, `q10` базовый 2 → 0) |
| Средняя оценка базового режима | 1,20 → 1,00 |
| Средняя оценка улучшенного режима | 1,10 → 1,30 |

- **Ноль температуры не даёт детерминизма.** Это самая неожиданная строка дня: 6 ответов из 30
  разошлись при нулевой температуре, и два из них поменяли оценку — то есть **вердикт по вопросу**.
  Причина не в коде (один и тот же контекст, одна и та же модель): у Ollama ответ зависит от
  батчинга и округлений в вычислениях, и повторный прогон с теми же входами даёт другой текст.
- **Разошлись формулировки, а не факты, — но не всегда.** Пример дешёвого расхождения (`q06`,
  схожесть 0,71): «представлял свинью, грозу, роды с первым криком ребёнка и … играл «Марсельезу»»
  против «…играл на фортепиано и представлял сценарии: свинью, грозу, роды». Пример дорогого
  (`q07`, схожесть 0,34): в одном прогоне модель пересказала эпизод («произносил извинения в виде
  нового оскорбления»), в другом — процитировала его («протянул за нос двумя пальцами… пробормотал»),
  и оценка разошлась с 0 до 2.
- **Худший случай — вопрос, ответа на который в базе нет** (`q10`): один прогон отказался отвечать
  и получил полный балл, другой сочинил «историю Верховенского» по фрагментам и получил ноль.
  Для системы, которая обязана молчать там, где не знает, это разница между правдой и выдумкой.

Практический вывод: у локальной модели стабильность — **отдельная метрика, а не свойство**
(«маленькая модель повторяема»); её надо мерить, и она мерится одним повтором.

## 6. Чего локальная модель не умеет и где облачная нужна

Кроме качества и стабильности, вылезло три вещи — все получены на этом же наборе:

1. **JSON-протокол дня 24 модель выполняет, а решения по нему принимает хуже** (§7). Форма ответа
   правильная — ответы приходят разобранными, с источниками и цитатами, выдуманных ссылок 0
   и невалидных цитат 0, — но на вопросе, ответ на который в базе есть, модель отказалась отвечать
   («ни одно утверждение не подтверждено цитатой»), а её предыдущий режим ответил верно.
2. **Без базы модель не молчит, а сочиняет** (§5.1). Облачная в том же режиме отвечает по памяти
   точнее и не выдаёт символизм за факт романа.
3. **Язык ответа не держится** (§5.1 и день 27): при системном сообщении — голом вопросе — модель
   может ответить украинским или переписать слово латиницей (`Jupiter`, `Жупитер`). У облачной
   модели такого не наблюдается ни в одном из прогонов.

Отсюда — граница применения: локальная модель годится для прогонов, где допустимы ошибки и нужна
**бесплатность и приватность** (индекс, поиск, отладка промптов, регрессия поиска), а для ответов
людям — там, где важна верность, — нужна облачная; но каждая из них запускается **одной и той же
системой** и переключается одной переменной, что и было целью дня.

## 7. Grounded-прогон дня 24 локальной моделью

День 24 требует от модели не пересказа, а проверяемого ответа: объект JSON с источниками и дословными
цитатами, отказ там, где подтверждать нечем, и программная проверка каждой цитаты по тексту чанка.
Прогон на трёх первых вопросах (`LLM_PROVIDER=local ./gradlew :rag:ragDemo -Pdemo.live=1
--args="--dir=build/rag-local-ground --grounded --only=q01,q02,q03"`, отчёт
`build/rag-local-ground/report.md`):

| Вопрос | Предыдущий режим | Grounded | Источник | Цитата | Подтверждено | Отказ |
| --- | --- | --- | --- | --- | --- | --- |
| q01 (что осталось после смерти жены) | нет | нет | ✓ | ✓ | ✓ | — |
| q02 (предмет с серебряным набалдашником) | нет | верно | ✓ | ✓ | ✓ | — |
| q03 (сколько раз видел сына) | верно | нет | — | — | — | лишний |

Итог: **Answer Accuracy 1 из 3**, Source Coverage 2 из 2, Quote Coverage 2 из 2, Grounded Answer
Rate 2 из 2, выдуманных ссылок 0, невалидных цитат 0. Предыдущий режим (без цитат) был верен
в 1 из 3.

Что это значит:

- **Форма протокола держится.** Модель возвращает разбираемый JSON, ставит номера фрагментов,
  цитирует дословно, и ни одна цитата не оказалась выдуманной — проверка по тексту чанка пропустила
  обе цитаты. Для модели в 1,7B это не само собой разумеется: цитата проверяется дословно, и обрывок
  или пересказ не прошёл бы.
- **Отказ срабатывает там, где не нужно.** На q03 ответ в базе есть («видел сына дважды»), но модель
  решила, что ни одно её утверждение не подтверждено цитатой, и честно отказалась. Формально отказ
  правильный (лучше молчать, чем сочинять), но по существу — потеря: **правило «не знаю» сильнее
  правила «ответь»**, и на слабой модели это видно на каждом третьем вопросе.
- **Отсюда и цена маленькой модели в RAG**: она не ухудшает поиск, но заставляет либо принимать
  лишние отказы, либо ослабить проверку цитат — а ослаблять её значит терять то, ради чего день 24
  сделан.

## 8. Страница сравнения: те же числа на экране

То, что выше посчитано в консоли и лежит в файлах, показывает страница дней 23–25
(`./gradlew :rag-ui:run`, http://127.0.0.1:8098): у неё появился раздел «Сравнение моделей: локальная
и облачная». Кнопка «Сравнить модели» прогоняет один и тот же набор тем же конвейером обеими
моделями и показывает три обещанных разреза — качество, скорость, стабильность, — а рядом ответы
обеих моделей по каждому вопросу.

- **Обе руки идут по одному индексу.** Раздел сравнения пользуется тем же файлом поиска, что и
  прогон страницы, и своего индекса не собирает: индексировать базу дважды значило бы получить два
  поиска под одним сравнением. Если индекса нет, запуск отвергается с причиной, а не собирает его
  молча.
- **Модели и повторы выбирает человек.** Вопросов — до десяти, повторов — до пяти; по умолчанию
  повтор **один**: это уже полное сравнение качества и скорости двух моделей, а второй повтор ничего
  к ним не добавляет — он добавляет разрез стабильности и стоит ещё одного набора вопросов на каждой
  модели, поэтому включают его осознанно. Пока повтор один, раздел стабильности честно говорит,
  что сравнивать нечего.
- **Облачной модели может не быть.** Без ключа сравнение идёт по локальной модели, а в разделе
  стоит причина словами: пустые колонки читались бы как «модель ответила плохо».
- **Считает сервер, а не браузер.** Оценки, средние по режимам, попадания источников и схожесть
  повторов приходят посчитанными тем же кодом, что у прогона (`Stages`, `Check`, `textSimilarity`):
  второй набор формул на странице разошёлся бы с отчётом при первой правке.

### 8.2. Отказ на уровне JVM: почему он тоже назван

Проверка на живой странице вылезла наружу одним случаем, который стоил правки в коде. Страница
работала с прошлого запуска одиннадцать часов, и за это время сборка перезаписала jar-ники в
`build/`: классы, которые JVM ещё не загрузила, перестали находиться, и прогон падал с
`java.lang.NoClassDefFoundError: com/osvin/aichallenge/models/ChatMessage` внутри
`Prompt.withoutContext`. Выглядело это так:

> Сравнение готово: прогонов 0 из 2 за 0,0 с.

То есть **сравнение объявляло себя состоявшимся, не сделав ни одного прогона**: `NoClassDefFoundError` —
это `Error`, а `catch (Exception)` его не ловит; исключение уходило мимо ветки отказа в `finally`,
который и объявляет работу законченной (`state = done`), а счётчик прогонов оставался нулевым.
Пустая таблица с подписью «готово» читается как результат сравнения, которого не было, — и именно
так это выглядит для человека, который нажал кнопку.

Правка: на уровне работы (прогон сравнения, прогон вопросов и сборка индекса в `RagSession`) ловится
`Throwable`, а не `Exception`, и `Error` попадает в то же поле причины, что и отказ модели. Отмену
по-прежнему пробрасываем, а точечные отказы этапов (`QuestionRunner`) по-прежнему ловят `Exception`:
там `Error` — это поломка JVM, а не «режим не ответил», и превращать её в отказ одного столбца нельзя,
она обязана остановить работу. Проверка на это есть в `CompareSessionTest`: подставная модель падает
с `NoClassDefFoundError`, и сравнение обязано быть провалом с названной причиной.

Сам по себе `NoClassDefFoundError` — не дефект кода, а следствие того, что сборка шла под работающей
страницей. Правило простое: **после пересборки страницу перезапускают** (`hub restart`, или заново
`./gradlew :rag-ui:run`) — JVM держит классы открытыми и подмену файлов не переживает.
